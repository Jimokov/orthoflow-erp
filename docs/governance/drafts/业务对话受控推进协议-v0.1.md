# 业务对话受控推进协议（草案）v0.1

> 身份：已审核通过的治理草案；规定性条款已写入根目录 `AGENTS.md`，本文件保留完整解释与设计依据，不新增业务规则。
> 目的：让业务推进有可追溯边界，同时保留流程推演、方案比较和探索性思考的开放性。

## 1. 核心原则：护栏，不是问卷

本协议只控制会改变项目事实或推进方向的事项，不规定每轮必须使用固定标题、固定问题数量或固定回答模板。

业务推演可以自然展开，可以提出多个候选路径、模拟异常、比较方案和暴露缺口；但必须让读者看得出哪些是当前事实、哪些是基于事实的推导、哪些是探索性方案、哪些仍需确认。

控制的目标是防止无依据的内容进入当前事实，不是压缩想象力，也不是把对话变成逐项填表。

## 2. 进入业务推进前的最小核对

只有在下列情形发生时，才执行启动盘点：新对话承接、切换模块或阶段、推进方向改变、发现资料冲突，或准备写入／发布正式资料。

启动盘点只需说明：当前模块与端、当前阶段、当前唯一任务、直接相关的当前资料、明确不进入的范围，以及是否存在真实待决事项。普通的局部推演不因格式要求重复全量盘点。

## 3. 业务推演的开放空间

在边界已经确认的范围内，助手可以：

- 先用业务语言还原完整流程，再决定使用流程图、对象表、原型或其他载体；
- 通过情景演练发现流程断点、对象缺失、结果回写断裂或责任不清；
- 提出候选方案并说明依据、收益、风险和待确认影响；
- 继承已有主线、对象结果图、探索记录和低保真，不因换计划而重做已有成果；
- 在不改变正式事实的前提下，用示例字段、示例状态和模拟数据帮助理解。

探索内容必须保持可回退：示例不自动成为字段，模拟状态不自动成为正式状态，原型按钮不自动成为业务能力。

## 4. 必须停下并回到资料层的情形

下列事项会改变业务事实，必须暂停受影响链路并确认来源或用户取舍：

- 新增或修改对象、责任、权限、状态、正式结果或跨模块回写；
- 把探索节点、原型行为或历史材料提升为当前规则；
- 资料之间发生冲突，或结论只能依赖聊天记忆成立；
- 推进方向、阶段顺序、页面集合或模块边界发生改变；
- 需要生成新模块、后台能力、库存流程或未登记接口。

停下时只报告缺口、影响、正式资料位置和恢复条件，不用行业惯例或“看起来合理”的内容补齐。

## 5. 推进方向变更

整体计划改变时，按以下顺序处理：

```text
识别方向变化
→ 暂停旧计划执行
→ 形成计划调整可行性论证
→ 用户确认调整方向
→ 全量检查当前资料及已有探索成果
→ 形成新计划
→ 用户确认新计划
→ 发布替代关系并同步索引、驾驶舱和进度
→ 开启新计划的第一个任务
```

计划论证不重复证明已经存在的业务流程，也不把旧计划失效本身伪装成业务问题。已有业务主线、流程图、低保真和探索记录默认进入全量检查的继承基线，只有发现冲突或缺口时才处理。

## 6. 资料与回复的可追溯性

- 当前事实必须能定位到当前正式资料；推导、候选和待确认内容使用明确的语义标记，但不要求逐句加格式化标签。
- 正式资料发生版本变化时，报告原版本、新版本、变更原因、影响文件和当前任务是否变化。
- 历史、废止和替代资料保留原身份，不重新充当当前事实；旧计划只通过替代关系退出，不静默删除。
- 每条用户可见助手回复使用当日连续回复编号；编号服务于追溯，不改变业务推演的表达方式。

## 7. 每轮完成标准

一轮业务推进完成时，应能回答：本轮推进了哪个业务问题，依据了哪些当前资料，形成了什么结论，哪些内容仍未确认，下一项唯一可执行动作是什么。

如果本轮只有探索、没有形成业务结论，应明确记录“未改变业务基线”，而不是为了看起来有进度而制造规则或计划。

## 8. 本草案的审核边界

本草案只提出对话和推进的控制方式。经用户确认后，才讨论是否将其中哪些条款写入 `AGENTS.md`；未确认前不改变项目业务规则、页面、接口、路线或验收状态。
