# 项目资料财产保护与可回退推进总则 v0.1

> 状态：当前有效项目治理规则
>
> 生效日期：2026-09-09
>
> 资料身份：本文件只约束项目资料的归档、恢复、迁移、同步和环境重建方式，不承载任何模块业务事实。

## 1. 目的与适用范围

本总则保护项目已经形成的资料财产，确保任何电脑、仓库或备份环境都能在不破坏原资料的前提下恢复并继续工作。

以下操作必须先执行本总则的闸门：

- 建立或更新独立归档仓库、网盘快照或恢复包；
- 批量复制、跨仓库同步或从备份恢复资料；
- 重建新的工作电脑、工作目录或讨论环境；
- 文件迁移、改名、合并、替代、批量整理或大范围链接修复；
- 可能改变唯一事实源、远端历史、分支、标签或资料身份的操作。

普通只读检查和单一已确认文件的局部增量修改，按根 `AGENTS.md` 的现有规则执行；如果操作扩大为批量、跨仓库或可覆盖范围，立即转入本总则。

## 2. 资料身份与唯一事实源

1. 现有主仓库及其当前有效模块资料继续是唯一工作事实源；本总则不改变任何模块资料的归属。
2. 归档仓库、网盘快照和恢复包是保护与恢复载体，不自动成为业务事实源，也不反向覆盖主仓库。
3. 每个文件在操作前后都必须保留身份：当前有效、历史、候选或探索；候选和探索资料不能因复制或恢复变成当前事实。
4. 每个归档项必须能回指原仓库路径、原始 commit、文件版本和归档时间；无法回指的副本不能作为可靠恢复资料。
5. 聊天记录只用于来源追溯或经批准的历史迁移，不直接补成当前业务事实。

## 3. 风险分级与确认边界

| 等级 | 操作 | 执行条件 |
|---|---|---|
| 绿色 | 只读盘点、复制到隔离区、追加新快照、建立新分支或新归档提交 | 通过范围和基线检查后可执行 |
| 黄色 | 修改正式资料、批量链接修复、跨仓库同步、发布归档标签 | 必须完成完整性检查，并在结果中报告文件和 commit |
| 红色 | 删除或覆盖资料、重写历史、强制推送、恢复覆盖当前工作树、切换唯一事实源 | 必须获得用户针对该操作的单独明确确认；默认停止 |

风险等级只约束资料操作，不替代业务规则确认。任何等级出现来源不明、版本冲突、哈希不一致或无法回退时，立即停止受影响链路。

## 4. 六道推进闸门

### 闸门一：范围闸门

记录操作目的、来源仓库或快照、目标位置、包含文件、排除文件、资料身份、风险等级和预期结果。

**通过标准：** 任何执行者都能据此回答“改什么、从哪里来、放到哪里、哪些明确不动”。

### 闸门二：基线闸门

在操作前记录：当前分支、`HEAD`、远端引用、工作区状态、文件清单、必要的文件哈希、当前有效版本、历史替代关系和未提交改动。

**通过标准：** 原始主仓库可以在操作后按原 commit 或原始副本恢复，且未提交的既有工作区改动已经被识别并隔离。

### 闸门三：隔离执行闸门

优先在临时目录、新分支或新归档仓库执行复制与整理。归档采用复制并追加；主仓库和原始快照不作为整理工作区。

**通过标准：** 隔离区的变更可以单独比较、撤销或丢弃，且主仓库没有出现范围外变化。

### 闸门四：完整性与防污染闸门

对照基线检查文件数量、哈希、链接、版本、当前／历史／候选标签、重复文件、旧名称、失效来源和被替代结论残留；确认归档没有把候选、草稿或历史材料包装成当前事实。

**通过标准：** 发现的差异都有明确解释；未解释差异、断链或身份不明项全部停止，不以“看起来完整”放行。

### 闸门五：恢复演练闸门

在干净的临时目录或另一台电脑中，从主仓库和归档资料实际恢复一次。按恢复说明找到项目驾驶舱、治理规则、任务矩阵、目标模块总池、当前有效资料和当前恢复点，并验证关键链接与来源 commit。

**通过标准：** 新环境可以区分当前事实、历史、候选和探索资料，可以定位下一项任务，且不依赖聊天记忆才能继续。

### 闸门六：发布与记录闸门

只提交本次限定范围，记录新增、修改、未改变和排除的文件；提交后记录 commit、标签、推送分支并验证远端包含该提交。归档清单同步登记来源 commit、归档 commit、时间和验证结果。

**通过标准：** 文件、Git 状态、远端状态和恢复结果均可复查；未完成远端验证时，不宣布归档或恢复完成。

## 5. 归档仓库的最低结构

独立归档仓库至少包含：

- `README.md`：说明它是归档载体，不是当前事实源；
- `恢复说明.md`：给新电脑的读取顺序、恢复步骤和停止条件；
- `归档版本清单.md`：每个文件的原路径、原始 commit、版本、身份和归档 commit；
- 按日期或里程碑追加的资料快照；
- 归档提交或标签的校验记录。

归档仓库不删除旧快照，不直接编辑主仓库资料，不把聊天全文、缓存、临时目录和未确认方案混入当前快照。需要保留的历史或候选资料必须保留其身份标记和来源。

## 6. 新电脑的恢复顺序

1. 拉取主仓库和归档仓库，先验证远端地址、分支和 commit；
2. 读取归档仓库的恢复说明与版本清单；
3. 读取根 `AGENTS.md`、`README.md`、`CONTEXT.md`、范围登记和项目治理资料；
4. 读取任务与对话承接矩阵、侧边对话承接索引和最近有效日报；
5. 读取目标模块的 `00-START-HERE.md`、当前恢复卡及其直接当前有效资料；
6. 对照来源 commit 和版本清单完成一次完整性核验；
7. 只有在当前事实、任务绑定、恢复点和下一入口均可定位后，才开始新的业务讨论。

GitHub 能恢复项目文件和版本，但不能保证恢复 Codex 对话界面；因此恢复工作的完成依据是正式资料、恢复卡、来源清单和可复查提交，而不是聊天窗口是否仍显示历史。

## 7. 异常停止与回滚

- 任一闸门失败，停止受影响的复制、恢复或同步，不继续整理业务内容；
- 原始主仓库、原始快照和未提交工作区改动保持不动；
- 先记录差异、影响和恢复条件，再决定修复资料或回退隔离区；
- 没有明确回退路径的操作不得进入红色操作执行；
- 本总则只允许回到已验证的资料版本，不允许用新整理结果静默覆盖旧资料。

## 8. 完成判定

一次资料保护或恢复操作只有同时满足以下条件才算完成：

1. 范围、基线、隔离和风险等级有记录；
2. 原始资料未被未授权删除、覆盖或改身份；
3. 当前、历史、候选和探索资料仍能区分；
4. 关键文件、链接、来源 commit 和版本清单通过校验；
5. 干净环境能够按恢复说明定位当前事实和下一恢复点；
6. 限定提交已经推送并完成远端验证，且结果已向用户报告。
