# 跨对话任务编排与增量收工治理方案 v0.2

> 状态：当前有效治理方案
>
> 生效日期：2026-08-28
>
> 目的：在保留“从正式沉淀继承业务基线”的前提下，补足跨对话、跨端并行任务的发现、承接、收工和建议输出机制。

## 一、问题判断

本次库存管理遗漏说明：模块资料继承链已经存在，但项目级任务发现链和盘点回复的判断链还不完整。

- 模块资料回答“这个模块已经确认了什么、从哪里继续”；
- 项目任务索引回答“项目当前有哪些任务、各自处于什么阶段”；
- 盘点回复还必须回答“这些事实代表什么、建议怎样处理”。

治理目标不是增加全项目重读，而是在业务继承前增加轻量任务导航，在盘点回复中补足判断和建议。

## 二、职责分层

### 1. 三类资料各自负责什么

| 层级 | 当前权威位置 | 负责内容 | 不负责内容 |
|---|---|---|---|
| 项目驾驶舱 | 根 `README.md` | 项目主线、当前主任务、阶段摘要、全局恢复点 | 全部任务明细、模块业务事实 |
| 项目任务索引 | `docs/progress/任务与对话承接矩阵.md` | 全部活动任务、任务类型、来源、阶段、恢复点、下一入口、依赖 | 业务规则、对象定义、页面事实 |
| 模块正式资料 | 模块总池、规则池、接口池、设计池、验收池 | 模块业务事实和正式结果 | 其他模块内部流程、项目任务总览 |

“当前主任务”是驾驶舱中的优先级摘要；“活动任务集合”是任务矩阵中的项目运行集合。主任务不等于唯一活动任务。

### 2. 活动任务的范围

活动任务是项目当前仍需要承接、推进、等待确认或保留恢复点的任务，包含但不限于：

- 业务模块任务；
- 跨模块候选或治理任务；
- 已暂停但保留明确恢复点的任务。

历史任务、已退出职责的旧对话和仅供追溯的资料不计入活动任务集合。

## 三、盘点型回复原则

适用于启动盘点、收工盘点、承接核验、状态审查和项目状态报告的回复，应同时表达：

1. **我看到了什么**：实际核对到的资料、任务或变化；
2. **这代表什么**：对当前任务、并行任务、风险或恢复条件的判断；
3. **我建议怎么处理**：下一步建议，或建议暂不动作及理由。

建议与执行、用户决定分开。提出建议不代表立即执行，也不要求用户当场作出业务取舍。该原则不固定标题、篇幅、问题数量或句式。

## 四、新对话启动协议

### A. 项目任务脉冲

每个新对话开始时，先读取以下最小索引：

- 根 `README.md`；
- `docs/progress/任务与对话承接矩阵.md`；
- 当日日报或最近一次有效日报中的恢复信息。

任务脉冲只确认并列出活动任务的索引信息：模块／任务、端、状态、当前阶段、当前唯一任务、恢复点、下一入口和直接依赖。它不读取其他模块正文，不复核其他模块业务事实。

### B. 指定模块承接

完成任务脉冲后，按现有规则承接用户指定模块：

1. 读取范围登记和目标模块 `00-START-HERE.md`；
2. 读取本轮直接相关的当前有效规则、接口、路线图和验证载体；
3. 核对目标模块的当前任务、恢复点和项目索引是否一致；
4. 只在冲突影响当前链路时暂停；不受影响的工作可以继续。

新对话仍以正式模块资料作为业务基线，任务脉冲不替代模块承接。

### C. 启动完成标准

新对话承接完成，必须满足：

- 全部活动任务已经能从项目索引定位；
- 用户指定模块的正式继承基线明确；
- 当前唯一任务、恢复点和下一入口明确；
- 并行任务和直接依赖已说明；
- 启动盘点回复包含事实、判断和建议。

“每个新对话”是触发条件；“每日首次业务推进”仍按现有每日启动盘点执行。两者都只做最小必要读取，不互相替代。

## 五、任务矩阵的最小字段要求

任务矩阵不改变其“关系索引、不保存业务事实”的职责。每个活动任务应能定位：

| 字段 | 作用 |
|---|---|
| 任务对象与端 | 区分模块、治理任务及 APP／Web 等端 |
| 任务状态 | 活动、暂停、阻塞、待承接或已完成等状态；现有记录不强制立即改写 |
| 来源／承接对话 | 只用于追溯与定位 |
| 当前阶段 | 判断推进边界 |
| 当前唯一任务 | 说明该任务本轮聚焦内容 |
| 恢复点 | 下次从哪里继续 |
| 下一入口 | 新对话如何进入 |
| 依赖与影响 | 标注跨模块关系和阻塞范围 |
| 最近同步时间 | 识别索引是否可能滞后 |

新增字段或状态词属于治理变更，需先修改进度规范和矩阵说明，不把草案字段直接当作当前事实。

## 六、收工协议：两层、增量、条件性同步

### 1. 当前任务收工

只整理本轮实际改变的内容：直接承载结论的正式资料、模块总池或首页、当前任务行、当日日报，以及发生资料变化时的 Git 提交。

### 2. 项目状态收工

只检查项目索引是否发生变化：

- 是否新增、暂停、恢复或完成活动任务；
- 主任务或阶段是否变化；
- 驾驶舱摘要是否滞后；
- 并行任务之间是否出现新的依赖或冲突；
- 是否有需要其他对话或其他端继承的资料变化。

项目状态收工不是全项目重审。没有项目级变化时，只记录“项目活动任务无变化”，不重写驾驶舱，也不重读无关模块。

### 3. Git 与跨端同步

- 发生需要跨对话或跨端继承的文件变化时，必须提交并推送，记录远端验证结果；
- 只有讨论、无资料变化时，不为形式制造提交；
- 资料尚未推送时，可以继续不依赖该变化的本地工作，但不得宣称跨端承接已完成。

## 七、跨对话、跨端继承路径

```text
项目任务索引
  ↓
指定模块正式承接资料
  ↓
当前任务与恢复点
  ↓
本轮业务推进
  ↓
当前任务增量收工
  ↓
项目状态增量同步
  ↓
Git 远端可继承状态
```

- 对话记录只作来源追溯，不作业务事实来源；
- 模块正式资料决定业务事实，任务索引决定任务定位；
- 本地工作副本用于推进，Git 远端是跨端传输边界；
- 任务索引与模块事实冲突时，以模块正式资料为准并修正索引。

## 八、失败与滞后处理

- 任务索引漏记：暂停受影响的承接判断，补登记任务、来源和恢复点；
- 驾驶舱滞后：以正式资料和任务矩阵为准，修正当前快照并在日报记录更正；
- 远端未同步：标明未同步状态和恢复条件，不宣称跨端可继承；
- 模块事实不足：登记为桩子或承接缺口，不用索引、行业惯例或聊天记忆补全。

## 九、建议写入 `AGENTS.md` 的原则

建议写入以下两条，不写入完整字段模板或固定回复格式：

> 盘点型回复不止罗列事实；应同时说明已核对到的内容、这些内容代表的当前判断，以及建议的处理方向。建议与执行、用户决定分开：提出建议不代表立即执行，也不要求用户当场作出业务取舍。该原则不固定回复标题、篇幅、问题数量或表达句式。

> 新对话先通过项目级任务索引发现全部活动任务，再按现有正式资料承接用户指定模块；项目主任务不等于唯一活动任务。任务发现只读取项目索引，不替代模块正式资料，也不要求全量重读其他模块。

## 十、启动实验与验收

### 实验目的

验证一个没有旧聊天上下文的新对话，能同时发现库存管理与手术植入两个并行任务，并仍只承接用户指定的一个模块。

### 实验前快照

记录以下内容，不修改业务资料：

- `README.md` 当前主任务；
- 任务矩阵中的全部活动任务；
- 最近日报中的恢复点；
- 当前 Git 提交和远端状态。

### 实验指令

在新对话中发送：

> 按项目当前正式资料启动一次新对话承接实验。先完成项目级活动任务脉冲，再承接“库存管理”模块。只读取项目规则、驾驶舱、任务与对话承接矩阵、最近日报、库存管理模块总池及直接相关正式资料；不读取旧聊天，不推进库存业务。请报告：发现的全部活动任务、库存模块的当前阶段／唯一任务／恢复点／下一入口、与并行任务的关系，以及建议如何处理。

### 通过标准

- 同时发现库存管理和手术植入等当前活动任务；
- 不把库存管理的“当前主任务”误报为项目唯一任务；
- 先完成索引发现，再承接库存模块；
- 不读取旧聊天，不把任务索引当业务事实；
- 不进入库存业务设计；
- 回复包含“看到什么、代表什么、建议怎么处理”；
- 读取范围没有扩张为所有模块全量资料。

### 失败判定

出现以下任一情况即失败：漏掉并行任务、直接进入业务、把主任务当唯一任务、读取旧聊天、把索引内容写成业务事实、无建议停在事实罗列，或因为任务脉冲而全量重读项目。

实验失败只修正治理机制和索引，不修改库存或手术植入业务规则。

## 十一、实施顺序

1. 确认本草案的分层、增量和非机械化原则；
2. 将两条盘点／任务发现原则写入 `AGENTS.md`；
3. 将项目任务脉冲、活动任务范围和条件性 Git 同步写入进度规范；
4. 按需补充任务矩阵字段，不立即重写历史行；
5. 用库存管理与手术植入执行启动实验；
6. 实验通过后，再决定是否调整驾驶舱展示。

## 十二、预期结果

- 新对话仍从正式沉淀继承业务基线；
- 并行任务不会因用户只提到一个模块而被隐藏；
- 收工不会变成全项目重审；
- 盘点回复同时提供事实、判断和建议；
- 治理控制来源、边界、同步和追溯，但不限制自然表达、宏观判断和探索能力。
