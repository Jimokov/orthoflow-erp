> 状态：当前执行设计；归档仓库已建立并按里程碑追加
>
> 盘点日期：2026-09-09
>
> 资料身份：本文件是归档实施方案和基线记录，不承载任何模块业务事实，不替代主仓库当前有效资料。

## 1. 目标与基本决定

本方案服务两个目标：

1. 任意电脑从云端拉取一份资料后，可以区分当前事实、历史、候选和探索，并定位一个可继续的任务恢复点；
2. 主仓库、Git 历史、未提交资料和已知临时成果不因归档、恢复或整理而丢失、覆盖或改变身份。

已确定的基本关系：

- 现有 `orthoflow-erp` 继续是唯一工作仓库和当前事实源；
- 新归档仓库只追加里程碑快照，不反向修改或覆盖主仓库；
- 每个里程碑快照采用可独立恢复的完整树，不依赖必须按顺序套用的差分补丁；
- 归档仓库中的启动说明只负责导航，业务事实仍回指主仓库的具体文件和 commit；
- 网盘保存归档仓库导出或加密快照，作为独立灾备，不作为第三个事实源。

## 3. 归档范围分层

### 3.1 完整树快照（必须）

以某个已验证的主仓库 commit 为根，原样保存该 commit 的全部已跟踪文件，不做删减和语义重写。当前基线快照必须覆盖：

- 根资料：`AGENTS.md`、`README.md`、`CONTEXT.md`、`.gitignore`；
- 项目范围、模块总池模板、治理资料、跨模块候选／遗产资料和进度资料；
- 手术通知、手术植入、库存管理及已登记业务域的全部已跟踪资料；
- `.codex/skills/business-evolution/` 的 `VERSION`、`SKILL.md` 和路由文件；
- 已跟踪的历史池、旧版本、低保真、HTML 和其他探索载体，保持原路径和文件身份。

完整树快照是“一个重要文件不丢失”的底线；启动时不要求全部阅读，但恢复时能够按清单找到它们。

### 3.2 启动资料包（必须）

在完整树快照之上，提供一份不重复业务正文的导航层，至少指向：

1. `AGENTS.md`、`README.md`、`CONTEXT.md`；
2. `docs/00-当前范围与模块登记.md`；
3. `docs/progress/任务与对话承接矩阵.md`、`docs/progress/侧边对话承接索引.md`、最近有效日报；
4. 目标模块的 `00-START-HERE.md`、当前恢复卡和当前有效资料；
5. `docs/跨模块候选资料/跨模块遗产索引-v0.4.md` 及其直接来源；
6. `.codex/skills/business-evolution/` 的版本、正文和路由规则。

启动资料包只告诉新环境“先读什么、当前到哪里、哪些不进入”；不能把它当作完整业务资料的替代品。

### 3.3 历史、候选与探索保留层（必须保留身份）

完整树中的历史版本、候选资料、草案、低保真和探索稿继续保留原始路径或清晰映射，并登记：

- 当前／历史／候选／探索身份；
- 替代关系或未替代状态；
- 不得作为当前事实的原因；
- 原始 commit、文件哈希和归档快照。

这层的目的是真实保全和来源追溯，不是让新环境把所有旧资料重新读成规则。

### 3.4 待鉴别区（必须先保护，再决定）

未提交、未跟踪、临时或工作区生成资料必须在归档实施前复制到隔离的待鉴别位置，登记原路径、状态、哈希、大小和发现时间。待鉴别区不参与当前事实启动，不得通过归档清理动作消失。

### 3.5 明确排除层

密码、密钥、`.env`、本地凭据、缓存、运行时目录和系统临时文件不进入归档仓库。排除项必须按规则或路径模式登记原因；如果某个被排除文件实际含有项目成果，先暂停并转入待鉴别区，不以“命中忽略规则”直接丢弃。

## 4. 归档仓库最低结构

归档仓库的每个里程碑快照至少包含：

```text
README.md                         # 归档仓库身份、事实源说明和快照入口
恢复说明.md                       # 新电脑恢复顺序、停止条件和下一恢复点定位方式
归档版本清单.md                   # 面向人工核验的清单
manifest/                         # 机器可读清单，每个快照一份
snapshots/
  snapshot-YYYY-MM-DD-<sha>/      # 可独立恢复的完整树快照
    project/                      # 主仓库在来源 commit 的完整树
    startup/                      # 启动导航和必要来源索引
    quarantine/                    # 经保护但尚未定级的资料
```

快照目录只追加，不覆盖旧快照。`startup/` 是导航副本，正文仍以 `project/` 中的来源文件和主仓库链接为准；如果两者不一致，快照不得发布。

每个快照还应提供逐文件追溯清单，至少记录来源路径、来源 commit、Git blob、SHA-256、大小、资料身份和校验状态；清单可采用 `manifest/files-*.tsv` 等机器可读格式。

若归档存储环境中的 `startup/` 目录不可写，可以使用等价且明确登记的 `startup-nav/`；必须在机器清单和恢复说明中保持同一路径，且不得修改 `project/` 内来源正文。

## 5. 版本清单设计

每个快照同时保存人读清单 `归档版本清单.md` 和机器清单 `manifest.yaml`。机器清单的最低字段如下：

```yaml
snapshot_id: snapshot-YYYY-MM-DD-<source_sha_short>
created_at: YYYY-MM-DDThh:mm:ss+08:00
source:
  repository: https://github.com/Jimokov/orthoflow-erp.git
  branch: main
  commit: <full_source_commit_sha>
  working_tree_status: clean | protected-uncommitted-present
archive:
  repository: <archive_repository_url>
  commit: <archive_commit_sha>
  tag: snapshot-YYYY-MM-DD-<source_sha_short>
  verification: passed | blocked
entries:
  - source_path: modules/...
    archive_path: snapshots/.../project/modules/...
    identity: current | history | candidate | exploration | uncommitted-quarantine | excluded
    version: <file_version_or_null>
    source_commit: <full_source_commit_sha>
    git_blob: <git_blob_sha_or_null>
    sha256: <file_sha256>
    size_bytes: <integer>
    relation: current | replaces:<path> | replaced_by:<path> | none
    verification: copied | hash-matched | link-checked | manually-reviewed | blocked
    note: <reason_or_scope>
```

### 5.1 清单规则

1. `source.commit` 是当前事实来源；`archive.commit` 只证明归档仓库中的快照提交。
2. `identity` 必填，禁止用目录名称猜测资料身份。
3. `version` 可以为空，但 `source_commit`、`sha256` 和 `size_bytes` 不得为空。
4. 被替代文件同时登记 `relation`，不删除历史项。
5. 工作区未提交资料使用 `uncommitted-quarantine`，不能冒充 `current`。
6. 排除项也登记，但不得写入业务正文；必须有 `note` 说明排除原因。
7. 快照清单采用追加方式；新快照只能新增记录，不能静默修改旧快照记录。

### 5.2 快照发布条件

快照只有同时满足以下条件才可标记 `verification: passed`：

- 来源 commit、分支、远端关系和工作区状态已经记录；
- 完整树文件数量与清单一致；
- 每个文件的哈希和路径通过校验；
- 当前／历史／候选／探索／待鉴别身份均可解释；
- 关键启动链接可打开并指向当前来源；
- 新电脑或干净临时目录能够按恢复说明定位当前资料和下一恢复点；
- 归档提交已推送并完成远端验证。

任一条件失败，清单标记 `blocked`，保留原始资料和隔离区，不发布为可恢复快照。

## 6. 新电脑恢复验收

恢复测试以最新完整快照为输入，不依赖原电脑缓存或聊天窗口：

1. 拉取主仓库和归档仓库，核对远端地址和 commit；
2. 读取归档仓库 `README.md`、`恢复说明.md` 和对应 manifest；
3. 校验完整树快照的文件数量、路径、哈希和资料身份；
4. 读取根治理、驾驶舱、范围登记、任务矩阵、侧边索引和最近日报；
5. 读取目标模块总池、当前恢复卡和直接当前有效资料；
6. 证明能定位当前任务、下一入口和不进入范围；
7. 证明不存在只能依赖旧聊天才能补齐的当前业务事实。
