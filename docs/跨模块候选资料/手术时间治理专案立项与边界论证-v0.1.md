## 2. 候选定位

本专案候选定位为：

> 一套持续成长的跨模块时间责任机制。它将已确认的业务时间事实、责任转换、任务与结果约束进行统一衔接，使业务员在各自业务页面内获得必要推进，而不形成独立的 APP 功能入口或替代各模块的规则所有权。

它服务于业务实际发生、责任可追溯和长期挂载可治理，不是日历功能、排班系统、单一提醒中心或固定时限模板。

## 3. 成长与归属原则

1. 专案不预先穷举所有未来模块或时限；一个模块形成新的时间责任场景时，先在本专案登记候选，再由拥有事实的模块论证。
2. 时间事实、动作权限、具体时限、任务、提醒和正式结果始终由所属模块规则／接口承载；本专案只维护共同语言、交叉关系、接入状态与来源定位。
3. 用户在 APP 内只进入订单、订单内还回、植入、未来库存相关入库及其既有待办；本专案不产生独立入口或额外页面。
4. 任何时间规则必须可追溯其业务事实、责任人、生效与失效条件、任务或结果去向；不得仅以页面倒计时或推送替代规则。
5. 专案中的候选经用户确认后，先写入事实所属模块，再同步跨模块遗产索引；本文件只登记正式去向，不复制事实正文。

## 4. 首轮论证范围

首轮只搭建共同框架，不确认具体阈值或页面。需依次确认：

1. 专案的治理目标与明确不治理范围；
2. 跨模块时间事件的共同描述骨架：业务事实、时间语义、责任、生效／失效、后果与追溯；
3. 手术通知的计划时间与手术植入的实际时间如何构成连续而不互相替代的关系；
4. 模块接入、变更、回写与退出机制；
5. 未来由全局任务、首页或订单页消费时间结果时所需的最小契约。

以下内容明确留待共同框架通过后、按所属模块逐项论证：

- 三天原则的起算事实、例外、提醒、逾期判定和管理后果；
- OCR、医院单据、手动录入或其他实际日期来源的采集与可信边界；
- 具体推送频率、强提醒阈值、免打扰规则和配置责任；
- 手术通知内借单还回的具体时间规则、未来库存相关入库及未启动模块的具体时间规则；
- Web 后台、审批、权限、技术字段、重试和实现方案。

## 6. 已确认的立项框架

1. 本专案以“减少长期无实际动作的业务挂载，并使责任可推进、可监督、可追溯”为首要目标；
2. 首轮覆盖手术通知（含既有借单还回动作）与手术植入的共同框架；未来库存相关入库只登记接入方向，不讨论其内部时限；
3. 本文件保持为跨模块候选立项入口；专案不升级为独立 APP 模块、页面组或活动任务。

## 7. 已确认的共同框架：最小治理单元

专案以“业务时间责任事件”作为最小治理单元；不管理所有日期，只管理会改变业务责任的时间事实。

每个进入治理的事件必须能够说明：

1. 关联对象；
2. 时间语义；
3. 事实来源；
4. 责任主体；
5. 有效、替换或失效关系；
6. 治理结果。

共同关系分为三层：

```text
业务时间事实 → 责任时钟 → 业务呈现
```

- 业务时间事实保存计划、实际发生、交接、提交、确认等可追溯时间；
- 责任时钟只基于当前有效事实判断是否需要行动；
- 订单、订单内还回、植入、未来库存相关入库及 G01／G03等业务承载只消费已生成的任务、风险或结果，不自行创造时间规则。

模块所有权保持不变：手术通知拥有计划手术时间及其履约、变更、无结果确认和订单内借单还回责任；手术植入拥有实际手术事件与正式植入记录；未来库存相关入库只在其规则成熟后接入内部事实；全局页面不拥有时间事实。

本节是专案共同框架的确认结论，不替代各模块的具体规则或接口。

## 8. 已确认的共同框架：事件准入与生命周期

一个时间事实只有同时满足以下条件，才进入本专案治理：

1. 关联明确业务对象；
2. 会导致某个角色需要行动、等待、确认或解除责任；
3. 具有可追溯事实来源，不是页面展示、个人备注或算法猜测；
4. 会改变可解释的业务结果；
5. 能说明何时失效、被替代或关闭。

共同生命周期只约束语义，不构成所有模块共享的固定状态机：

```text
形成 → 生效 → 替代／失效 → 关闭
```

- 形成：已有可追溯来源；
- 生效：成为当前责任判断依据；
- 替代：新的有效事实取代原计划或承诺；
- 失效：取消、撤销或正式更正使原事实不再参与判断；
- 关闭：对应责任已有正式结果，不再产生时钟或催办。

不同时间类型只使用适用分支。计划时间可以被替代；真实发生时间通常只能通过正式更正或原记录失效保留调整链。

时间事件生效不等于自动生成待办。它先进入责任判断；只有当前有效时间与未完成责任共同满足条件，才生成可追溯的任务、风险或正式结果。
