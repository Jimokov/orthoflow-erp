# 公司库存业务：销售统计到配置变更链路探索 v0.1

> 状态：暂存探索稿，非当前推进入口；待后续阶段审核，不是最低库存算法、审批流、页面或技术接口。  
> 所属任务：T4 公司库存业务宏观逻辑规划。  
> 形成日期：2026-08-31。

## 1. 本轮目标

> 方向校正：本稿由用户提出的最低库存机制触发形成，保留作后续阶段的议题材料；当前 T4 阶段一不沿此链路继续展开。

拆解用户提出的前半条链：销售统计如何进入库存判断，如何形成配置建议，业务员如何申请，公司的总库管理方如何决定配置变化，以及配置何时成为后续库存判断的依据。

本轮不展开最低库存数值、统计周期、算法、自动调拨、采购或外借细则。

## 2. 宏观链路

```text
外部业务统计结果（来源待登记）
        ↓ 作为输入
公司库存业务进行趋势／供给判断
        ↓ 形成建议
个人库存配置建议
        ↓ 被业务员发起申请
配置变更申请
        ↓ 由公司总库管理方作出管理决定
配置变更结果
        ↓ 在生效后成为新的供给基准
后续最低库存／可用性判断的参照
```

这不是一个自动闭环：统计、判断、建议、申请、管理决定和生效是不同的业务节点。

## 3. 逐步拆解

### 3.1 销售统计：外部输入来源提供的输入

销售统计回答的是过去或已发生业务中的销售／使用表现。它可能成为判断“哪些物资经常被需要、哪些业务员侧需要增加准备”的依据。

当前只能把它定位为一个尚未完成拥有者登记的外部输入结果，不能直接把它称为已经确认的“相邻业务结果”，也不能直接等同于：

- 未来一定会发生的需求；
- 现实中已经拥有的实物；
- 应当立即增加的配置；
- 最低库存数值。

销售统计的业务拥有者、是否属于某个已登记业务、统计口径和正式生效方式暂未确认。

### 3.2 智能判断：库存侧的解释过程

库存业务读取销售统计后，形成对供给配置是否需要调整的判断。这里的“智能”在宏观上先表示：由既有业务数据辅助判断，而不是人工凭感觉决定；不代表已经确定机器学习、公式或自动执行。

判断结果至少要与以下概念分开：

- 统计事实：过去发生了什么；
- 判断建议：基于统计认为可能需要调整什么；
- 管理决定：公司是否真正允许配置变化。

统计事实本身不直接改变配置，智能判断也不直接改变配置。

### 3.3 配置建议：库存侧提出的候选结果

判断可以形成“建议调整某业务员侧某类物资配置”的候选结果。它表达的是公司供给意图可能需要变化，不代表：

- 现实实物已经增加；
- 业务员已经获得对应物资；
- 最低库存已经改变；
- 公司已经承担了后续履约责任。

配置建议的结果归属更接近公司库存业务，但是否由库存业务正式形成、还是由公司管理方形成，仍需后续确认。

### 3.4 业务员申请：把建议转成管理请求

业务员根据建议或自身业务需要，向公司总库管理方发起改变个人库存配置的申请。申请是一个新的管理动作，不是配置生效本身。

这一步至少要区分：

- 建议是否被业务员采纳；
- 业务员申请的内容是否与建议一致；
- 申请针对的是配置、现实实物，还是一次性补足；
- 申请提交后由谁承担等待期间的责任。

当前不设计申请页面、审批节点或字段。

### 3.5 总库管理方决定：配置责任的管理确认

公司总库管理方接收申请后，可能形成同意、调整后同意、暂缓或不同意等管理决定。这里的“总库管理方”先作为用户提出的管理责任角色，不等同于某个已经登记的 Web 岗位。

管理决定至少可能影响：

- 个人库存配置是否改变；
- 配置从何时起有效；
- 后续最低库存／可用性判断以什么为参照；
- 是否需要另行进入实物补足履约。

管理决定改变的是配置关系，不必然同时改变现实实物关系。

### 3.6 配置生效：形成可供后续使用的正式结果

只有当配置变更达到约定的生效条件后，才可能成为后续库存判断的新供给基准。配置生效结果与以下事项分开：

- 建议已提出但未决定；
- 申请已提交但未生效；
- 配置已改变但实物尚未补足；
- 实物已补足但尚未改变配置。

因此，配置变化和实物变化可能不同步，必须在宏观上保留两条关系。

## 4. 结果归属的初步划分

| 节点 | 结果性质 | 候选形成方 | 当前判断 |
|---|---|---|---|
| 销售统计 | 已发生业务的统计输入 | 外部输入来源（拥有者待登记） | 库存读取，不直接改配置 |
| 智能判断 | 对供给是否需要调整的解释 | 公司库存业务候选 | 先作为判断过程，不直接生效 |
| 配置建议 | 建议改变供给基准的候选结果 | 公司库存业务或管理方候选 | 待确认正式归属 |
| 业务员申请 | 管理请求 | 业务员 | 是发起动作，不是配置结果 |
| 总库管理方决定 | 管理决定 | 公司管理方候选 | 待确认生效条件与责任 |
| 配置变更生效 | 新供给基准 | 公司管理方／库存业务候选 | 可能是正式结果，需确认生效时点 |
| 实物补足 | 现实实物关系变化 | 库存履约方候选 | 不与配置变更自动合并 |

## 5. 这条链暴露的宏观边界

1. **统计不等于需求**：销售统计可以作为供给判断依据，但不能直接证明未来需求或配置必然改变。
2. **建议不等于决定**：智能推荐和业务员申请都不能自动改变个人库存配置。
3. **配置不等于实物**：配置已改变时，现实实物可能尚未补足；实物增加时，也不代表配置已经改变。
4. **配置结果不等于履约结果**：总库是否有物、是否调拨、是否采购或外借，是后续履约问题，不在本链路中提前合并。
5. **外部输入来源不等于相邻业务**：只有当销售统计的拥有者、业务含义和责任边界被正式登记后，才能判断它是否属于相邻业务；在此之前只称为外部输入来源。库存侧如何解释、谁作出管理决定，属于公司库存宏观逻辑需要继续确认的部分。

## 6. 与前面三层关系的连接

```text
销售统计（外部输入，拥有者待登记）
    ↓
供给配置判断（配置层）
    ↓
配置建议／申请／决定（管理事件）
    ↓
配置生效（正式结果候选）
    ↓
与现实实物和可用性比较（数量与事件阶段）
```

这条链说明了为什么配置和实物必须分层，也说明最低库存不能脱离配置、现实实物和可用性单独定义。
