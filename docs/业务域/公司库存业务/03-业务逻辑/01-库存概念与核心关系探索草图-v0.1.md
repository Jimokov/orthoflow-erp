## 1. 本轮目标

回答“公司库存业务究竟管理什么关系”，避免把库存简化为一个数量字段。当前只建立分析骨架，不确认任何内部规则、计算、流程、权限、页面或端能力。

## 2. 当前正式事实与边界

- T4 是跨端的公司库存业务宏观逻辑任务；T2 是业务员移动端 APP 子任务，库存 Web 后台尚未启动。
- 已接收的手术通知实物先形成来源订单的在手待结余责任，不自动成为业务员侧常备物资。
- 手术植入实物销售的来源追溯至少涉及产品、批号／可追溯身份（如有）与数量；现有植入结果、取消／失效和冲正边界只确认通知责任回写。
- 上述内容是 T4 可核验的外部约束，不等于公司库存内部对象或规则。

## 3. 宏观关系骨架（探索性）

本计划提供的七个分析坐标暂作为关系骨架：

```text
配置／期望供给
        │ 约束、覆盖或比较
        ▼
实物 ──保管／所在──> 位置与保管形态
  │                    │
  ├─追溯身份───────────┘
  │ 产品、批号／身份、数量、时间
  │
  ├─可用性（针对某业务需要与时点的判断）
  │
  └─责任（对实物或业务结果的承担关系）
          ▲
          │ 被事件／动作改变或确认
业务事件／动作 ─────────> 正式结果 ──> 可被相邻任务承接
```

这不是系统对象图。图中“位置、保管形态、业务需要与时点”是为了说明关系所需的语境候选，是否成为独立对象仍待确认。

## 4. 暂定管理对象层次（探索性）

| 层次 | 本轮要表达的关系 | 当前不能确认的部分 |
|---|---|---|
| 配置 | 公司希望哪些物资在什么业务范围内可被准备或常备 | 配置主体、依据、覆盖范围、生效方式 |
| 实物 | 现实中实际存在的物资及其所在、保管和持有关系 | 是否按单件、批次、包装或其他粒度管理 |
| 可用性 | 某实物或一组实物能否满足特定业务需要 | 判定条件、时效、质量／放行与数量规则 |
| 责任 | 哪一方对实物、持有过程或业务结果承担责任 | 责任随保管、用途、订单还是事件变化 |
| 动作／事件 | 接收、配置、发出、使用、归还、转入、异常等发生的业务变化 | 事件边界、触发人、合法性、撤销与补正 |
| 正式结果 | 一次动作完成后，供其他业务承接的可引用结论 | 结果清单、确认主体、生效时点、回写边界 |
| 追溯 | 产品、批号／可追溯身份、数量与时间的对应关系 | 追溯粒度、拆分、合并、纠正和保存责任 |

## 5. 本轮待确认的宏观取舍

以下问题会改变公司库存业务的核心对象或正式结果，不能用端设计代替：

1. **管理主体**：公司库存管理的第一主体，是“公司要准备的供给配置”、现实实物，还是二者之间的关系？本草图暂建议把二者分层，而不是互相替代。
2. **可用性语境**：可用性是否必须针对具体业务需要和时点判断，而不是实物一旦存在就等于可用？本草图暂按“关系性判断”保留，不形成算法。
3. **责任分层**：实物持有责任、业务用途责任和业务结果责任是否需要分开记录？若合并，哪些事件会导致责任转移仍无法解释。
4. **事件与结果**：接收、使用、归还、转入和异常等动作，是否都必须形成独立的正式结果，还是只有会影响相邻业务的结果才正式化？
5. **追溯地位**：追溯是所有实物关系的基础约束，还是仅在销售／植入等特定业务中触发？当前只能继承已确认的销售来源追溯粒度，不能外推到全部库存场景。

## 7. 用户确认的阶段性概念结论（2026-08-31）

- “供给配置”和“现实实物”分层：前者表达公司希望准备什么，后者表达实际存在什么、在哪里以及由谁保管；二者不得用一个库存数字互相替代。
- “可用性”按具体业务需要和时点判断，不把实物存在数量直接等同于当前可满足数量。
- 宏观上区分实物持有责任、业务用途责任和业务结果责任；这表示责任关系需要可区分，不表示已经确定三个岗位、权限或系统字段。

以上为用户确认的概念层结论；具体对象、责任主体、事件、正式结果和计算／操作规则仍待后续论证。

## 8. 用户确认的后续探索基线（2026-09-01）

- 同一实物先后服务多个业务时，暂以“稳定实物身份＋连续业务服务关系”保持责任与追溯连续；这只是探索基线，不确认独立系统对象。
- 归还、异常等事件是否进入正式结果候选，按其是否形成稳定结论、被其他业务承接、改变责任或需要追溯判断；不把所有过程事件或数量变化都正式化。
- 责任变化继续从发起者、成立依据、生效时点和承担者四个维度分析；不预设统一的“事件发生即生效”或“必须公司确认后生效”规则。

以上为用户确认的阶段性探索基线，仍需在后续场景中验证具体结果归属、责任主体、生效条件和数量连续性。

## 9. 用户确认的库存层级与机制作用域基线（2026-09-02）

- 公司库存按两级结构理解：一级为公司管理并实际持有、管理进出的公司库存；二级为以医院为绑定边界的统一二级库存，一家医院原则上只设一个。
- 同一家医院可以由一个或多个业务员服务；业务员与二级库存的绑定由公司后台管理，不预设一对一关系。业务员日常面向自己关联的二级库存，但手术通知面向公司全域库存提出要货需求。
- 最低库存机制服务二级库存；一级还需要覆盖全公司进出业务的动态联动机制，当前仅作描述性概念，不确认正式名称、规则或算法。
- 公司库存是向外开放的二层供给体系：一级公司总库存承接公司实物与外部资源关系；医院二级库存同时是公司库存第二层和面向医院的供给、交付关系层，不能拆成内外二选一。
- 实物服务医院二级库存后，对外来源、归还或结算责任仍保留在公司一级；医院二级和业务员不替代该责任。
- 医院二级库存至少区分供给配置、实物供给／交付和具体手术用途三层关系；三层相互关联但不互相替代。
- 一级公司配置服务公司整体供给，医院二级配置服务单家医院供给准备；二者联动但不互相替代，一级不等同于二级配置的机械相加。
- 可用性分为医院二级当前可用和公司整体按时可履约；两者不互相替代，当前不定义来源选择、时间算法或履约动作。
- 公司供货承诺不等于具体实物绑定；未选定具体实物时不自动产生绑定或占用。
- 公司库存形成供货承诺，手术通知形成需求并承接该正式供给结果；具体实物绑定仍由后续有效业务流建立。
- 实际业务结果由实际发生业务形成，公司库存读取正式结果并改变自身实物关系；总库自身直接改变实物关系的管理行为可形成库存结果。
- 每次实物关系变化保留前一关系、新关系与触发变化的有效业务流；稳定实物身份及公司一级对外来源责任始终不断链。

以上为用户确认的宏观结构基线；业务员的持有、服务和管理责任仍需在后续场景中分别验证。

## 10. 具体手术的预留、占用与登记关系（待论证）

用户确认：医院二级库存需要考虑实物面向具体计划手术的预留、占用与登记关系；并确认以“稳定实物身份＋业务流触发的绑定关系”作为统一表达。

预留、占用和登记不是三种固定关系或必经顺序，而是绑定关系可能产生的不同作用：可追溯登记、优先供给准备和对其他业务可用性的限制。该关系在实际植入前即可能影响可用性与后续责任，但当前尚未确认：具体建立、解除与责任效果；是否影响其他手术的可用性；以及与手术通知、实物交付和实际植入结果的边界。

已确认：有效业务绑定一旦成立，即建立实物面向相应业务的用途责任；但不自动改变持有责任、对其他业务的可用性或业务结果责任。

已确认：手术通知只形成需求，不直接占用具体实物；只有有效业务流明确锁定具体实物给具体手术时，绑定才产生占用作用，限制其服务其他业务的可用性。

已确认：占用关系的任何变化必须由可追溯的有效业务流完成；变化可表现为使用、解除、替换或后续机制中的其他关系转换。公司总库自动或人工管理行为可以发起变化，但不单独构成变化结果。

绑定关系的集中管理形态保留为桩子。本节不形成预留算法、锁定规则、页面或操作流程。
