# 公司库存业务：概念关系单场景推演 v0.1

> 状态：探索稿，待用户审核；不是库存操作规则、计算规则、页面或接口。  
> 所属任务：T4 公司库存业务宏观逻辑规划。  
> 形成日期：2026-08-31。

## 1. 推演目的

把已确认的概念放入一个完整情景，检验公司库存业务是否必须同时区分配置、实物、可用性、责任、动作、正式结果与追溯。

以下数字与名称只是说明关系的假设，不是公司库存事实或计算规则。

## 2. 情景设定（探索性）

公司希望某类手术在指定时间具备产品 X。现实中存在若干产品 X，分布在不同地点或保管关系中；其中一部分已经用于其他业务、一部分不满足当前条件，另有一部分可以在本次需求的时间窗口内使用。

本情景只验证关系，不规定公司实际采用的仓库、来源、审批或履约方式。

## 3. 沿七个层次推演

### 3.1 配置：公司希望准备什么

公司对产品 X 的期望供给，表达的是“哪些业务范围应当具备什么物资”，而不是宣称现实中已经拥有对应数量。

**得到的关系**：配置是供给意图／基准，与现实实物进行比较。

### 3.2 实物：现实中有什么

实际存在的产品 X 需要能被识别，并知道其所在、保管关系及数量。若涉及销售或植入，至少沿用产品、批号／可追溯身份（如有）与数量的追溯粒度。

**得到的关系**：实物是现实对象，不等于配置，也不因被记录就自动可用。

### 3.3 可用性：当前能否满足这项需要

针对本次具体业务和时间窗口，判断哪些实物真正能够满足需求。物资即使存在，也可能因地点、已被其他业务占用、规格不符或状态未确认而不能满足当前需要。

**得到的关系**：可用性是“实物 × 业务需要 × 时间语境”的判断，不是实物的永久属性，也不是简单的总量。

### 3.4 责任：同一物资上可能存在不同责任

- 实物持有责任：谁负责当前保管、清点和避免遗失；
- 业务用途责任：谁负责这件物资被安排服务于哪项业务；
- 业务结果责任：谁负责确认最终使用、未使用归还或异常等结果。

**得到的关系**：责任不是一个笼统的“库存归谁”，而是随持有、用途和结果分别观察的关系；同一主体可以同时承担多种责任，也可能发生分离。

### 3.5 动作／事件：什么使关系发生变化

本情景至少需要观察：配置形成或调整、实物被接收或放置、需求提出、可用性被判断、物资被用于业务、未使用物资被归还，以及异常被确认。

**得到的关系**：动作／事件是关系变化的原因，不能用“数量变了”代替事件本身。

### 3.6 正式结果：哪些结论可以被后续业务使用

本情景可能产生不同类型的正式结果：

- 当前供给不足的需求缺口，需要由相邻业务承接；
- 已接收的临时实物仍属于来源订单的在手待结余责任；
- 某件实物已经实际使用，形成可追溯的业务结果；
- 某件实物未使用并完成归还，或进入待确认异常。

这些结果的具体清单、确认主体和生效时点仍未确认；本节只说明“结果不能被配置或数量字段替代”。

### 3.7 追溯：结果如何回到具体实物

当实物被使用或发生需要纠正的结果时，必须能把业务结果关联回产品、批号／可追溯身份（如有）、数量和时间；否则只能知道“用了一个数量”，无法确认是哪批实物和哪个结果。

**得到的关系**：追溯连接实物、事件与正式结果；当前仅继承已确认的销售来源追溯边界，不外推全部库存场景。

## 4. 本情景暴露的核心对象候选

| 候选 | 为什么需要 | 当前身份 |
|---|---|---|
| 供给配置／基准 | 解释公司希望准备什么 | 概念候选，待确认是否独立管理 |
| 现实实物 | 解释实际存在什么及其追溯 | 概念候选，待确认管理粒度 |
| 业务需要 | 使可用性有判断语境 | 关系语境候选，未确认是否由库存域拥有 |
| 可用性判断 | 区分存在与当前可满足 | 概念候选，未形成计算规则 |
| 责任关系 | 区分持有、用途和结果责任 | 概念候选，未确认主体与转移条件 |
| 业务事件 | 解释关系何时改变 | 概念候选，未形成操作流程 |
| 正式结果 | 供其他业务承接或追溯 | 概念候选，未确认结果清单 |
| 追溯关系 | 把实物、事件、结果连回去 | 已有部分外部约束，整体范围待确认 |

## 5. 当前暂定判断

公司库存业务的核心不是维护一个“库存数量”，而是维护：

> 公司希望准备什么（配置）—现实中有什么（实物）—当前能否满足什么需要（可用性）—谁对哪一层负责（责任）—发生了什么变化（事件）—形成什么可承接结论（正式结果）—如何回到具体实物（追溯）。

这是阶段一的概念判断，不是对具体业务流程或系统实现的确认。

## 6. 后续需要验证的宏观问题

1. 已确认“业务需要”作为可用性判断语境；继续验证不同需求输入如何被库存读取，不扩展为库存域需求生命周期。
2. 已确认正式结果按业务承接、责任变化和追溯后果筛选；继续列出具体场景中的结果候选及其形成方。
3. 已确认责任关系需随事件分析；继续验证不同事件的发起者、依据、生效时点和承担者。

## 7. 用户确认的阶段性概念结论（2026-08-31）

- “业务需要”作为可用性判断所需的关系语境；库存业务可以使用需求信息判断能否满足，但不因此自动拥有需求的创建、修改、取消或完整生命周期。
- 正式结果是事件形成的稳定业务结论，优先保留会被其他业务承接、会改变责任或需要追溯的结果；不把所有过程事件或数量变化都等同为正式结果。过程事件仍可保留为记录。

以上为宏观边界原则；需求输入内容、正式结果清单、确认主体和承接方向仍需继续推演。

## 8. 用户确认的单场景探索基线（2026-09-01）

- 同一实物先后服务多个业务时，暂采用“稳定实物身份＋连续业务服务关系”的探索表达，避免后续业务覆盖前一业务的责任与结果。
- 归还、异常等事件只有在形成稳定业务结论、被承接、改变责任或需要追溯时，才进入正式结果候选；过程事件仍可保留为记录。
- 责任变化不采用单一生效规则，继续从发起者、成立依据、生效时点和承担者四个维度观察。

以上为用户确认的阶段性探索基线，不确认正式对象、状态或操作规则。

## 9. 场景重跑的结构前置（2026-09-02）

后续中性场景必须带入以下已确认结构：一级公司库存实际持有并管理公司实物进出；二级库存以医院为绑定边界且一家医院原则上只有一个统一二级库存；一个或多个业务员可由公司后台绑定到该二级库存；业务员日常面向关联二级库存，但手术通知面向公司全域库存提出需求；最低库存只作为二级库存机制，一级全域动态联动机制暂不命名、不展开规则。

本节只规定场景的宏观语境，不确认绑定字段、页面、算法、履约路径或责任结果。
