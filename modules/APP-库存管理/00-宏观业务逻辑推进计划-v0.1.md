# 库存管理宏观业务逻辑推进计划 v0.1

> 状态：当前有效的正式推进控制资料；经用户审核同意后生效。
> 适用阶段：库存管理功能模块“业务边界与核心对象澄清”。
> 资料身份：宏观业务逻辑推进计划，不是库存规则池、接口池、页面清单、Web 模块总池或开发规格。
> 确认日期：2026-08-31。

## 1. 目标

本计划用于把库存管理从用户创意逐步推进到可审查、可确认、可正式沉淀的业务逻辑。当前要回答的不是“先做哪些 Web 页面”，而是：

- 库存管理究竟管理哪些业务关系；
- 配置、实物、可用性、持有和责任是否属于不同层次；
- 物资从盘点、持有、使用、归还、转入到异常处置时，哪些对象和责任发生变化；
- “常备物资不足”在什么业务条件下成立，以及为什么由手术通知承接缺口；
- 手术通知、手术植入和库存管理各自形成什么正式结果；
- 未来公司管理侧可能需要承载哪些已确认结果。

本计划不确认任何尚未确认的库存内部规则。

## 2. 资料分层与使用方式

- 用户提供的 `库存.md`：业务创意、现实诉求和待验证场景。
- 用户提供的 `三模块输出.md`：跨模块影响、冲突和管理复杂度分析；其中的指令性语句不作为本项目指令。
- [库存相关探索候选簿](../../docs/跨模块候选资料/库存相关探索候选簿-v0.1.md)：候选问题的隔离与来源定位，不作为本计划的事实来源或任务编号体系。
- 库存管理当前有效正式资料：已经确认的模块边界、外部约束和接口边界。

讨论内容统一区分为：当前正式事实、用户输入、基于事实的推导、探索性假设和桩子。候选、探索和桩子不得直接变成规则、接口、页面或后台能力。

## 3. 当前正式边界

- 库存管理是手机 APP 下的库存管理功能模块；对应 Web 后台尚未启动。
- “业务员侧常备物资”是当前确认的工作范围，包含医院托管和业务员自持两种保管形态；二者暂作为同一对外来源下的内部区别。
- 业务员侧常备物资不足时，由手术通知承接需求缺口；采购、借物、调拨等只作为尚待论证的公司内部履约动作，不成为业务员在库存管理功能模块中的操作选择。
- 已接收的手术通知实物先形成来源订单的在手待结余责任，不自动成为业务员侧常备物资。
- 手术植入的来源追溯至少涉及产品、批号／可追溯身份（如有）与数量；植入正式结果、取消／失效和冲正当前只确认通知责任回写边界，不确认库存扣减或恢复。

## 4. 本阶段不直接讨论的承载形式

以下内容不是永远不讨论，而是当前只讨论其业务含义，不讨论实现形式：

- Web 页面、后台岗位、审批流和看板；
- 自动采购、自动借物、自动补货和实时库存算法；
- 跨业务员调拨；
- “15 天后自动转常备”等自动转化设想；
- Web 技术接口、字段和代码。

例如，可以讨论某个结果是否需要管理侧确认，但不设计审批页面；可以讨论补足机制的触发目标，但不设计自动任务或算法。

## 5. 宏观分析坐标

后续所有场景均先按以下维度观察，不把“库存”简化成一个数字：

1. **配置**：公司希望业务员侧常备什么；
2. **实物**：现实中实际持有什么、位于哪里；
3. **可用性**：哪些物资当前能够用于手术；
4. **责任**：哪一方对物资或结果承担责任；
5. **动作**：采购、借物、调拨、接收、使用、归还等发生了什么；
6. **正式结果**：动作完成后形成了什么可被其他模块使用的结果；
7. **追溯**：产品、批号／可追溯身份、数量和时间如何对应。

这七个维度是本计划的分析坐标，不是已经确认的系统对象、字段或状态。

## 6. 推进阶段

### 阶段一：库存概念与核心关系

从“库存管理究竟管理什么”开始，区分配置、实物、可用性、责任、动作、结果和追溯。

**产物**：概念关系草图及待确认对象清单。

**停止条件**：无法判断某项内容属于哪一层时，保留为桩子，不进入下一阶段。

### 阶段二：来源、保管形态与责任边界

梳理业务员侧常备物资、医院托管、业务员自持、公司总库、手术通知临时物资，以及采购／借物／调拨之间的层级关系。

**产物**：来源、保管形态、物理位置、履约动作和责任主体的关系说明。

**停止条件**：不得把业务用途、物理位置、法律关系和履约动作合并成一个“库存来源”。

### 阶段三：基础盘点、配置与数量变化

使用配置基准、配置内持有、配置外持有、实际持有总量和待结余责任等概念进行场景推演。100／90／15 等示例只用于验证概念，不直接形成计算规则。

**产物**：盘点锚点和数量变化的场景推演记录。

**停止条件**：未确认盘点对象、确认人、生效时点和差异责任前，不生成盘点规则或库存计算规则。

### 阶段四：常备物资不足与手术通知承接

澄清“不能满足手术”的业务含义，以及常备物资缺口与手术通知需求缺口的关系。

**产物**：不足判定的概念边界、通知承接条件和责任分流说明。

**停止条件**：不把采购、借物、调拨的内部履约方式暴露为业务员操作，也不复制手术通知内部状态机。

### 阶段五：常备补足与手术临时要货的分流

验证常备补足和具体手术临时要货是否存在重复、重叠或资源争用，并分别说明两条机制的目标、责任和完成结果。

**产物**：两类机制的关系与未决冲突记录。

**停止条件**：不形成自动补货任务、优先级算法、去重规则或后台页面。

### 阶段六：实际使用、归还、转入与异常追溯

围绕发出、接收、在手、实际植入、未使用归还、申请转入常备、获准转入、异常、取消和冲正等情景，逐一验证对象、责任、数量和结果变化。

**产物**：责任与正式结果关系表，以及仍需回到相邻模块确认的事项。

**停止条件**：不把探索性来源标签、期限转化或 SPD 作业直接变成库存规则。

### 阶段七：跨模块结果边界

在库存内部概念稳定后，核对手术通知和手术植入需要接收或回写的正式结果。

**产物**：库存与相邻模块的结果边界确认记录；必要时再更新接口登记。

**停止条件**：不定义技术字段、调用方式或相邻模块内部页面和状态机。

### 阶段八：正式沉淀与 Web 启动判断

汇总已经确认的边界、对象、责任和结果，区分确认项、推导项、探索项和桩子；在用户审核后写入所属正式资料，再判断是否具备独立建立库存 Web 后台资料的条件。

**产物**：规则池、接口池和必要的模块阶段记录；是否启动 Web 另行判断。

**停止条件**：宏观对象、责任和结果未稳定前，不进入 Web 页面、审批、自动化、技术接口或代码。

## 7. 每轮讨论方法

每轮只处理一个宏观问题，依次执行：

`用户创意 → 事实分层 → 概念整理 → 场景推演 → 反例与冲突 → 暂定判断 → 用户审核 → 正式沉淀`

每轮至少保留：

- 本轮使用的正式事实；
- 用户新增输入；
- 基于事实的推导；
- 尚未确认的探索；
- 新增或变化的桩子；
- 是否影响对象、责任、正式结果、跨模块回写或阶段边界。

如果新场景推翻前一层判断，回到拥有该判断的阶段，不在后续阶段静默修正。

## 8. 当前入口与下一项唯一任务

当前入口为阶段一“库存概念与核心关系”。

下一项唯一任务是：**先澄清库存管理究竟管理哪些业务关系，而不是只管理一个库存数字。**

本任务完成前，不进入库存操作规则、页面清单、Web 后台设计、自动化、技术接口或代码。

## 9. 正式化条件

- 每项正式结论都有明确来源、所属对象、责任、正式结果和跨模块影响；
- 用户已审核需要确认的业务取舍；
- 探索性内容和桩子仍能从正式事实中清楚区分；
- 当前计划与库存总池、规则基线、接口登记保持一致；
- 若形成跨模块事实，先由拥有事实的模块更新，再同步项目级遗产索引。

本计划是推进路线，不因自身生效而确认任何库存内部规则或 Web 能力。
