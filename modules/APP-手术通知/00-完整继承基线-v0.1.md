## 2. 模块定位、角色与术语

### 2.1 模块定位与明确边界

**当前事实：**“手术通知”是业务员围绕一台计划手术，向公司提出产品与器械缺口需求，并承接后续订单协同、实际接收、手术结果衔接和本单物品责任闭环的 APP 模块。它不是医院排程通知，也不是业务员向厂家采购。

业务员负责提出需求、查看对本人有影响的结果、完成本人确认／回复／申请／接收／实物去向动作；公司负责内部采购、借调、仓储、配货、发货、审批、公司收货和最终完成。APP 不展示公司内部来源、仓库或作业路径，也不允许业务员选择内部履约方式、改写订单主状态、直接完成订单或跨业务员交接责任。

患者、住院号和完整实际植入事实属于手术植入；个人仓审批与库存计算属于库存；器械处理、清洁、灭菌及再次放行尚未形成独立模块；Web 后台内部页面和岗位尚未启动。

### 2.2 角色与权限

- APP 一人一机，所有正式动作绑定当前业务员；严禁查看、代办、转交或确认其他业务员对象。
- 后台可为业务员代建全新原单，也可在已有订单下代建补充单；后台创建人不成为共同所有人，不能在 APP 冒充业务员确认。
- 全新代建原单的确认只作用于该原单；代建补充单确认只作用于该补充单，不能覆盖同一手术需求组其他单据。
- 业务员只能提请、回复、确认本人实际行为、提出正式申请及查看结果；系统和后台不得绕过数量守恒和未闭环责任强制完成。
- 并发采用“先成功的正式动作生效”：旧版本动作被阻止，刷新当前事实并保留历史记录。

### 2.3 术语基线

以下术语继承根 `CONTEXT.md` 与当前规则：

| 术语 | 当前含义 |
|---|---|
| 手术需求组 | 一台计划手术的稳定聚合对象；由原始手术通知及其全部接续订单组成 |
| 主订单／接续订单 | 首次提交形成主订单；受理后新增需求形成独立编号的接续订单，二者均保留真实履约与审计 |
| 订单内容 | O01按主订单及接续订单展示需求与正式版本，不用“需求与变更”作为固定页面入口 |
| 发货与接收 | 面向业务员展示供货、正式出货批次、出货清单／照片、实际交付及本人确认接收；不称“履约与交付” |
| 实际交付批次 | 一次真实寄送或线下交接，可关联本人多张订单，但订单、实物和责任分别保留 |
| 待结余／本单物品结余 | 待结余是订单主状态；本单物品结余是已接收实物逐项落实最终去向的过程 |
| 在手待结余 | 已确认接收、尚未植入、已还回、已入库、已转用或已获批准异常处置的本人实物责任 |
| 订单记录 | O04 的正式历史，不再称“业务记录” |
| 待我处理 | 从底层事实派生的本人任务集合，不是订单主状态或完成条件 |

## 3. 对象、关系与正式结果

### 3.1 核心对象关系

```text
计划手术
  └─ 手术需求组
      ├─ 主订单（首次提交）
      ├─ 接续订单（受理后补充；各自编号与结果）
      ├─ 正式发货批次 → 实际交付批次 → 本人接收事实
      ├─ 手术植入记录（相邻模块，仅带入适用实物）
      ├─ 本单物品去向／还回批次
      └─ O04订单记录（同一需求组的正式历史）
```

订单中心的一条目录记录对应一个手术需求组，不把补充单平铺为独立卡片；O01与O04均一一对应同一手术需求组。复制需求新建会产生新的需求组、O01和O04，不与来源订单合并。

### 3.2 需求与交付对象

- 手术信息必填：医院、科室、术者、计划手术日期和准确时间。交付地点不是手术医院；只有交接安排影响业务员时才要求其处理。
- 产品需求必须到品牌／厂家、系列、型号或规格、数量和单位；不选择批号、序列号、仓库或来源。多规格备货不以最终植入量倒推。
- 产品与器械需求独立。推荐器械包须由业务员明确采用；采用后形成可单独编辑／移除的器械需求组。额外器械、手动器械和非目录器械均可独立或关联产品组。
- 非目录产品／器械是独立需求行，至少记录类型、名称或用途、数量、单位，可附厂家、规格、说明、图片或资料；后台映射后不得覆盖原始描述，映射结果由业务员确认。
- 公司正式发货批次冻结结构化出货清单和至少一张整批实物照片；错误通过作废、补发或更正处理，不覆盖原清单。
- 本人接收、物流／线下签收、后台发货是三个不同事实。业务员正常确认接收后，对相应正式清单承担实物责任。

### 3.3 物品去向与数量守恒

已接收实物可分别形成：实际植入、经批准转入个人仓（前台显示“已入库”）、经批准转入本人另一明确订单（“已转用”）、还回公司、经批准异常处置，或继续在手待结余。不同数量和不同实物身份可并行处于不同结果，不可按整单简单归为植入或还回。

```text
实际接收数量
= 实际植入数量
+ 公司确认还回数量
+ 批准转个人仓数量
+ 批准转入本人其他订单数量
+ 批准异常处置数量
+ 在手待结余数量
```

在手待结余不为零、还回未形成正式结果或异常未闭环时，不具备完成资格。

## 4. 从创建到终局的完整主线

### 4.1 创建域：C00—C11

C组是一套共用需求编辑系统，不是线性向导。其五种来源最终都汇入 `C02 → C03（按需）→ C09`：

| 来源 | 入口与处理 | 正式结果 |
|---|---|---|
| 空白新建 | G01→C00→C02；填写本次手术信息与需求 | C09提交形成新主订单并进入新O01 |
| 从模板创建 | C00→C11选择共享／已下载模板→C02核对本次信息 | 新主订单；模板只提供需求基座 |
| 复制需求新建 | 当前或历史O01 | 带入最后有效需求快照，必须重填新手术日期和准确时间；形成另一台手术的新订单 |
| 待受理撤回修改 | 来源O01 | 保留原订单／补充单编号和首次提交关系；重提后仍回同一O01，仅产生新提交版本 |
| 已受理订单补充 | 来源O01 | 继承手术场景，只新增需求或有效的本次补充要求；提交后形成独立接续订单并回原O01 |

**草稿规则：**仅打开空白 C02 不形成草稿。首次实际输入且本机持久保存成功才形成可见草稿；模板、复制、补充和撤回修改带入有效内容后也以首次成功本机保存为形成点。本机保存与公司同步分开判断，离线可继续编辑但正式提交须联网。C00只显示最近一张当前可继续草稿；C10管理全部草稿，按“可继续／无法继续”两层、最后本机保存时间倒序组织。普通未提交草稿可删除；撤回修改稿只能继续修改或在最新事实与权限允许时正式取消，不能用删除掩盖正式身份。

**模板规则：**C11首先服务“选择模板创建本次需求”，其次低频管理“我的模板申请”。公司共享模板和已下载模板都只用“使用模板”进入同一创建链；下载只是账号绑定可用副本，不是私人模板。业务员可加一条账号私有的个人备注（可搜索、不能记患者信息），不改变模板、不进入订单、额外要求或候选。模板候选可从C11主动创建、基于模板调整，或在新主订单首次提交成功后一次性低强调创建；候选不进C00/C10、不填具体手术时间、在C02模板态直接提交公司审核、不经C09。审核中的候选只读；退回可重提或正式放弃。模板审核、额度／付费权益和后台治理均为桩子。

**C02／C03／C09边界：**C02是统一编辑中枢，承载手术信息、需求摘要与添加产品／器械基座；C03是产品与器械需求组编辑，含推荐器械和非目录需求；C09是只读全量核对与唯一正式提交边界，只能直接编辑整单额外要求／本次补充要求。补充没有新增产品或器械时，本次补充要求必填，不能形成空接续订单；正式变更、取消和普通协同不能借补充代替。

复制／模板带入的医院、科室、术者失效时保留来源原文并要求重新匹配；仍无适用项可标记“请公司确认”进入C09，且必须明示未匹配。空白新建不开放任意填写。产品、规格、器械包等最终摘要粒度等待组配方案，是当前阻塞最终低保真的桩子。

### 4.2 订单状态与受理—发货阶段

主状态仅有八种：

```text
待受理 → 处理中 → 待发货 → 已发货 → 待结余 → 已完成
                            └→ 发起追回 → 按当前有效事实重算
已取消：无遗留实物流的独立终局
```

| 主状态 | 形成条件与前台边界 |
|---|---|
| 待受理 | 已提交、公司尚未受理；本人提交的原单可“修改订单（撤回）／取消订单”，本人补充单只可改／取消该补充单 |
| 处理中 | 公司仍在解决有效需求；可按权限补充需求、发起变更取消 |
| 待发货 | 当前履约方案已形成，尚无有效正式发货批次；可按权限补充需求、变更取消 |
| 已发货 | 已有至少一个有效正式发货批次，即使仍有待发内容；部分发货不另立主状态，O01分别表达已发和待发 |
| 发起追回 | 公司已对一个或多个已发批次正式发起追回且尚未闭环；不是业务员按钮或任务。成功／失败／撤销后按有效实物流重算 |
| 待结余 | 已有有效植入结果，或取消生效且已接收物品仍有去向／审批／还回／异常责任未闭环 |
| 已完成 | 需求、交付、手术结果和实物责任均闭环，系统判定资格后由后台最终确认 |
| 已取消 | 整个需求组取消已生效且没有有效发货、接收、追回、异常、还回或其他未闭环责任 |

公司代建版本待本人确认时，O01顶部同一任务提供“确认订单／确认补充单”或“提出异议”；不显示业务员修改或取消按钮。受理后，新增需求必须作为接续订单，不覆盖主订单。

### 4.3 任务、协同、接收与变更

任务是唯一全局任务源的派生层，回答“本人现在是否必须行动”。G01只摘要和必要强提醒，G03是完整集合，O01只引用当前订单同一任务，真实动作回原页面；任务完成、失效或替代后所有入口同步退出。普通等待公司、运输、审批、清点、系统校验和后台普通消息均不是任务。

| 任务／动作 | 触发与承载 | 完成／退出 |
|---|---|---|
| 代建原单／补充单确认 | O01动态任务 | 本人确认／异议被接受，或版本撤销／替代 |
| T01订单协同 | 公司正式要求本人补充、沟通或作出必要决定 | 回复／结构化决定被接受后如只等待公司即退出；结束、撤回或替代后只读 |
| T02实际交付确认 | 真实交付批次已送达／线下交接且本人未确认 | 正常明细确认、异常明细完成申报且无未表态明细 |
| T03收货异常 | 只能从T02当前异常明细进入 | 提交或取消返回T02；后续公司处理不继续占据T02任务 |
| 手术情况确认 | 有效计划手术时间已过，且无植入／已生效延期／取消结果 | 进入植入形成有效结果，或延期／取消申请提交后等待公司 |
| T05变更取消 | O01主动“变更取消”，或手术情况任务指定延期／取消 | 仅提交申请；只等待公司时退出，退回时按新事实重启任务 |
| 处理本单物品结余 | 待结余且仍有本人需选择去向的实物 | 合法去向提交后等待公司／第三方时退出 |
| 执行借单还回／处理还回问题 | 公司受理后要求本人执行，或公司发现需要本人处理的问题 | 动作被接受，回到还回中或形成正式结果 |

**T01：**同一手术需求组共用一张订单协同页，但不同事项有独立任务、版本和状态，页面一次只展开一项。前台只回答“哪台手术、公司要我做什么、我能怎么处理”。业务员不能无事项新开聊天；文字、图片和附件只是沟通，结构化决定才改变订单事实；不同意不自动取消或变更订单。等待公司时仅可补充遗漏资料，事项结束后从O04只读。

**T02/T03：**一次真实交付批次一条T02任务，可关联本人多张订单。全部相符时一次确认；有异常时，先由T03申报异常明细、可追加同批同一问题明细，再确认其余正常物品。未收到部分不形成在手责任；到手异常部分形成临时在手责任并冻结；混合情况按数量拆分。接收后的在手异常回O01组件，还回清点差异回S01，三者不混同。

**T05：**同一现实事件的相关变更可合并且分别回写前后内容；“取消整单”必须单独提交。延期可填新日期与准确时间，或提交“时间待定”；生效后旧时间失效，延期期间订单与已接收实物仍绑原手术。

### 4.4 手术植入与待结余

计划时间到达不等于手术完成。计划时间前O01可低强调进入手术植入；时间过后无结果才升级为任务。手术植入只带入已实际接收且仍绑定本订单的候选实物，默认不全选，业务员选择实际植入的具体产品、可追溯身份和数量。植入模块可另用合法自有库来源，手术通知只依据通知来源分配重算本订单剩余责任。

手术已实施并有有效植入结果，或取消已生效且存在已接收实物责任时，O01汇总本单物品结果。顶层面向业务员使用“等待手术结果、已植入、已入库、已转用、异常处理中、需要还回／还回中／已还回”；每条原交付明细在自身位置叠加结果及数量，不重新造第二套清单。

待结余阶段不固定提供补充或变更取消；只允许处理本人已接收实物的合法去向。入库、转用、在手异常由O01轻量组件承载；借单还回进入S01。申请提交后仅等待公司时退出待办，不自动解除责任。

### 4.5 S01借单还回与终局

S01不是第二张订单详情，而是一次还回批次的办理页。只有已形成植入结果或取消生效、已接收实物仍在手待结余、且未被其他有效去向占用时，O01可选择待还实物进入S01。进入S01不产生批次；正式提交才形成还回批次。

- 一张订单可分批还回；同一业务员多张订单可在公司安排明确后合并一次交寄，但每个来源订单、实物身份、数量和责任分别留存并回写。
- 产品可按可还数量部分选择；器械包以整包为普通最小还回单位，独立器械可按件选择。缺件、破损、污染或不符进入异常，不能用拆包／少选掩盖。
- 前台局部进度只收束为“发起还回、公司受理、还回中”，正式结果为“已还回”。运输、公司接收与清点不拆更多 APP 状态。
- 发起且未受理时可撤回；公司受理先成功时不可撤回。撤回将尚未受理实物恢复至来源O01在手待结余，并保留发起／撤回记录。
- 公司需要本人补证、处理实物差异或重新处理时，生成同一S01上下文的“处理本次还回问题”任务；同批问题尽量合并。已清点一致实物可先解除责任，其他问题不阻塞其他来源订单。
- 还回提交照片、后台安排／执行表单、跨订单后台呈现、业务报销跳转和受理后批次调整均为桩子；不阻塞主体逻辑，阻塞相应字段或最终低保真。

订单完成资格要求：所有有效需求与补充有结果；交付已确认或接收前成功撤回；有效植入或取消结果已形成；未按期交付需求已解除本次绑定并保留记录；所有已接收实物已落实；还回已公司清点；无在手待结余、未闭环异常或未形成结果的还回；数量守恒通过。APP不提供完成按钮，后台执行最终确认。

完成或取消后历史冻结。若实质性更正重新产生需求、实物流、数量差异或本人责任，先形成“重新打开”正式记录，再重算主状态和任务；不能直接在已完成／已取消历史订单挂任务。

## 5. O01总承载、O04历史与页面集合

### 5.1 O01固定骨架

O01是订单生成后单一手术需求组的总承载页；尽量在一页总览和分流，不再设置第二张订单流向总览。连续滚动固定顺序：

1. 当前待我处理（仅有任务时，内容第一位；多任务只完整显示最高优先项和“另有N项”）；
2. 订单身份、医院／术者／手术时间、一个主状态及必要说明；
3. 订单内容：主订单在前、接续订单按发生顺序；
4. 发货与接收：整单或分批交付只出现一次，清单、照片和来源可按需展开；
5. 本单物品结果与适用的集中操作；
6. 当前可执行主动操作；
7. 页面末端“查看订单记录”。

O01不展示独立关键结果卡、最近进展、小型时间线、固定T步骤轴或后台内部流程。任务动作优先于主动操作；无任务、接续订单、交付或合法操作时对应区块整体隐藏。

O01主动操作遵循主状态：待受理本人原单可修改订单／取消订单；本人补充单只改／取消该单；处理中、待发货、已发货及底层仍允许的追回情形可补充需求／变更取消；待结余不再显示这些操作，只显示物品去向入口；已完成／已取消仅可低强调复制需求新建。代建待确认完全由顶部任务承载。

### 5.2 O04订单记录

O04与O01一一对应，回答“这张订单怎样走到现在”，不是第二张订单详情。主订单和全部接续订单共用同一O04，单条记录仍标明对象身份。它只记录导致订单事实、业务版本、本人责任或正式结果变化的事件：提交／撤回／重提／受理／版本替代、补充单、正式协同和申请、发货与接收、追回、植入与物品结果、还回、完成／取消／重新打开及实质更正。

O04不记录派生主状态、任务生命周期、提醒推送、普通沟通、物流节点、页面行为、草稿保存失败或后台内部日志。它以正式生效时间倒序时间线组织，复杂时才允许按主订单、接续订单、交付批次或事项定位；历史详情只读，不能恢复旧任务或动作。

O03已删除独立身份：普通／复杂批次的只读清单、照片和证据均由O01批次轻量下钻承载；真实接收动作仍在T02。该删除保持编号空缺，不重排其他页面。

## 6. 跨模块契约

### 6.1 给手术植入的输入与返回

手术通知向手术植入提供：当前业务员、手术需求组／订单引用、手术场景、已实际接收且仍绑定本订单的候选实物及来源上下文。手术植入不默认全选，只取本次实际需要物品；可使用其他合法来源。

植入正式结果返回：唯一植入记录引用、实际植入产品／可追溯身份／数量，以及通知来源分配。手术通知仅按通知来源分配重算剩余责任和待结余。取消、失效或销错冲正由植入侧保留原记录，并按“先反向调整原来源、再在正确结果形成后正向回写”的顺序传回；未正式形成、自动校验异常、放弃或超期退出不回写。字段、权限、时限、幂等与重试仍是技术桩子。

### 6.2 与库存、器械可用结果的边界

- 手术通知不展示任何仓库、个人仓余额或可用数量；已有并可直接销售的本人库存不重复要货。
- 已接收物品不会自动成为个人仓可用库存；申请入库只有后台批准后才生效。
- 未来库存只能继承已批准入库结果及可追溯实物责任，不能继承手术通知的要货、履约或状态机。
- 器械包公司确认还回后，本订单业务员保管责任可解除；订单完成不等待后续器械处理。器械包转入下一订单前须有公司确认的可用／放行结果；其形成能力未启动。

### 6.3 与订单中心、全局任务和Web后台

- 订单中心接收正式订单的当前／历史归属、主状态、业务更新时间和至多一条必要提示；草稿、模板、交付批次、植入记录、还回记录不成为独立订单。

### 6.4 跨模块遗产索引

本模块已经论证的植入、库存交叉事实、继承方向、桩子与来源，由项目级[跨模块遗产索引 v0.1](../../docs/跨模块候选资料/跨模块遗产索引-v0.1.md)统一定位；本文件及其细分规则／接口仍是手术通知侧事实正文。相邻模块先读索引定位直接条目，再读本节与对应接口，不复制本模块内部页面或状态机。
- G03、O01和G01始终引用同一任务ID；任务完成后只等待公司时退出待办，订单事实仍保留。
- Web后台从APP接收需求、接收确认、正式申请、异常／还回事实；向APP返回履约结果、正式版本、任务触发事实、安排和最终确认。后台岗位、界面、内部状态机、采购仓储和技术协议未定义。
- S01跨订单交寄的后台必须保留交寄批次、来源订单、实物身份和分别回写关系；这只是输入约束，不是后台页面设计。
