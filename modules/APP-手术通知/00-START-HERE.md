# 手术通知 APP 总池

> 建池日期：2026-08-10  
> 当前阶段：页面设计  
> 当前作用：这是任何新任务接管“手术通知 APP”的唯一入口。

## 1. 模块身份与边界

- 所属端：业务员移动端 APP；
- 模块核心：业务员围绕确定手术时间向公司提出产品和器械缺口需求，并承接后续订单协同、实际交付确认及本单物品结余；
- 本模块不是字面意义上的手术排程通知；
- 业务员已有并可直接用于销售的本人库存不进入本次缺口要货；
- APP 不向业务员展开公司内部采购、借用、调拨和仓库来源判断；
- 手术植入、库存及 Web 后台保持独立范围；器械包可用／放行结果只是尚未登记承接能力的外部依赖，本池只保存已经确认的衔接结果，不代替它们定义内部流程。

## 4. 当前必须继承的关键结论

- 底部全局入口是首页、订单中心、我的；
- 手术通知模块通过自己的起点页承接通用主动创建和草稿恢复，草稿不放在全局首页或订单中心；
- 订单中心只聚合正式订单，分当前订单和历史订单；
- 订单主状态使用待受理、处理中、待发货、已发货、发起追回、待结余、已完成、已取消；
- “待还回”不是订单主状态，还回是待结余下的一条物品去向分支；
- O01展示当前任务、订单身份与状态、主订单／接续订单、整单／分批交付和当前可执行操作；有任务时任务位于内容第一位；
- T01 是公司针对正式订单发起的“订单协同”，不是通用聊天；同一手术需求组共用一张T01页，多个事项独立且一次只展开一项，不同事项不混流；业务员只能围绕已有事项回复、决定或补充遗漏资料，事项结束后只读；
- T01前台始终只回答“这是哪台手术的订单、公司现在要本人做什么、本人现在可以怎么处理”；完整方案和审计留在底层，不以固定四层或固定字段堆给业务员；
- T03 只能从实际交付确认 T02 中进入；
- 手术植入只带入本次实际需要的部分物品，不默认全选；
- 植入结果先回写O01；仍有物品未落实去向时，O01展示待结余责任总览并进入适用S动作页；
- 现有低保真仍含旧状态词和旧 T 页面表达，不能作为当前规则依据。

### 5.1 O01专题推进锁

每次继续O01前，必须同时核对“当前设计进度、设计总控、状态矩阵、O01结构稿”，并遵守：

1. 已确认矩阵只作为页面结构输入，不把验收勾选项重新解释成业务访谈题；
2. 新发现的问题先判断是否阻塞O01结构成立；不阻塞的S、T、G、推送和Web问题按所属阶段暂缓；
3. 只有现行文件之间发生实质冲突时才回到规则层，并明确指出冲突文件和影响；
4. O01结构与低保真已经完成验收，O／T／S关系也已闭合；在全部页面组逻辑及模块业务闭环验收与总路线图确认前，不制作模块整体低保真总览；
5. 每次形成结论后同步本页与当前设计进度，确保始终只有一个“当前任务”。

### 5.2 组间切换硬闸门

完成任意一组页面逻辑讨论后，必须先形成组间切换筛查记录，再开启下一组。筛查覆盖全部当前有效资料、全部已知文件索引、相关接口、历史隔离、旧结论残留、跨池同步和当前唯一任务；不得搜索或读取旧任务聊天。存在阻塞冲突时停止切换，非阻塞缺口登记明确归属。筛查通过并完成资料对齐后，必须先限定本次范围完成Git提交、推送和远端验证；远程同步未成功前不得开启新组宏观审查。

### 5.3 新组开启宏观审查硬闸门

组间切换筛查通过后，必须先从整组层面审查业务目标、对象、入口出口、结果回写和跨组交集。已有候选页面时，对每页判断保留、融合、修改、删除或条件性出现；没有候选页面时，先从用户问题和业务能力决定承载方式，不从模板生成页面。宏观方案经用户确认前，不逐页讨论、不默认旧页数、不创建新页面编号。

候选页面名称和编号不是默认骨架。宏观审查必须先形成“业务能力—现有承载位置”矩阵，并对每张建议保留的独立页完成删除反证；凡是职责已经被O／T／G／C等现有页面、条件区块或共用组件接住的候选页，不能因为旧编号或旧低保真继续保留。缺少上述两项时，宏观审查不得标记完成。
