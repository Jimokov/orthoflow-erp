# O01—T任务编排规则 v0.1

> 状态：已确认，作为当前任务编排基线  
> 日期：2026-08-07  
> 范围：只定义O01与T01—T05之间的任务关系，不设计具体视觉稿，不修改现有原型。

## 1. 核心模型

O01始终是某张手术通知订单的详情入口。订单主状态回答“整张订单总体走到哪里”，T任务回答“当前是否有事情必须由业务员本人处理”，二者并行存在，互不覆盖。

```text
O01订单详情
= 订单身份
+ 订单主状态
+ 当前关键结果
+ 本人待处理任务
+ 需求、交付和业务记录入口
+ 业务员可主动发起的订单操作
```

T01—T05不是一条依次经过的流程，也不是订单主状态。

## 2. O01与T页面的直接关系

### 2.1 O01直接承载

- T01订单协同；
- T02实际交付批次确认；
- T04手术情况确认。

### 2.2 不从O01任务区直接承载

- T03收货异常申报：只能从T02核对具体交付批次时进入；
- T05变更与取消申请：由业务员从O01主动发起，或承接T04的延期和取消。

```text
O01
├─ T01 订单协同
├─ T02 实际交付确认 → T03 收货异常
├─ T04 手术情况确认 → 手术植入
│                    └→ T05 延期／取消
└─ 主动发起T05 变更／取消
```

## 3. O01任务区的展示规则

### 3.1 没有任务

完全隐藏“待我处理”区域，不显示“当前没有待办”。订单普通进度继续由主状态和关键结果表达。

### 3.2 一项任务

完整展示该任务的标题、必要影响和明确动作。按钮使用具体动作名称，不统一使用“处理当前任务”。

### 3.3 多项任务

完整展示动态计算出的最高优先级任务，并显示“另有N项待处理”。点击后进入全局任务中心，并限定为当前订单；不另建第二套订单任务列表。

## 4. 任务优先级

任务不按T编号固定排序，依次考虑：

1. 是否已经逾期；
2. 是否阻塞手术或下一步履约；
3. 风险等级；
4. 距离任务截止时间；
5. 距离计划手术时间；
6. 已等待时长；
7. 稳定任务编号。

默认情况下，已到期的T04通常高于影响手术的T01，影响手术的T01通常高于刚刚生成的普通T02；但逾期T02可以动态升高。

任务排序只决定页面展示顺序。是否推送或形成首页强提醒单独判断，避免业务员被普通进度频繁打扰。

## 5. 任务生命周期

任务底层区分：

- 待本人处理；
- 处理中；
- 等待公司或其他模块结果；
- 已完成；
- 已失效／已替代。

O01任务区只显示仍需业务员本人行动的任务。业务员已经完成动作、只等待公司处理时，任务退出“待我处理”，普通结果回到订单详情；完成、失效和替代记录进入O04，不删除历史。

### 5.1 T01

- 后台发起需要业务员补充、沟通或决定的订单协同事项时生成；
- 协同获得所需回复或正式决定后完成；
- 后台撤回事项时失效；
- 出现新版本时，旧事项保留记录，新事项取代旧事项；
- 同一事项的重复保存和推送不能产生重复任务。

### 5.2 T02

- 实际交付批次已经送达或完成线下交接、业务员尚未确认时生成；
- 正常明细完成确认、异常明细完成事实申报且不存在未表态明细时完成；
- 公司在业务员接收前成功拦截并完成公司清点时失效；
- 一次实际交付批次只生成一条T02，即使该批包含同一业务员的多张订单。

### 5.3 T04

- 当前有效计划手术时间已经过去，且没有有效植入、已生效延期或已生效取消结果时生成；
- 选择“手术已进行”后进入手术植入，只有有效植入结果正式提交后才完成；
- 提交延期或取消申请后进入等待公司处理，不继续占据待我处理；
- 申请被退回时重新激活；
- 其他入口已经形成有效植入结果时自动完成。

## 6. 入口与返回

任务页面记录进入来源和页面上下文：

| 来源 | 完成或退出后的默认返回 |
|---|---|
| O01 | 返回原O01并重新计算主状态和剩余任务 |
| G01 | 返回G01并更新任务摘要 |
| 全局任务中心 | 返回原筛选、排序和滚动位置 |
| O03进入T02 | 返回原O03交付批次位置 |
| T03 | 无论提交或取消，固定返回T02 |
| T04进入T05 | 提交后返回T04的最初来源 |
| 系统推送或无来源深链 | 返回O01 |

G02只展示订单任务摘要，点击整张订单先进入O01，不在订单卡增加第二个直接处理按钮。

T04进入手术植入时继续携带最初来源。植入正式提交后不强制业务员立刻进入物品结余处理，由O01或全局任务中心提供后续入口。

## 7. T01订单协同

### 7.1 定位

T01不是“确认替代方案”，也不要求业务员识别沟通类型。后台按照当前条件无法直接继续处理订单、需要业务员补充、沟通或决定时，发起绑定该订单的协同事项。

### 7.2 页面形态

T01采用聊天式时间线，可以承载：

- 后台说明；
- 业务员文字回复；
- 图片和附件；
- 补充资料；
- 后台发送的方案或问题；
- 必要的结构化业务动作。

前台不要求业务员区分替代、规格、数量、非目录映射、时间或交付安排等类型；后台可以保留分类用于任务路由、统计和权限。

### 7.3 正式业务边界

普通文字、图片和附件只作辅助沟通，不能直接改变正式订单事实。需要业务员作出正式决定时，后台在会话中发送结构化操作卡，例如“同意按该方案继续／不同意”。只有明确提交结构化动作，才能产生订单变更、方案确认或其他正式结果。

T01不能代替：

- T02正式收货确认；
- T03收货异常申报；
- T04手术情况确认；
- T05正式延期、取消或变更申请；
- 手术植入结果；
- 本单物品结余处理。

## 8. 待结余与后续任务

订单主状态使用“待结余”，不再使用“待清算”和“待还回”作为主状态。手术结果明确但已接收产品或器械仍有去向未闭环时进入待结余。

待结余可以同时存在：

- 已植入；
- 申请转个人仓；
- 申请转本人其他订单；
- 还回公司；
- 实物异常处理。

还回公司只是其中一个并行分支，内部可出现待交寄、运输中、待公司清点和已确认还回。等待公司接收清点时只展示普通进度，不继续作为业务员待办；确需业务员交寄、补充凭证或处理差异时才生成相应任务。

## 9. 当前明确不做

- 不在本稿设计T01聊天视觉稿；
- 不在本稿设计全局任务中心页面；
- 不修改现有原型；
- 不把T01建设成脱离订单的通用即时通讯；
- 不允许业务员之间沟通或跨业务员处理；
- 不让自由文字自动触发正式业务状态变化。
