# O01—T任务编排规则 v0.1

> 状态：已确认，作为当前任务编排基线  
> 日期：2026-08-07  
> 范围：定义O01、T01—T03、T05及手术情况确认任务之间的关系，不设计具体视觉稿，不修改现有原型。

## 1. 核心模型

O01始终是某张手术通知订单的详情入口。订单主状态回答“整张订单总体走到哪里”，T任务回答“当前是否有事情必须由业务员本人处理”，二者并行存在，互不覆盖。

```text
O01订单详情
= 本人待处理任务（存在时置顶）
+ 订单身份、手术场景和一个主状态
+ 订单内容（主订单＋接续订单）
+ 发货与接收（整单或分批）
+ 业务员当前可主动发起的订单操作
+ 页面末端的订单记录入口
```

T01—T03、T05及手术情况确认任务不是一条依次经过的流程，也不是订单主状态。T04已退出正式页面集合，但手术情况确认任务及其跨模块入口继续保留。

## 2. O01与T页面的直接关系

### 2.1 O01直接承载

- T01订单协同；
- T02实际交付批次确认；
- 手术情况确认任务：直接在O01／G03任务组件中处理，不进入独立T04页面。

### 2.2 不从O01任务区直接承载

- T03收货异常申报：只能从T02核对具体交付批次时进入；
- T05变更与取消申请：由业务员从O01主动发起，或承接手术情况确认任务的延期和取消。
- T05保持一张页面：从O01“变更取消”主动进入时先选择当前允许的申请事项；从手术情况确认任务点击延期或取消进入时，直接定位对应模式，不重复选择。
- 同一现实事件引起的多项相关变更可以合并为一份T05申请，各项分别保存并回写处理结果；“取消整单”必须独立提交，不与其他变更项混合。

```text
O01
├─ T01 订单协同
├─ T02 实际交付确认 → T03 收货异常
├─ 手术情况确认任务 → 手术植入
│                   └→ T05 延期／取消
└─ 主动发起T05 变更取消
```

## 3. O01任务区的展示规则

### 3.1 没有任务

完全隐藏“待我处理”区域，不显示“当前没有待办”。订单普通进度继续由主状态、必要状态说明和对应订单／交付事实表达。

### 3.2 一项任务

完整展示该任务的标题、必要影响和明确动作。按钮使用具体动作名称，不统一使用“处理当前任务”。

### 3.3 多项任务

完整展示动态计算出的最高优先级任务，并显示“另有N项待处理”。点击后进入全局任务中心，并限定为当前订单；不另建第二套订单任务列表。

## 4. 任务优先级

任务不按T编号固定排序，依次考虑：

1. 是否已经逾期；
2. 是否阻塞手术或下一步履约；
3. 风险等级；
4. 距离任务截止时间；
5. 距离计划手术时间；
6. 已等待时长；
7. 稳定任务编号。

默认情况下，已到期的手术情况确认任务通常高于影响手术的T01，影响手术的T01通常高于刚刚生成的普通T02；但逾期T02可以动态升高。

任务排序只决定页面展示顺序。是否推送或形成首页强提醒单独判断，避免业务员被普通进度频繁打扰。

## 5. 任务生命周期

任务底层区分：

- 待本人处理；
- 处理中；
- 等待公司或其他模块结果；
- 已完成；
- 已失效／已替代。

O01任务区只显示仍需业务员本人行动的任务。业务员已经完成动作、只等待公司处理时，任务退出“待我处理”，普通结果回到订单详情；完成、失效和替代记录进入O04订单记录，不删除历史。

### 5.1 T01

- 后台发起需要业务员补充、沟通或决定的订单协同事项时生成；
- 业务员不能在没有公司协同事项时主动创建T01聊天；
- 所需回复或结构化决定被页面接受后，若后续只等待公司，任务退出“待我处理”；
- 等待公司期间允许在原事项中补充遗漏的文字、图片或附件，但补充不新建另一项协同，也不把本人任务重新激活；
- 公司再次正式要求本人行动时，以新事实或新版本形成任务；
- 公司正式结束事项后只读；
- 后台撤回事项时失效；
- 出现新版本时，旧事项保留记录，新事项取代旧事项；
- 同一事项的重复保存和推送不能产生重复任务。

### 5.2 T02

- 实际交付批次已经送达或完成线下交接、业务员尚未确认时生成；
- 正常明细完成确认、异常明细完成事实申报且不存在未表态明细时完成；
- 公司在业务员接收前成功拦截并完成公司清点时失效；
- 一次实际交付批次只生成一条T02，即使该批包含同一业务员的多张订单。
- 全部相符时一次确认整个批次；存在异常时先由T03申报并标记异常明细，再一次确认其余正常明细；不要求逐项勾选正常、逐件扫码或按关联订单分别确认。
- T03从一条具体异常明细进入，同批次内可以追加其他相关异常明细一次提交；不同批次不合并，各条异常仍分别回写原订单和实物事实。
- 未实际收到的异常部分不形成本人在手责任；实际到手但异常的部分形成临时在手责任并冻结；同一明细部分正常、部分异常时按数量拆分回写。
- 所有明细已有明确结果后T02退出待我处理；未闭环异常继续留在O01对应交付事实并阻止订单完成，不用T02继续承载公司后续处置。

### 5.3 手术情况确认任务

- 当前有效计划手术时间已经过去，且没有有效植入、已生效延期或已生效取消结果时生成；
- O01和G03直接提供“记录手术植入、手术延期、手术取消”三个动作，不进入独立T04页面；
- 选择“记录手术植入”后进入对应手术植入记录，只有有效植入结果正式提交后才完成；
- 提交延期或取消申请后进入等待公司处理，不继续占据待我处理；
- 延期申请可以填写新的手术日期和准确时间，也可以标记“时间待定”；延期正式生效后，旧计划时间不再触发手术情况确认任务，新时间确定后形成新的有效计划时间；
- 延期期间订单和已接收实物仍绑定原手术，不因延期自动进入本单物品结余；
- 申请被退回时重新激活；
- 其他入口已经形成有效植入结果时自动完成。
- 计划手术时间到达前，在订单仍可关联该台手术且尚无正式结果时，O01可以提供低强调的条件性“记录手术植入”入口；到达计划时间仍无结果时再升级为本人任务。

## 6. 入口与返回

任务页面记录进入来源和页面上下文：

| 来源 | 完成或退出后的默认返回 |
|---|---|
| O01 | 返回原O01并重新计算主状态和剩余任务 |
| G01 | 返回G01并更新任务摘要 |
| 全局任务中心 | 返回原筛选、排序和滚动位置 |
| O01发货与接收区域进入T02 | 返回原批次位置 |
| T03 | 无论提交或取消，固定返回T02 |
| 手术情况确认任务进入T05 | 提交后返回任务的最初来源 |
| 系统推送或无来源深链 | 返回O01 |

G02只展示订单任务摘要，点击整张订单先进入O01，不在订单卡增加第二个直接处理按钮。

从手术情况确认任务进入手术植入时继续携带最初来源。植入正式提交后不强制业务员立刻进入物品结余处理，由O01或全局任务中心提供后续入口。G01继续保留手术植入模块入口；O01／G03入口负责携带当前订单和候选实物上下文。

## 7. T01订单协同

### 7.1 定位

T01不是“确认替代方案”，也不要求业务员识别沟通类型。后台按照当前条件无法直接继续处理订单、需要业务员补充、沟通或决定时，发起绑定该订单的协同事项。

T01不是业务员可以主动打开的通用聊天工具。没有公司正式发起的协同事项时，O01不显示新建协同或发送消息入口。

### 7.2 页面形态

T01采用聊天式时间线，可以承载：

- 后台说明；
- 业务员文字回复；
- 图片和附件；
- 补充资料；
- 后台发送的方案或问题；
- 必要的结构化业务动作。

前台不要求业务员区分替代、规格、数量、非目录映射、时间或交付安排等类型；后台可以保留分类用于任务路由、统计和权限。

T01前台不采用固定四层或固定字段模板，始终只回答三个核心问题：这是哪台手术的订单、公司现在要本人做什么、本人现在可以怎么处理。订单语境只保留防止错单所需的最小信息；事项要求直接表达；沟通记录、变化事实、影响和期限只在理解或完成当前动作确有需要时展示。

### 7.3 订单页面与事项任务

- 同一手术需求组只有一张T01订单协同页，不为每个协同事项重复创建页面；
- 公司发起的每个协同事项分别保留稳定事项身份、任务身份、版本、影响、截止时间和当前状态；
- 同一订单存在多个有效协同事项时，它们仍分别计为任务并参与全局优先级排序；
- 从O01、G03或系统深链进入时，T01直接定位并突出对应事项，不要求业务员在整条时间线中自行查找；
- T01一次只展开一个事项及其独立对话；不同事项的消息、附件和结构化动作不混成一条总聊天流；
- 存在其他有效事项时显示“另有N项协同”，通过事项切换在同一T01页打开；
- 已结束事项可以在同页收敛显示，但不得与当前事项混成一个无法独立完成的聊天任务。

### 7.4 正式业务边界

普通文字、图片和附件只作辅助沟通，不能直接改变正式订单事实。需要业务员作出正式决定时，公司在会话中发送结构化操作卡。卡片只说明当前决定所必需的方案变化和实际影响；不建立必须覆盖所有可能字段的固定对比表，期限也只在该事项实际存在时显示。

业务员明确提交“同意按此方案继续”后，才形成对该方案的正式确认并写回对应业务对象。选择“不同意”时，当前订单事实保持不变，原事项继续协同；不同意本身不取消订单、不发起订单变更，也不替代T05。是否需要补充说明只按当前事项的实际必要性处理，不预设复杂原因分类。公司后续提出实质不同的方案时，按新事实或新版本处理，不覆盖原决定记录。

本人完成当前要求、后续只等待公司时，T01任务退出“待我处理”，页面显示“已回复，等待公司”。此时业务员可以在原事项中补充遗漏资料，但不能开启新的沟通主题；公司正式结束、撤回或替代事项后，原事项只读。

等待公司时不再从O01顶部任务区或G03作为本人任务进入；事项正式结束、撤回或替代后，从O04对应订单记录进入只读事项，不保留当前任务入口。

T01不能代替：

- T02正式收货确认；
- T03收货异常申报；
- 手术情况确认任务；
- T05正式延期、取消或变更申请；
- 手术植入结果；
- 本单物品结余处理。

## 8. 待结余与后续任务

订单主状态使用“待结余”，不再使用“待清算”和“待还回”作为主状态。手术结果明确但已接收产品或器械仍有去向未闭环时进入待结余。

待结余可以同时存在：

- 已植入；
- 申请转个人仓；
- 申请转本人其他订单；
- 还回公司；
- 实物异常处理。

还回公司只是其中一个并行分支。面向业务员的局部进度只显示“发起还回、公司受理、还回中”，公司形成正式结果后显示“已还回”；后台处理、第三方运输和公司清点不展开为更多APP状态。只等待公司或第三方过程时不继续作为业务员待办；确需业务员执行公司安排、补充资料或处理差异时才生成相应任务，差异不作为并列还回状态。

待结余阶段不再提供“补充需求、变更取消”固定入口。仍有实物需要本人选择去向时，生成“处理本单物品结余”任务并进入O01对应实物位置；借单还回进入独立还回办理页面，申请入库、申请转用和申报在手异常打开O01相应轻量组件。申请或本人动作已经提交、后续只等待公司或第三方过程时，退出待我处理。公司正式要求本人执行还回安排、补充资料、重新选择或处理问题时，再生成本人任务并返回原办理上下文。

手术情况确认任务不再出现，T05不再作为主动入口。此前批次迟到并完成实际交付时，T02仍可与待结余共存；本人确认后新增的在手责任继续进入本单物品结余。

已完成订单不生成T01—T03、T05、手术情况确认或S系列任务。完成后的实质性更正如果重新产生本人责任，订单必须先通过正式结果重新打开并重新计算主状态，之后才允许生成任务；不能在“已完成”历史状态下直接挂载待办。

已取消订单同样不生成T01—T03、T05、手术情况确认或S系列任务。取消被正式撤销或实质性更正重新产生本人责任时，订单必须先形成重新打开结果并重新计算主状态，之后才允许生成任务；不能在“已取消”历史状态下直接挂载待办。

## 9. 当前明确不做

- 不在本稿设计T01聊天视觉稿；
- 不在本稿设计全局任务中心页面；
- 不修改现有原型；
- 不把T01建设成脱离订单的通用即时通讯；
- 不允许业务员之间沟通或跨业务员处理；
- 不让自由文字自动触发正式业务状态变化。
