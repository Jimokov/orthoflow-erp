# 手术通知 APP 跨模块接口摘要

> 更新日期：2026-08-26；2026-09-04
> 作用：让新模块只继承手术通知已经确认的必要结果，不必重新理解整套手术通知，也不把其内部流程复制过去。

## 1. 输出给手术植入 APP

### 进入条件

- 计划手术时间到达不等于已经实施；
- 业务员从O01或G03的“手术情况确认”任务选择“记录手术植入”后，可以进入同一台手术对应的植入记录；该任务不再经过独立T04页面；
- 计划手术时间到达前，在订单仍可关联该台手术且尚无正式结果时，O01可以提供低强调的条件性入口；到达计划时间仍无结果时升级为本人任务；
- G01继续保留手术植入模块入口；O01／G03入口负责携带当前订单、任务和候选实物上下文，两类入口职责不同；
- 仅进入页面不构成植入结果，必须由手术植入正式提交有效结果。

### 可以带入

- 当前公司与业务员；
- 来源手术通知或手术需求组的唯一引用；
- 来源任务、来源页面和返回目标；
- 已由业务员确认实际接收、仍绑定本订单的候选实物；
- 候选实物对应的可追溯身份、批号和可选数量。

其中，每条正常确认的候选实物必须能够回查到其实际交付批次、冻结出货清单明细、来源手术需求组或订单、接收业务员、确认时间以及正常确认数量；这条本人接收事实构成候选实物的最近有效交接。T02不要求逐件扫码，也不要求所有实物存在单件唯一编码；批号或可追溯身份按实际已有信息保留。

### 不得替手术植入决定

- 候选实物默认不全选；
- 患者信息、住院号和实际植入明细由手术植入采集；
- 手术植入可以使用个人仓等其他合法来源；
- 手术通知不能把整张订单一键转成植入或入库。

### 手术植入返回

- 正式植入记录的唯一引用；
- 已确认的实际植入产品、批号和数量；
- 结果正式形成的事实。

实物销售按“产品＋批号／可追溯身份（如有）＋数量”记录来源分配。来源为本手术需求组候选实物的分配，必须携带对应候选实物引用并回写；一次植入可同时包含自有库和通知来源。手术通知只依据通知来源分配重新计算候选实物的剩余责任与结余。

植入侧依据胶贴或同等凭证的产品、批号／可追溯身份和数量回查上述交接事实；不能形成正常通知来源归属时，不得人工改归通知来源，也不构成通知正式回写，按植入侧“来源核验异常”保留实际使用事实。

仅当该异常实际使用记录仍携带来源手术通知或需求组上下文时，植入侧向对应 O01 发送一条非结清的“来源待核实使用关联”：包括正式植入记录引用、来源通知上下文引用、实际使用的产品、批号／可追溯身份（如有）、数量和凭证引用。它不携带正常通知来源分配，不结清候选实物，也不等同于正常植入回写；通知将其记为“已使用，来源待核实”并保留为未闭环责任。完全没有通知上下文的来源核验异常不得触碰任何 O01。

后续来源核验只按真实上游链校正一次：确认属于该通知时转换为正常通知来源回写；确认属于其他来源时撤销该待核实关联并恢复通知候选实物的原责任；仍无法核实的继续阻止通知订单完成。后续处理岗位、时限、审批与页面不在本接口中定义。

返回后，手术通知完成“手术情况确认”任务，重新计算O01状态与任务。没有被植入的候选实物继续保留在原订单责任中；仍有物品待落实去向时，O01展示待结余责任总览并提供适用动作入口，但不强制立即跳转。

### 正式结果的取消、失效与冲正回写

- 取消／失效已形成的正式植入结果时，植入侧保留原记录，并按该记录的可追溯关系撤销它产生的一切通知侧结果：正常通知来源分配、仍有效的“来源待核实使用关联”，以及该关联此前已转换出的正常通知来源结果。手术通知据此恢复相应候选实物的责任并重算数量、待结余与完成资格；自有库部分不参与本模块回写。
- 销错冲正时，先完整撤销被冲正原记录的一切通知侧结果；正确的新正式记录形成后，再按其真实来源独立返回正常通知来源分配或“来源待核实使用关联”。通知按这一顺序重算，不得让旧记录的结果静默保留。
- 来源核实只是同一有效正式植入记录内的责任校正，不属于取消；关联的形成、转换或撤销及其原记录、冲正记录和正确记录都必须可追溯，不能互相覆盖。
- 原记录撤销后，如当前有效计划手术时间已过，且不存在任何有效植入、已生效延期或已生效取消结果，O01／G03按既有规则重新生成“手术情况确认”任务；否则不因本项自动生成本人待办。O01继续呈现重算后的当前责任，O04保留原记录及其调整链，不新增页面或订单状态。
- 未正式形成、自动校验异常、补齐重提、放弃或超期退出均不回写手术通知。
- 具体权限、时限、审批、幂等键、重试和接口字段仍未定义；不得由本摘要推导后台或库存能力。

## 2. 与库存管理功能模块的已确认边界

- 手术通知不展示总仓、地方仓、个人仓或可用数量；
- 业务员本人已有并可直接销售的库存不重复进入手术通知要货；
- 手术通知已接收物品不会自动成为个人仓可用库存；
- “转入个人仓”只形成业务员申请，后台批准后才生效；
- 个人仓审批、最低库存和库存计算尚未由库存模块正式定义，本摘要不得替库存模块补全。

因此，未来库存模块只能继承“经批准转入个人仓的结果”和可追溯实物责任，不能继承手术通知的要货、履约或订单状态机。

## 3. 器械包可用／放行结果边界

- 器械包可用／放行结果是本模块外部依赖，不构成当前已登记的独立模块；
- 手术通知不设计器械处理、清洁、灭菌和再次放行流程；
- 公司确认器械包还回后，本订单中的业务员保管责任可以解除，订单完成不等待后续器械处理结束；
- 具体器械包转入本人下一张订单前，必须读取公司确认的可用或放行结果。

该结果如何形成仍不属于本池，且当前不建立承接它的独立页面或模块。

## 4. 输出给订单中心与全局任务

- 草稿只留在手术通知创建域，由C00／C10及来源O01按规则引用，不进入订单中心；
- 正式订单向订单中心输出当前／历史归属、主状态、业务更新时间和最多一项必要提示；
- 需要业务员本人行动时引用同一条动态任务，不生成第二套订单中心任务；
- 任务完成后只等待公司处理时退出“待我处理”，底层订单事实与责任继续保留。

## 5. 与 Web 后台的当前边界

APP 已经确认会向公司提交需求、确认实际接收、提出变更或结余申请，并读取公司返回的履约结果和最终确认。复制订单或模板带入的医院、科室、术者无法映射且当前资料库仍无适用项时，APP还可以保留来源原文并输出“待公司确认的基础资料”；该结果必须与已经匹配的正式基础资料区分。

当前项目没有启用 Web 后台总池，因此以下内容仍未定义：

- 由哪个后台页面或岗位处理；
- 公司内部采购、借调、配货、仓库与上游路径；
- 后台内部状态机、权限和批量操作；
- 具体接口字段与技术协议。

未来讨论 Web 后台时，可以把本段作为 APP 对外结果约束，但不能把旧 Web 草稿直接当成现行后台设计。

S01允许一次交寄合并当前业务员本人多张来源订单的待还实物。未来Web手术通知后台必须同时保留交寄批次、来源订单、实物身份和分别回写的责任关系；具体后台呈现与处理方式登记为桩子，留待Web模块正式启动后讨论，不由APP资料推演。

寄回方式由后台发起并形成有效安排。后台可选择的方式、下发内容形式、APP侧动态执行表单、必填项和凭证要求均登记为归属未来Web后台及其APP接口的桩子；手术通知APP当前只确认S01能够展示有效安排、承接本人动作并回写结果，不在本阶段固定字段。

## 6. 与未来业务报销模块的桩子

- S01“借单还回”在记录交接方式的相应位置登记进入未来“业务报销”模块的跳转桩子；
- 当前只确认存在这一衔接方向，不创建业务报销模块、页面编号、表单字段、报销规则、审批流程或结果状态；
- 具体触发条件、携带内容、返回位置以及报销结果是否影响S01提示，留到业务报销模块正式登记并与S01进行接口讨论时确认；
- 在上述桩子正式闭合前，S01自身的还回、交寄、运输和公司清点责任链不得依赖未经定义的报销流程。
