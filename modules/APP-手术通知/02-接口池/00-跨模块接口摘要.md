# 手术通知 APP 跨模块接口摘要

> 更新日期：2026-08-10  
> 作用：让新模块只继承手术通知已经确认的必要结果，不必重新理解整套手术通知，也不把其内部流程复制过去。

## 1. 输出给手术植入 APP

### 进入条件

- 计划手术时间到达不等于已经实施；
- 业务员在 T04 确认“已进行”后，可以进入同一台手术对应的植入记录；
- 仅进入页面不构成植入结果，必须由手术植入正式提交有效结果。

### 可以带入

- 当前公司与业务员；
- 来源手术通知或手术需求组的唯一引用；
- 来源任务、来源页面和返回目标；
- 已由业务员确认实际接收、仍绑定本订单的候选实物；
- 候选实物对应的可追溯身份、批号和可选数量。

### 不得替手术植入决定

- 候选实物默认不全选；
- 患者信息、住院号和实际植入明细由手术植入采集；
- 手术植入可以使用个人仓等其他合法来源；
- 手术通知不能把整张订单一键转成植入或入库。

### 手术植入返回

- 正式植入记录的唯一引用；
- 已确认的实际植入产品、批号和数量；
- 结果正式形成的事实。

返回后，手术通知完成 T04，重新计算 O01 状态与任务。没有被植入的候选实物继续保留在原订单责任中；仍有物品待落实去向时提供“本单物品结余”入口，但不强制立即跳转。

## 2. 与库存 APP 的已确认边界

- 手术通知不展示总仓、地方仓、个人仓或可用数量；
- 业务员本人已有并可直接销售的库存不重复进入手术通知要货；
- 手术通知已接收物品不会自动成为个人仓可用库存；
- “转入个人仓”只形成业务员申请，后台批准后才生效；
- 个人仓审批、最低库存和库存计算尚未由库存模块正式定义，本摘要不得替库存模块补全。

因此，未来库存模块只能继承“经批准转入个人仓的结果”和可追溯实物责任，不能继承手术通知的要货、履约或订单状态机。

## 3. 与消毒模块的已确认边界

- 消毒是独立业务域；
- 手术通知不设计清洗、消毒、灭菌和再次放行流程；
- 公司确认器械包还回后，本订单中的业务员保管责任可以解除，订单完成不等待后续消毒结束；
- 具体器械包转入本人下一张订单前，必须读取独立消毒模块返回的可用或放行结果。

消毒模块内部如何形成该结果仍不属于本池。

## 4. 输出给订单中心与全局任务

- 草稿只留在手术通知工作区，不进入订单中心；
- 正式订单向订单中心输出当前／历史归属、主状态、业务更新时间和最多一项必要提示；
- 需要业务员本人行动时引用同一条动态任务，不生成第二套订单中心任务；
- 任务完成后只等待公司处理时退出“待我处理”，底层订单事实与责任继续保留。

## 5. 与 Web 后台的当前边界

APP 已经确认会向公司提交需求、确认实际接收、提出变更或结余申请，并读取公司返回的履约结果和最终确认。但是当前项目没有启用 Web 后台总池，因此以下内容都还是未定义：

- 由哪个后台页面或岗位处理；
- 公司内部采购、借调、配货、仓库与上游路径；
- 后台内部状态机、权限和批量操作；
- 具体接口字段与技术协议。

未来讨论 Web 后台时，可以把本段作为 APP 对外结果约束，但不能把旧 Web 草稿直接当成现行后台设计。
