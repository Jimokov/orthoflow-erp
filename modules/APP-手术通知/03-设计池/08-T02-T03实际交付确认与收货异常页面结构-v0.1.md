# T02／T03 实际交付确认与收货异常页面结构 v0.1

> 状态：结构已确认，低保真暂缓至O／T／S关系打通后统一处理  
> 更新日期：2026-08-16  
> 范围：只定义业务员移动端 T02、T03 的页面关系与交互结构，不制作低保真，不定义 Web 后台清单更正、物流或仓库处理。

## 1. 页面身份

### 1.1 T02 实际交付确认

T02用于业务员核对并确认一次已经送达或完成线下交接的真实交付批次：

- 一次真实交付批次只生成一个T02任务；
- 同一批次可以关联当前业务员的一张或多张订单；
- 多张订单仍分别保留订单和明细身份，确认结果分别回写；
- 业务员不能自行把没有共同交付关系的订单拼成一批；
- T02不是发货确认，只有实际送达或完成线下交接后才生成。

### 1.2 T03 收货异常申报

T03只处理业务员正式确认接收前、核对当前实际交付批次时发现的异常：

- 唯一入口是T02中的当前交付明细；
- 提交或取消均返回原T02批次；
- 业务员只申报事实和证据，不能修改后台冻结的正式出货清单；
- 本人确认接收后发生或发现的在手异常回到来源O01并打开异常申报组件；还回后公司清点发现的差异留在S01“借单还回”；T03与O01异常组件可以共享表单能力，但不合并入口、责任判定、返回和结果回写。

## 2. T02入口与返回

同一个T02任务可以从以下位置进入：

- O01顶部“待我处理”中的实际交付确认任务；
- O01“发货与接收”中的对应未确认批次；
- G03“待我处理”；
- O03复杂供货与收货详情中的对应未确认批次；
- 系统交付提醒或深链。

G02订单中心不直接增加T02处理按钮，点击订单仍先进入O01。完成或暂时退出T02后按来源返回；从O01或O03进入时恢复原批次位置。

## 3. 已确认的正常／异常分流

T02以“少操作、不掩盖异常”为原则：

1. 业务员核对整个真实交付批次；
2. 全部相符时，一次执行“全部无误，确认接收”；
3. 发现问题时，只对异常明细进入T03申报；
4. 从T03返回后，异常明细在T02中明确标记，并排除在正常确认范围外；
5. 业务员一次执行“确认接收其余物品”；
6. 正常接收事实与异常申报分别回写对应订单和明细。

T02不要求：

- 逐项勾选正常；
- 逐件扫码；
- 按关联订单分别确认；
- 用一次“全部确认”覆盖已经发现的异常。

## 4. 已确认的T03申报粒度

- 从T02点击某条异常明细进入T03，默认只带入该条；
- 同一实际交付批次内，受同一问题影响的其他异常物品可以追加到本次申报；
- 一次提交可以覆盖同批多条相关异常明细，但每条仍分别保留所属订单、实物和异常事实；
- 不要求业务员进入T03前先完成多选，也不要求同一问题逐条重复填写；
- 不同实际交付批次不能合并申报。

## 5. 已确认的接收责任回写

| 现场事实 | 接收与责任结果 |
|---|---|
| 未实际收到或数量短少 | 记录未收到，不形成本人在手责任 |
| 实物已到手但存在异常 | 记录“已到手但异常”，不算正常接收；形成临时在手责任，公司处理前不能按正常物品使用或进入后续去向 |
| 同一明细部分正常、部分异常 | 按数量拆分；正常部分确认接收，未收到部分不形成责任，到手异常部分形成临时在手责任 |

正常明细确认且所有异常明细已经完成事实申报后，T02任务完成并退出“待我处理”。尚未闭环的异常继续显示在O01对应交付事实中并阻止订单完成，但T02不继续承载公司的后续处理过程。

## 6. 结构收口结论

T02／T03的页面身份、入口返回、整批确认、正常／异常分流、同批多条相关异常一次申报及接收责任回写均已确认。结构讨论至此收口，不展开后台处置、异常类型字段或具体表单排布；低保真暂缓。本文件不再承担当前推进位置，后续唯一任务以模块首页、当前设计进度和页面设计总控为准。
