# T01 订单协同页面结构 v0.1

> 状态：结构已确认，低保真暂缓至O／T／S关系打通后统一处理  
> 更新日期：2026-08-16  
> 范围：只定义业务员移动端 T01 的当前页面结构，不制作低保真，不定义 Web 后台内部发起流程。

## 1. 页面身份

T01 是公司针对正式订单发起具体协同事项后，业务员查看说明、补充资料、沟通或作出必要正式决定的订单内页面。

- 同一手术需求组共用一张 T01 页面；
- 公司发起的多个事项分别保留事项、任务、版本和状态；
- 页面一次只展开一个事项，不把不同事项的消息、附件和动作混成一条总聊天流；
- 没有公司正式发起的事项时，业务员不能主动新建聊天；
- T01 不是订单详情、通用聊天工具或 T05 正式变更取消的替代品。

## 2. 最高设计约束

T01 页面始终只服务三个核心问题：

1. 这是哪台手术的订单？
2. 公司现在要我做什么？
3. 我现在可以怎么处理？

任何字段、卡片、状态、记录或操作，不能直接帮助回答这三个问题时，默认不进入业务员当前界面。系统底层仍可保存完整方案、版本、影响、期限和审计事实，但不能把底层完整性等同于前台信息量。

## 3. 三个核心问题的呈现原则

### 3.1 这是哪台手术的订单

- 只显示足以防止业务员处理错单的最小订单语境；
- 不固定要求订单号、医院、手术时间和主状态同时出现；
- 从 O01 进入时不重复 O01 已经清楚表达的完整订单内容；
- 从 G03 或系统深链进入时，可以补足识别当前手术所需的信息。

### 3.2 公司现在要我做什么

- 直接用一句清楚的业务语言说明当前要求；
- 不要求业务员识别替代、规格、数量、非目录映射、时间或交付安排等后台分类；
- 只有影响理解或判断的变化事实才显示；
- 期限只在当前事项实际存在期限时显示；
- 历史沟通只作为理解当前要求的辅助，不与当前要求争夺首屏。

### 3.3 我现在可以怎么处理

页面只给出当前真正适用的处理方式：

| 当前情形 | 页面重点 | 可执行动作 |
|---|---|---|
| 需要补充或沟通 | 公司当前要求和必要上下文 | 文字、图片或附件回复 |
| 需要正式决定 | 当前方案及决定所必需的变化与影响 | 同意当前方案／不同意并继续协同 |
| 本人已完成、只等待公司 | 简洁显示“已回复，等待公司” | 仅在遗漏时补充资料，不重新激活本人任务 |
| 公司已结束、撤回或替代 | 当前结果和必要历史 | 只读 |

结构化方案不建立覆盖所有可能字段的固定对比表。没有变化的信息不重复，没有实际期限时不显示期限；“不同意”不预设复杂原因分类，是否需要补充说明只根据当前事项的真实必要性处理。

## 4. 事项与沟通记录

- 当前页一次只展开一个事项及其必要沟通记录；
- 不混入同一订单其他协同事项的消息、附件或动作；
- 存在其他有效事项时，通过“另有 N 项协同”切换；
- 较早历史可收敛，不能让完整聊天历史遮住当前要求和当前动作。

## 5. 入口、切换与返回

- O01、G03 和系统深链进入同一 T01 页面，并直接定位对应事项；
- 同一事项从不同入口进入时引用同一任务，不重复生成；
- 切换“另有 N 项协同”只改变当前展开事项，不改变订单；
- 暂时退出且本人任务未完成时，按来源返回并保留任务；
- 本人动作完成后若只等待公司，任务退出“待我处理”，按来源返回；
- 等待公司期间不再从 O01 顶部任务区或 G03 作为本人任务进入；需要补充遗漏资料时，可从O04原事项记录回到同一事项，但不得新开事项、恢复本人任务或修改已经提交的正式决定；
- 公司结束、撤回或替代事项后，只从 O04 对应订单记录进入只读事项，不保留当前任务入口；
- 普通回复、图片或附件本身不直接改写正式订单事实。

## 6. 与其他页面的边界

T01 不承接：

- T02 实际交付确认；
- T03 收货异常申报；
- 手术情况确认任务；
- T05 正式延期、取消或变更申请；
- 手术植入结果；
- O01本单物品总览、独立还回办理、O01入库／转用轻量组件及在手异常原办理上下文。

正式结果形成后写回原业务对象，并由 O01 展示当前有效事实；完整正式记录进入 O04，不把自由沟通全文复制到 O01 或 O04。

## 7. 结构收口结论

补充或沟通、正式决定、等待公司、事项结束四种情形均可由三个核心问题覆盖，没有新增页面、字段或后台能力缺口：

- 有本人动作时，T01是轻量处理页；
- 只等待公司时退出待办，原事项仅保留低强调的遗漏补充能力；
- 事项结束后进入O04历史记录并只读；
- T01不再继续讨论固定四层、固定字段、固定对比表或复杂原因分类。
