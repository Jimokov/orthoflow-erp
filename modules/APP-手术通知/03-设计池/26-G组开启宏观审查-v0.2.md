## 1. 审查结论

G组不是手术通知的第二套业务流程，而是业务员进入、查找和被分流至既有业务上下文的全局层：

- **G01**负责开始工作、看见任务摘要或必要强提醒，并导航到真实入口；
- **G02**负责查找本人正式订单，并进入该订单的 O01；
- **G03**负责汇集跨模块、当前必须由本人直接处理的同一批任务，并进入原动作承载；
- **G04**保留为“我的”的全局外壳，不在当前阶段补写内部设置能力。

真实订单信息、订单操作、协同、交付确认、变更、还回和异常仍分别留在 O01、T、S 或其已经确认的轻量组件中。G组只导航、汇总或保持全局入口，不复制业务事实，不形成第二套订单、任务或操作流。

## 2. 继承事实、对象与边界

| 项目 | 当前事实 |
|---|---|
| 核心对象 | 本人正式订单、本人当前任务、全局导航入口；草稿与模板不是 G 组对象 |
| 起点 | APP 默认进入 G01；底部全局导航固定为 G01、G02、G04；G03由摘要、强提醒、O01“另有任务”或系统深链进入 |
| 终点 | G01进入C00、G02、G03或已登记的其他模块入口；G02进入O01；G03进入真实动作页；G04当前只承载全局入口身份 |
| 角色责任 | 业务员只能查看本人对象，并在原业务页面完成本人动作；G组不代替公司内部处理或跨业务员操作 |
| 结果回写 | 原动作页接受、失效或替代任务后，同一任务ID在G01、G03、O01同步；订单事实回写O01，G02仅刷新必要的目录摘要 |
| 不包含 | Web后台、库存与手术植入内部设计；G01提醒阈值与推送频次；G03／G04字段和视觉结构；草稿、模板、个人资料或医院绑定的未确认能力 |

## 3. 业务能力—现有承载位置矩阵

| 业务能力 | 当前唯一或主承载 | G组处置 | 不可重复承载的边界 |
|---|---|---|---|
| 开始手术通知、进入已登记模块 | G01 → C00／对应模块入口 | 保留G01 | G01不保存草稿，不承担C00创建链 |
| 查看本人正式订单目录、检索、筛选、排序 | G02 | 保留G02 | 不设“全部订单”第三集合；草稿留C00／C10，详情与操作留O01 |
| 查看某一订单的完整身份、进度、任务与操作 | O01 | 不由G02复制 | G02卡片仅一主状态及至多一项必要提示，不放任务按钮 |
| 汇总所有当前需本人直接行动的事项 | G03 | 保留G03 | G01只显示摘要／条件性强提醒；O01只引用本订单任务；原动作在T／S／O01／植入模块完成 |
| 处理某个协同、交付、变更、物品去向或还回事项 | T、S、O01条件区块及手术植入模块 | 不新增G页动作页 | G03只带入真实动作页，完成后回原G03位置 |
| 订单状态与普通等待公司进度 | O01，G02仅目录摘要 | 不进入G03 | “只等待公司”、普通消息、已完成记录均不形成待我处理 |
| 强提醒与系统推送 | G01条件性强提醒／系统深链 | G01保留承载资格 | 阈值、优先级细则和推送策略仍为G组／通知后续桩子，不在本次补全 |
| 全局个人／设置型入口 | G04 | 保留G04外壳 | 不自动推出资料、医院、模板、草稿或任何设置项 |

## 5. 跨组关系与返回

| 来源／去向 | G组应承担 | 不应承担 |
|---|---|---|
| G01 → C00 | 进入手术通知起点 | 展开草稿、模板或需求编辑细节 |
| G02 → O01 | 定位并进入订单 | 复制O01交付、任务或操作 |
| G01／G03／O01 → T、S、植入 | 引用同一任务并分流 | 在G组直接完成业务动作 |
| 动作页 → G01／G02／G03 | 按来源返回；G03保留筛选、排序与滚动位置 | 强制回首页或丢失原查询上下文 |
| 系统推送 → G03／O01／真实动作页 | 只做深链 | 生成第二个任务或把普通等待误作任务 |

## 7. 推荐的后续顺序

待各核心业务模块具备自身规则、页面与任务接口后，G组不重排页数，按以下顺序恢复单页逻辑：

1. G01：先确定任务摘要、强提醒、搜索与模块入口之间的克制边界；
2. G03：再确定唯一任务集合的列表、排序、筛选、进入与来源感知返回；
3. G02：核对目录卡片、当前／历史集合、检索及进入O01；
4. G04：仅在有明确的全局能力输入时讨论内部内容；否则保持外壳，不为凑页设计。

本次只完成宏观审查，未进入上述任何单页设计，也未修改已确认业务结论。
