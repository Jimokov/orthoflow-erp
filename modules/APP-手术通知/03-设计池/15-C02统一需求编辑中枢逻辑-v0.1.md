# C02 统一需求编辑中枢逻辑 v0.1

> 状态：主体逻辑已确认，产品与器械组配细节暂缓
> 更新日期：2026-08-18
> 范围：只定义C02单页逻辑；不制作低保真，不展开C03、C09、C10、C11内部结构

## 1. 页面身份

C02是同一笔未提交需求的编辑中枢，用来汇总本次手术信息、当前已有需求组，并分流到C03进行局部编辑或进入C09核对并提交。原C01手术基本信息已经融入本页，不恢复独立页面。

C02承接五类订单草稿来源和一类模板候选编辑上下文，但这些只是同一编辑能力接收的不同来源与权限，不拆成六张页面，也不复制六套结构。

## 2. 已确认的来源提示

来源信息只在确实影响当前身份、可编辑边界或提交结果时显示。提示位于页面标题下方，采用紧凑说明，不做大面积提示卡，不压过实际编辑内容。

| 来源上下文 | 页面标题／来源说明 | 既有编辑边界 |
|---|---|---|
| 空白新建 | 标题“编辑手术通知”，不显示来源说明 | 从空白填写本次手术信息与需求 |
| 从模板创建订单 | 标题“编辑手术通知”；显示“来自模板：模板名称” | 模板内容只作为本次草稿起点，允许继续调整并填写本次手术信息 |
| 复制需求新建 | 标题“编辑手术通知”；显示“复制自订单：订单号”，并说明“新手术，需重新填写手术时间” | 可带入医院、科室、术者并允许修改；日期与准确时间必须重填；具体在手实物不复制 |
| 撤回修改 | 标题“编辑手术通知”；显示“修改订单：订单号”，并说明“重新提交后沿用原订单” | 恢复原提交内容，按当前权限修改并形成同一业务身份的新提交版本 |
| 补充需求 | 标题“编辑手术通知”；显示“补充订单：订单号”，并说明“手术信息继承原单且不可修改” | 手术场景只读，只新增需求，不覆盖原订单已生效内容 |
| 模板候选 | 标题切换为“编辑需求模板”；显示模板名称、可选适用信息和固定要求，不显示具体手术日期与时间 | 不生成订单草稿、不进入C10，完成后进入模板审核而不是C09订单提交 |

## 3. 主体分区

C02不是固定步骤向导，而是一张可以反复进入和修改的编辑总览。页面从上到下固定为：

1. **条件性来源说明**：只在第2节规定的来源下显示；
2. **本次手术信息／模板信息**：订单来源集中承载医院、科室、术者、手术日期和准确时间；模板候选改为模板名称、可选适用医院／科室／术者和可选固定要求，不显示具体手术日期与时间；
3. **产品与器械需求**：只展示当前已经加入的需求组摘要，点击后进入C03编辑；不在C02摊开规格选择、器械包组成和非目录条件表单；
4. **添加基座**：需求区末端始终保留“添加产品”和“添加器械”，即使复制或模板内容被整组移除也不能消失；
5. **底部主操作**：订单草稿显示“下一步：核对并提交”并进入C09；模板候选显示“提交审核”，不进入C09。

C02不显示步骤条、完成百分比，也不强迫业务员按固定顺序编辑手术信息和需求组。业务员可以多次往返C03；点击底部主操作时，再集中指出当前尚未完成的部分。

因此C02始终只回答两个主要问题：“这台手术是什么”“目前已经要了什么”。

### 3.1 本次手术信息

“本次手术信息”直接在C02内展开，不再进入另一张页面。区域固定承载医院、科室、术者、手术日期和准确时间五项：

| 来源上下文 | 区域表现 |
|---|---|
| 空白新建、从模板创建订单、撤回修改 | 五项直接在本区编辑 |
| 复制需求新建 | 医院、科室和术者可以带入并修改；手术日期与准确时间留空且必须重新填写 |
| 补充需求 | 五项完整展示但整体只读，用于确认补充的是哪台手术 |
| 模板候选 | 不显示本次手术日期与时间；将本区替换为“模板信息”，模板名称必填，适用医院／科室／术者和固定要求可选 |

“固定要求”只在模板候选态编辑，保存可跨多次手术复用的稳定要求；它不是个人备注。使用模板创建具体订单时，固定要求进入C09“整单额外要求”供本次重新核对，不在普通订单C02重复编辑。

C02只使用系统当前已经提供的基础资料选择能力，不在本页增加医院、科室或术者的新建、维护和绑定功能。缺失项不持续制造红色警告；业务员点击“下一步：核对并提交”时，再集中提示尚未完成的必填内容。

### 3.2 复制或模板带入的失效基础资料

- 医院、科室或术者停用、删除或无法映射时，原始名称继续显示，并使用一次“资料需核对”标识；
- 当前资料库存在适用项时，业务员在原位置重新选择并完成匹配；
- 当前资料库仍无适用项时，业务员可以保留来源原文并选择“请公司确认”，随后继续进入C09；
- 待确认项不能显示成已匹配成功，C09必须继续明确呈现；
- 该入口只处理复制订单或模板带入的既有资料，空白新建不能借此任意填写医院、科室和术者；
- C02不设计公司内部如何确认、新建或绑定资料，只形成明确的APP输出。

### 3.3 产品与器械需求摘要

C02只展示足以回答“目前已经要了什么”的组摘要：

- 产品需求组显示产品名称、规格与数量摘要，以及有关联时已经采用的配套器械包名称或数量；关联器械只是跟随摘要，仍是可独立编辑和移除的器械需求组；
- 器械需求组显示器械或器械包名称和申请数量；有关联产品时使用低强调的来源说明，无关联时不制造空占位；
- 非目录内容保留原始名称，并按当前情况显示低强调的“非目录”或“资料待核对”标识；
- 不显示器械包完整组成、库存数量、仓库来源或后台处理状态；
- 整张需求组卡片点击进入C03编辑。

每张卡片提供明确但低强调的“移除”操作。点击后直接从本草稿移除该组，并提供短暂“撤销”，不连续弹出确认框；撤销窗口结束后再按自动保存规则固化。整组移除后，对应的“添加产品”或“添加器械”基座继续保留。

不同来源只改变摘要内容，不改变卡片结构：

- 补充需求只显示本次准备补充的新需求组，不复制或开放原订单已有需求；
- 撤回修改恢复原提交内容并允许修改；
- 复制和模板创建显示各自带入的需求组；
- 模板候选显示候选模板当前包含的需求组。

### 3.4 只有正式补充要求的补充单

补充来源允许在没有新增产品或器械组时进入C09。此时：

- C02不以“产品和器械同时为空”为由阻止进入C09；
- C09将对应字段显示为“本次补充要求”，且必须填写后才能正式提交；
- 提交后仍形成具有独立编号、受理结果和记录的接续订单；
- 该内容必须与本次手术履约直接相关，不是普通备注或主动聊天；
- 医院、科室、术者、手术时间、需求减少、停止剩余和取消等正式变化仍进入T05，不能写进补充要求绕过规则。

除该补充来源例外外，普通订单草稿和模板候选仍至少需要一个产品需求组或器械需求组。模板候选还必须填写模板名称；适用医院、科室、术者和固定要求不作为必填条件。

### 3.5 进入下一层前的结构性校验

C02只判断当前内容是否具备进入核对／审核层的基本结构，不替代C09完整核对。

订单草稿点击“下一步：核对并提交”时检查：

- 医院、科室、术者、手术日期和准确时间是否齐全；补充来源读取原订单只读信息，不要求重填；
- 除第3.4节补充空组例外外，是否至少有一个产品需求组或器械需求组；
- 每个需求组是否已经从C03返回“编辑完整”结果；C02只读取组级结果，不复制C03逐字段校验；
- 失效基础资料是否已经重新匹配，或明确选择“请公司确认”；
- 补充、撤回等订单来源的当前状态和本人权限是否仍允许继续。

模板候选点击“提交审核”时不检查手术信息，但至少需要一个已经编辑完整的产品或器械需求组。

底部主操作保持可点击，不使用无解释的灰色禁用。校验失败时：

1. 停留在C02；
2. 顶部只显示一次“还有N项未完成”；
3. 对应区域使用轻量标记；
4. 自动定位到第一项未完成内容；
5. 平时编辑过程中不持续铺满红色警告。

结构校验通过后先完成本机持久保存，再进入C09或提交模板审核。C09继续负责全量内容核对、疑似重复提示、整单额外要求／本次补充要求、最终权限与版本校验及正式提交；即使C02已通过，事实变化时C09仍可重新拦截。

### 3.6 自动保存与离线退出

C02将“内容不丢失”和“已经同步到公司端”分开处理：

- **本机持久保存**：产生实际输入并成功保存在本机后，即形成可见草稿；业务员可以安全退出，并能从C00或C10恢复；
- **公司端同步**：在有网络时自动进行，不影响草稿在本机的形成和继续编辑；尚未同步的草稿使用低强调的“待同步”标识；
- **排序依据**：C00和C10按内容最后一次成功保存在本机的编辑时间排序；网络恢复后的同步时间不改变草稿次序；
- **正常反馈**：自动保存只在原位短暂显示“保存中”“已保存”，成功后自行消失，不反复弹出通知；
- **同步失败**：显示持续但紧凑的“暂未同步，内容已保存在本机”，并提供重试；不把同步失败误报为内容丢失；
- **本机保存失败**：不能静默退出；退出前明确告知内容可能丢失，并提供重试或确认不保存退出；
- **离线编辑**：允许继续编辑、保存和退出；需要公司端校验或形成正式业务结果的提交动作必须联网，离线时保留内容并提示联网后继续。

模板候选同样继承本机保存与公司端同步边界，但仍归C11管理，不因本机保存而进入C10订单草稿集合。

模板候选从空白进入时，仅打开C02不形成可见记录；产生实际输入并成功保存在本机后，才进入C11“未完成”。基于现有模板或订单成功提示进入时，以带入内容首次本机持久保存成功作为候选形成点。候选正式提交必须联网并防止重复提交；失败时保留当前内容。

模板候选点击“提交公司审核”并通过校验后，只做一次轻量后果确认，随后直接形成模板申请，不进入C09。成功不新增页面：C11来源返回C11并更新为“审核中”，O01一次性提示来源返回原O01；退回修改和重新提交沿用同一申请身份。

## 4. 展示原则

- 来源说明不是订单状态、待办或业务记录，不增加状态卡片；
- 空白新建没有需要解释的来源，不显示空占位；
- “从模板创建订单”和“编辑模板候选”是两种不同上下文，不能因都涉及模板而混用标题或提交结果；
- 来源提示只解释当前身份与关键后果，不展开来源订单明细、历史记录或模板审核过程；
- 进入C02及正式提交前仍按现行规则校验权限和版本，来源文字不能替代校验。

## 5. 继续继承的边界

- C02只汇总需求组和承载手术信息，不把产品规格、推荐器械、独立器械和非目录条件表单全部摊开；这些局部编辑进入C03；
- 具体订单的整单额外要求位于C09，不在订单态C02重复填写；模板候选态的“固定要求”属于模板正式内容，在C02模板信息区编辑；
- 订单草稿完成后进入C09核对并提交；模板候选不进入C09；
- C02、C03、C09均不显示全局底部导航；
- 中途退出按C00已经确认的来源返回矩阵处理；有实际输入时先完成本机持久保存，公司端同步可以随后进行。

## 6. 阶段性收束与回补口

| 检查项 | 结论 |
|---|---|
| 页面身份 | C02只承载手术信息、需求组总览和局部编辑分流，不恢复线性向导 |
| 来源上下文 | 五类订单草稿与模板候选共用同一编辑能力，提示和权限边界明确 |
| 主体结构 | 手术信息、需求摘要、添加基座和底部主操作的职责已经闭合；需求摘要最终组配形态待回补 |
| 补充例外 | 只有正式补充要求时可以进入C09，且不能绕过T05或T01 |
| 校验分工 | C02负责结构完整，C09负责正式核对与提交成立 |
| 保存退出 | 本机保存、公司端同步、排序、离线编辑及失败处理已经闭合 |
| 页面边界 | C03、C09、C10、C11及Web内部能力均未提前展开 |

已确认并继续有效的部分包括：页面身份、六类来源上下文、主体分区、手术信息、补充空组例外、C02／C09校验分工、自动保存与离线退出，以及产品组／器械组“视觉关联、业务独立”的原则。

以下内容统一留待“产品与器械组配方案”形成后回补，不在本轮自行推演：

- C02需求摘要卡最终按怎样的产品组、器械组及关联层级呈现；
- 同一器械服务一个或多个产品时的合并、去重和摘要表达；
- 产品规格数量、单位和器械组配结果在C02显示到什么粒度；
- 关联器械移除、产品移除及复制需求时的最终联动提示。

检查结论：C02主体逻辑可以阶段性收束，上述回补口不影响C09讨论“核对什么、怎样正式提交”，但在组配方案确认前不得制作C02最终低保真、视觉稿或代码，也不得把摘要形态解释为最终定稿。
