# O01订单详情页面结构 v0.3

> 状态：结构与低保真均已确认；O01设计当前有效  
> 确认日期：2026-08-14  
> 页面：业务员移动端 APP 的 O01“订单详情”  
> 替代：[O01订单详情页面结构 v0.2](../06-决策与历史池/2026-08-14-O01订单详情页面结构-v0.2.md)  
> 不包含：视觉风格、代码、Web后台、库存、手术植入、T／S页面内部设计

## 1. 本版结论

O01不再以“当前关键结果、订单进展、需求入口、供货入口”组成一组并列卡片，而是按业务员理解一笔订单的自然顺序组织：

```text
0. 待我处理（有任务时出现）
1. 订单编号
2. 主要基本信息＋当前主状态
3. 订单内容
   3.1 主订单
   3.2 接续订单（存在补充单时出现）
4. 发货与接收
   4.1 整单交付
   或
   4.2 分批交付
5. 当前可执行操作
6. 订单记录入口
```

页面采用单列纵向滚动。一个事实只在与其业务对象对应的位置出现一次，不在页面顶部、批次摘要和清单区重复表述。

新主订单首次提交成功并直接进入O01时，可以在页面顶部显示一次紧凑的“订单已提交／创建需求模板”反馈。它不是新的固定业务区，不计入0—6结构，不进入待我处理，也不压过真实任务；关闭或离开后消失。补充订单和撤回重提不显示，O01不因此恢复永久“保存为模板”入口。

## 3. 两个必须分开的业务维度

### 3.1 订单构成

订单构成回答“这台手术当前提出了什么需求”：

- 主订单是首次正式提交形成的原始手术通知；
- 受理后新增需求形成补充单；
- O01用户端将全部补充单统一分组为“接续订单”；
- “接续订单”只是页面分组名称，不替代补充单的独立编号、来源、版本、受理、履约和审计身份；
- 当前有效需求由主订单和已经生效的接续订单共同组成，但页面仍保留各自来源，不能把补充内容覆盖回主订单。

### 3.2 实物交付

实物交付回答“公司实际发了什么、业务员是否收到”：

- 正式发货批次、出货清单、照片和本人接收事实属于发货与接收维度；
- 一个批次可以包含主订单和一张或多张接续订单中的物品；
- 同一实际交付还可以关联当前业务员的多张订单；
- 因此批次不固定嵌套在主订单或某张接续订单下，而是在“发货与接收”中只出现一次；
- 批次清单的具体明细可以标明来源主订单或哪张接续订单，但不能复制整张批次。

## 4. 0区：待我处理

### 4.1 位置

- 页面导航标题之后、正式订单内容之前；
- 有任务时是页面内容层第一项；
- 没有任务时整个区域隐藏，不显示空卡片或“暂无待办”。

### 4.2 订单语境

待办虽然位于订单编号之前，但必须自带最小订单语境，例如医院和手术时间，防止从G03或系统深链进入后在未识别对象时直接操作。

### 4.3 0／1／多项

| 当前本人任务数 | O01表达 |
|---|---|
| 0 | 隐藏整个区域 |
| 1 | 完整显示任务标题、必要影响、最小订单语境和明确动作按钮 |
| 多项 | 完整显示最高优先级任务，并显示“另有N项待处理”；汇总入口进入G03并限定当前订单 |

任务按钮使用真实动作名称。任务完成、失效或只等待公司后立即退出本区，不在批次或页面底部复制第二个高强调按钮。

### 4.4 手术情况确认任务

- 计划手术时间已过且尚无有效植入、已生效延期或已生效取消时，O01直接显示同一条手术情况确认任务；
- 任务组件直接提供“记录手术植入、手术延期、手术取消”，不再进入独立T04页面；
- 记录手术植入进入同一台手术对应的植入记录，延期或取消进入T05；
- 进入植入记录不等于任务完成，只有正式植入结果返回后任务才退出。

## 5. 1—2区：订单身份、基本信息与状态

### 5.1 订单编号

- 页面名称统一为“订单详情”；
- 原手术通知编号是O01稳定主身份；
- 补充单编号不与原订单号并列充当页面主身份；
- O01始终聚合同一手术需求组的主订单和全部接续订单。

### 5.2 主要基本信息

固定展示：

- 医院；
- 科室；
- 术者；
- 当前有效计划手术日期和准确时间。

医院与手术时间承担快速识别，科室和术者作为必要补充。患者、住院号和手术植入内部信息不进入本区。

### 5.3 当前主状态

- 同时只显示八种主状态中的一个；
- 主状态与基本信息合并为订单概览，不再另建“当前关键结果”卡片；
- 确需解释时，在状态下方显示一条与当前事实直接相关的状态说明；
- 状态说明不得重复批次数量、出货清单或任务动作。

状态说明示例只表达差异：

| 主状态 | 可表达的差异 |
|---|---|
| 待受理 | 当前等待受理的是主订单还是某张接续订单、建立来源 |
| 处理中 | 哪部分订单内容仍在公司处理，或只等待公司回复 |
| 待发货 | 当前供货结果已形成及预计到手时间 |
| 已发货 | 仍有待发内容时说明“尚有部分待发”；全部发出时不再重复批次数量 |
| 发起追回 | 哪个交付事实正在追回，以及当前只需等待公司还是另有本人任务 |
| 待结余 | 当前仍未闭环的本人实物责任摘要 |
| 已完成 | 完成时间和最终结果摘要 |
| 已取消 | 取消时间、原因和是否曾发生实物流的结果摘要 |

## 6. 3区：订单内容

订单内容紧跟身份与基本信息，直接回答“这笔订单是什么”。

### 6.1 主订单

主订单固定出现，展示：

- 当前有效的产品、器械包、非目录需求和整单要求摘要；
- 适量明细；
- 长清单默认收敛，通过“展开完整清单”在O01内继续查看；
- 原始版本、生效变更和更正通过来源标识与O04记录保持可追溯，但不在O01堆叠完整版本时间线。

### 6.2 接续订单

只有存在补充单时出现，按发生顺序展示。每张接续订单至少表达：

- 补充单编号；
- 发起来源：业务员本人或公司代建；
- 提交或建立时间；
- 当前单据结果或待确认状态；
- 本次新增的产品、器械和其他需求摘要；
- 适用时提供修改当前补充单、确认补充单或提出异议的对应任务／操作，但不改写主订单。

单张补充单取消只在对应接续订单中表达，不把整个O01改为已取消。

### 6.3 O02处理

原O02“需求明细”的核心职责已经融入本区：

- O02退出当前正式页面集合；
- O01直接展示主订单和接续订单内容；
- 普通长清单优先在O01原地展开，不因内容稍长就跳转；
- 不再设置每笔订单固定的“需求明细”跳转行。

## 7. 4区：发货与接收

### 7.1 渐进出现

- 尚无确认供货或发货事实时不显示空区域；
- 形成供货结果但尚未发货时，显示公司确认提供的内容和预计到手时间；
- 发生正式发货后，显示实际出货、照片、到手和本人接收事实；
- 公司内部采购、借入、调拨、仓库和人员作业不展示。

### 7.2 整单交付

只有一次正式发货且本次覆盖当前全部待交付内容时，使用“整单发出／整单交付”表达：

- 不显示“第1批”；
- 直接展示发货时间、出货照片、出货清单、预计或实际到手、物流／线下交接结果和本人接收状态；
- 不在区域顶部额外重复“已发1批”。

### 7.3 分批交付

存在多次发货或仍有待发内容时，按批次纵向展示：

- 每个正式发货批次只出现一次；
- 批次头部展示时间和接收状态；
- 批次内部展示照片、结构化出货清单、预计或实际到手和本人接收事实；
- 清单明细可标记来自主订单或具体接续订单；
- 尚未发出的内容单独以“仍待发”表达，不伪装成新批次；
- 不使用横向滑动承载主要照片或批次信息。

### 7.4 T02与批次轻量详情

- 待本人确认的实际交付形成页面顶部同一条T02任务；
- 对应批次只显示“待确认接收”等状态，不复制第二个高强调按钮；
- 简单整单和普通分批直接在O01完成查看；
- 跨订单关联由T02按一次真实交付批次统一处理；
- 清单、照片或证据较多时，从O01具体批次打开轻量只读详情，不建立O03独立页面；
- 关闭批次详情时恢复O01原批次位置。

### 7.5 本单物品结果与分流

- O01是订单生成后的唯一总承载页面，不另建第二张订单流向总览；
- 正式植入结果及后续物品去向继续汇总在本区，O01至少回答“当前是什么结果、是否需要本人处理、从哪里进入处理”；
- 前台顶层结果文案统一为“等待手术结果、已植入、已入库、已转用、异常处理中、需要还回／还回中／已还回”；其中“已入库”表示转入本人自有库已经正式生效，规则层仍可使用“转入个人仓”描述该业务动作；
- 本单物品继续沿用原整单／交付批次／出货清单结构，不按后续结果重新生成“已植入清单、已入库清单、已转用清单”等第二套物品列表；
- 每条原交付明细在自身位置叠加当前结果和数量，业务员沿着“公司实际交付了什么”即可继续看到“后来去了哪里”；顶部结果数量只能用于快速概览和定位，不能复制明细；
- 同一产品明细按数量形成多个结果时，在原明细内紧凑展示各结果数量，展开后查看具体批次、数量或实物；器械包按具体包编号逐包展示结果，不能只用件数汇总；
- 操作入口集中放在本单物品区末端，按当前符合条件的对象显示“办理还回（N件）／申请入库（N件）／申请转用（N件）／申报异常”，不在每条明细后重复堆叠同一组按钮；
- 点击集中操作后再选择当前符合条件的具体物品；从某条明细进入同一办理流程时可以预选该物品，但必须重新校验当前资格；
- 复杂交付继续在O01具体批次渐进展开，不为查看复杂度另建正式页面；复杂填写进入对应正式动作载体，完成结果必须回写O01。

## 8. 5区：当前可执行操作

### 8.1 位置与承载

- 位于订单内容与发货接收摘要之后；
- 长清单默认收敛，避免常规操作被大量明细埋没；
- 不使用吸底操作栏；
- 没有合法操作时整个区域隐藏；
- 任务动作的优先级始终高于主动发起操作。

### 8.2 操作矩阵

| 主状态与条件 | 可显示操作 |
|---|---|
| 待受理；本人提交且原单本身尚未受理 | 修改订单、取消订单 |
| 待受理；只有本人提交的补充单待受理 | 修改当前补充单；适用时显示变更取消 |
| 公司代建原单或补充单待本人确认 | 不显示修改／取消；确认或异议由顶部任务承载 |
| 处理中 | 补充需求、变更取消 |
| 待发货 | 补充需求、变更取消 |
| 已发货 | 补充需求、变更取消 |
| 发起追回 | 底层事实仍允许时显示补充需求、变更取消；不显示追回按钮 |
| 待结余 | 不显示补充需求、变更取消；本单物品区展示结果和集中操作；还回进入S01，入库／转用和在手异常使用O01相应轻量组件 |
| 已完成 | 复制需求新建 |
| 已取消 | 复制需求新建 |

危险后果在目标流程中明确说明。本区入口不直接用危险色替代文字语义。

“复制需求新建”是跨状态低强调便利操作：当前或历史O01存在可复用正式需求快照时均可显示。点击后为另一台手术创建新草稿，进入C02统一需求编辑中枢重填手术时间并分组核对需求，再由C09提交；它不形成来源订单补充单，也不复制或自动转移具体实物。

### 8.3 计划时间前的植入入口

- G01继续保留手术植入模块入口；
- 在订单仍可关联该台手术且尚无正式结果时，O01可以在计划手术时间到达前提供低强调的条件性“记录手术植入”入口，并携带当前订单、候选实物和返回上下文；
- 到达计划手术时间仍无结果时，该入口升级为顶部手术情况确认任务，不在本区重复显示；
- 正式植入结果回写O01并在本单物品区只读展示；同一区域继续汇总已入库、已转用、异常、还回和仍在手结果。需要本人正式动作时再进入对应办理流程。该修正不改变O01固定骨架，具体低保真在O／T／S打通后统一同步。

## 9. 6区：订单记录

- O04“订单记录”继续保留，承载与业务员有关的完整正式事实；
- 入口位于页面末端或次级菜单，当前订单中保持低强调；
- 文案统一为“查看订单记录”，不使用容易与发货清单混淆的“全部记录”；
- 已完成或已取消时可以提高可见性，但仍不取代最终结果；
- O01不再展示独立订单进展、最近进展或小型时间线；
- 发货、交付和接收事实回到对应整单或批次，主订单和补充单事实回到订单内容，其他历史进入O04。

## 10. 八状态区域可见性

| 主状态 | 顶部任务 | 订单身份与状态 | 订单内容 | 发货与接收 | 主动操作 | 订单记录 |
|---|---|---|---|---|---|---|
| 待受理 | 按事实 | 必显 | 必显 | 按事实 | 按来源和对象 | 低强调 |
| 处理中 | 按事实 | 必显 | 必显 | 按事实 | 补充需求、变更取消 | 低强调 |
| 待发货 | 按事实 | 必显 | 必显 | 显示供货结果 | 补充需求、变更取消 | 低强调 |
| 已发货 | 按事实 | 必显 | 必显 | 整单或分批 | 补充需求、变更取消 | 低强调 |
| 发起追回 | 其他任务按事实 | 必显 | 必显 | 显示受影响交付事实 | 无追回操作；其他按权限 | 低强调 |
| 待结余 | 按本人责任 | 必显 | 必显 | 已接收事实只读 | 无补充／变更；S入口按事实 | 低强调 |
| 已完成 | 隐藏 | 必显 | 只读 | 只读 | 复制需求新建 | 明确入口 |
| 已取消 | 隐藏 | 必显 | 只读并显示单据结果 | 按历史事实只读 | 复制需求新建 | 明确入口 |

表中当前订单各状态的“主动操作”只列状态专属动作；满足正式需求快照条件时，另可显示低强调“复制需求新建”。

## 11. 页面加载、返回与并发

### 11.1 来源感知返回

- 从G02返回原订单集合、筛选和滚动位置；
- 从G03、G01或系统深链进入时，完成动作后返回原来源；无来源深链默认回O01；
- 从O01进入T、S或O04后，返回时恢复原订单、展开区域和滚动位置；关闭O01批次轻量详情时恢复原批次位置；
- 任务、状态、权限和批次事实返回后重新计算，不保留已失效按钮。

### 11.2 加载与失败

- 先建立稳定骨架，再加载任务、订单构成、交付和权限；
- 区域加载失败不能伪装成空数据；
- 整页失败提供重试和返回；局部失败只影响对应区域并允许重试；
- 已成功提交的动作不能因刷新失败而被重复提交。

### 11.3 并发变化

采用“先成功的正式动作生效”。点击操作后若状态、对象版本或任务已变化：

1. 阻止旧版本继续提交；
2. 刷新O01；
3. 说明事项已经变化；
4. 失效事实进入O04记录，不继续占据顶部任务。
