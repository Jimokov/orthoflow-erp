# O04订单记录逻辑 v0.1

> 状态：单页逻辑已确认；低保真留待全流程逻辑验收后统一推进
> 建立日期：2026-08-19
> 范围：只讨论业务员移动端O04订单记录的业务身份、记录范围、进入返回及只读关系；不制作低保真，不定义Web后台日志或内部操作。

## 1. 已确认的页面业务身份

O04与来源O01一一对应，绑定O01所代表的同一台手术需求组，而不是只绑定其中一张主订单、接续订单或交付批次。

- 主订单及其全部接续订单共同进入同一O04正式记录；
- 每条记录保留自身业务对象身份，明确属于主订单、哪张接续订单、哪个交付批次或哪个正式事项；
- O04不把这些对象重新合并成无法追溯的一条笼统订单历史；
- “复制需求新建”形成新的订单身份、新的O01和新的O04，不并入来源订单记录；
- 同一真实交付批次关联本人多张订单时，当前O04只记录该批次对本手术需求组产生的正式影响，并保留批次引用，不复制其他订单历史。

## 2. 已继承边界

- O01展示当前有效事实，O04保存正式历史演进；
- O04从O01末端“查看订单记录”进入，返回时恢复来源O01原位置；
- 已结束、撤回或替代的T01事项从O04进入只读上下文；
- O04不复制自由聊天全文、后台内部操作日志或不影响业务员结果的系统噪声；
- O04不提供改变当前订单的正式动作。

## 3. 已确认的记录范围

### 3.1 已确认的记录准入原则

O04只记录导致订单事实、业务版本、本人责任或最终结果发生正式变化的事件，不把普通过程、提醒、系统动作或派生主状态写成独立记录。

- 八种订单主状态由底层正式事实推导，不另行生成“状态变为某状态”的重复记录；
- 正式申请或异常事项记录“本人正式提交”和“公司形成正式结果”两个关键节点；
- 两个节点之间只有等待、运输、审批或处理进度时，不逐条形成订单记录；
- 照片、清单和凭证附着在对应的发货、接收、异常或还回事件上，不独立生成时间事件。

### 3.2 必须进入的正式事件

| 类型 | 正式事件 |
|---|---|
| 订单形成与版本 | 首次提交、公司代建及本人确认、撤回、重新提交、正式受理、版本替代和影响业务员结果的正式更正 |
| 主订单与接续订单 | 补充单建立、提交、生效、撤回和取消，并保留具体接续订单身份 |
| 正式协同与申请 | T01结构化决定及事项结束／撤回／替代；T05变更、延期、取消申请及正式结果 |
| 发货与接收 | 正式发货批次形成、发起追回及结果、T02接收确认、T03异常申报及正式处理结果 |
| 手术与物品结果 | 正式植入结果、手术延期／取消生效、申请入库、申请转用、在手异常、借单还回及各自正式结果 |
| 终局和纠正 | 订单完成、取消、重新打开，以及会改变原结论的正式更正 |

### 3.3 不形成独立记录

- 派生的订单主状态变化；
- 本人任务的创建、排序、已读和退出；
- 首页提醒、系统推送和角标；
- 普通聊天、图片消息和附件发送；
- 物流的每个运输节点和预计时间反复变化；
- 页面打开、查看、刷新和返回；
- 草稿保存、填写一半和提交失败；
- 公司内部采购、调拨、配货、仓库和审批操作；
- 不影响业务员订单结果的后台修正或系统同步。

## 4. 已确认的单条信息

### 4.1 已确认的单条最小信息

一条记录固定回答三个问题：什么时候发生、属于哪个业务对象、形成了什么正式结果。

1. **发生时间**：使用正式事件被系统接受或结果生效的时间，不使用消息发送、页面操作或普通过程时间；
2. **所属对象**：使用整张订单、主订单、具体接续订单、具体交付批次或具体正式事项等简短身份；页面已经继承来源O01，不在每条记录重复主订单号；
3. **正式结果句**：用一句话表达“谁做了什么并形成什么结果”；“本人／公司”写入结果句，不额外占用固定字段，也不默认展示后台具体人员姓名。

以下信息只在确有业务意义时出现：

- 变化摘要，例如新增产品数量或手术时间变化；
- 责任影响，例如正常接收、未收到或异常在手数量；
- 照片、清单和凭证等附件摘要；
- 进入对应T／S原业务上下文的“查看详情”；
- 更正、撤销或替代与原记录的关系。

以下内容不在单条记录中重复：医院、科室、术者、当前主状态、完整需求或交付清单、当前操作按钮、技术记录ID、任务ID和后台账号。

## 5. 已确认的整体组织

### 5.1 已确认的整体组织

- O04使用一条按正式生效时间倒序排列的完整时间线，最新事件在前；
- 同一天记录可以自然归组，但不按八种主状态或订单／交付／手术／物品类别拆成固定页签；
- 已完成或已取消订单进入O04时先看到终局事件，再向下追溯原因与过程；
- 简单订单不显示筛选工具；只有存在多个接续订单、交付批次或较多正式事项时，才提供低干扰的对象定位；
- 对象定位可以限定主订单、具体接续订单、具体交付批次或具体正式事项；从记录对象标签可以直接定位同一对象的全部记录；
- 定位状态必须明确当前对象并允许一键恢复全部记录；
- 不提供关键词搜索、多条件组合筛选、按主状态筛选、按后台人员筛选或常驻分类标签。

## 6. 已确认的历史详情关系

### 6.1 已确认的历史详情只读原则

- O04单条记录必须先做到脱离原页面也能读懂；“查看详情”只用于核验当时提交的正式内容、证据、清单或业务版本；
- 查看详情进入事件发生时的历史快照，不读取当前可编辑内容，不提供改变订单的动作；
- 从详情返回时恢复O04原时间位置和对象定位；原业务载体暂不可用时，O04本身仍须保留可读的正式结果；
- 历史详情不能重新制造本人责任。当前出现新的本人责任时，必须依据当前事实重新生成任务，并回到O01／G03等当前入口；不得从O04恢复旧按钮或旧任务。

### 6.2 各类记录的只读进入关系

| 记录来源 | O04中的详情关系 |
|---|---|
| T01订单协同 | 进入对应事项的历史快照；结束、撤回或被替代后完全只读。唯一例外是事项已经回复且仍“等待公司”时，可以从原记录回到同一事项补充遗漏资料，但不得新开事项、恢复本人任务或修改已经提交的正式决定 |
| T02实际交付确认 | 查看当次真实交付批次的确认快照；一个批次关联本人多张订单时保留原批次整体上下文，同时突出当前O01所属部分，不重新提供确认动作 |
| T03收货异常 | 查看当时提交的异常明细、数量、说明和证据快照，不重新进入可申报状态 |
| T05变更与取消申请 | 查看该次正式申请版本及其处理结果，不重新提供申请或修改动作 |
| S01借单还回 | 查看对应还回批次的发起、受理、撤回、本人动作、问题处理及正式结果；具体后台安排字段继续受S01桩子约束，历史入口始终只读 |
| O01入库／转用／在手异常组件 | 在O04内展开对应正式申请、证据和结果快照，不重新打开O01可执行组件 |
| 提交、撤回、重提和版本更正 | 查看事件发生时的正式版本快照，不进入C02或C09编辑流程 |
| 手术植入结果 | 当前只保留正式结果摘要；是否进入手术植入记录，等待手术植入模块确认跨模块接口，不在O04内推演 |

## 7. 已确认的终局连续性

O04采用“终局不覆盖，重新打开后续接同一订单时间线”的原则：

- 已完成、已取消均是不可覆盖、不可删除的正式历史节点，保留当时生效时间和业务快照；
- 重新打开不创建新订单，不改变原订单号、手术需求组、O01或O04身份；它形成一条新的正式记录，说明重新打开的原因和结果；
- 原终局节点只增加“后续已重新打开”的关系标识，不改写为当前状态；O01依据重新打开后的当前有效事实重算主状态，O04继续保留此前完整过程；
- 订单再次完成或取消时，再增加新的终局节点。多次终局与重新打开按发生顺序保留在同一条倒序时间线，不拆成多张订单或多个历史页签；
- 单张接续订单取消是该接续订单的局部正式事件，不构成整个手术需求组的终局；
- 不产生新需求、实物流、数量差异或本人责任的历史更正，只增加与被更正记录相互关联的正式更正事件，原终局和当前归类不变；
- 更正重新产生有效需求、实物流、数量差异或本人责任时，必须先形成正式重新打开结果并重算主状态，之后才能依据当前事实生成本人任务；历史订单不能直接挂载任务；
- 手术取消已经生效但仍有已发、已接收或其他实物责任时，只记录“手术取消已生效”，订单继续按当前实物流和责任处理；责任闭环后再形成“订单已完成（手术已取消）”，不得提前把整张订单写成“已取消”。

倒序时间线的表达规则：

1. 当前仍处于终局时，最新的完成或取消事件位于顶部；
2. 当前已经重新打开时，重新打开及其后的正式事件位于顶部，较早终局节点保留“后续已重新打开”关系；
3. 再次终局时，新的终局事件位于顶部，较早生命周期段继续向下可追溯；
4. O04不为派生主状态重复生成状态变化事件，生命周期段由完成、取消、重新打开及其底层正式事实自然构成。

## 8. 单页收口结论

O04已经具备稳定页面身份、入口返回、正式记录准入、单条最小信息、倒序时间线、按需对象定位、历史详情只读关系及终局连续性。它只回答“这张订单怎样走到现在”，不复制O01当前事实，不恢复历史任务，也不承担Web后台操作日志。

单页逻辑讨论至此收口。当前不制作O04低保真；O组结束全面筛查与远程同步已经完成，后续推进位置只以模块首页、当前设计进度和页面设计总控为准。
