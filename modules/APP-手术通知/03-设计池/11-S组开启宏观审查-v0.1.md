# S组开启宏观审查 v0.1

> 状态：宏观方案已确认
> 审查日期：2026-08-16
> 确认日期：2026-08-16
> 范围：只审查S组整体职责、与现行O／T及跨模块结果的交集，以及原S01—S05的保留、融合、修改或删除；不进入单页结构、低保真、视觉、代码、Web后台、库存或手术植入内部设计。

## 1. 继承的现行事实

- S组只处理业务员已经确认接收、仍绑定当前订单且责任尚未解除的具体实物；
- 只有手术已形成有效植入结果或取消已经生效，并且仍有实物责任未闭环时，订单才进入待结余；
- 实际植入结果由手术植入模块形成并回写，不在S组重新确认；
- 转入个人仓、转到本人其他订单、还回和异常处置只有在正式结果形成后才解除或改变当前订单责任；
- 业务员完成本人动作、只等待审批、运输、公司清点或异常处置时退出“待我处理”，但责任仍可能阻塞订单完成；
- 业务员没有“完成订单”按钮，系统判断完成资格后仍由公司最终确认；
- 发生过实物流的订单即使手术取消，也必须先完成实物责任闭环，最终为“已完成＋手术已取消”。

## 2. 经全局复盘后的S组宏观身份

S组不是一套独立于订单详情的“实物责任总览”。O01已经承载订单交付物、实际接收、植入、入库、转用、还回、异常和仍在手结果；相关物品仍需处理时继续由O01回答：

1. 本单还有哪些已接收实物尚未闭环；
2. 每件实物已经形成什么结果或正在等待什么；
3. 当前是否存在需要本人执行的处理动作。

S组只保留O01无法用摘要、状态和轻量入口清楚承载的正式动作页面。其输入是O01中的具体在手实物及当前动作上下文，输出分别回写原订单、实物责任和O04正式记录，不建立第二套总览或独立订单。

## 3. 与现行页面和模块的宏观交集

| 关联对象 | 当前承载关系 | 明确边界 |
|---|---|---|
| O01订单详情 | 直接展示未闭环实物责任总览、只读结果、普通等待进度和适用动作入口；入库／转用与在手异常使用页内轻量组件 | 不在O01展开跨订单还回批次、公司有效安排下的本人动作和还回问题处理上下文 |
| G03待我处理 | 引用同一条本人任务；已知具体动作时可直达独立载体或回到O01相应组件，否则进入O01未闭环实物位置 | 等待公司、运输或清点时退出任务，不建立S组任务池 |
| T02／T03 | T03处理确认接收前异常；O01异常组件处理确认接收后在手异常 | 两者可以共享表单能力，但不能共享责任判定、入口、返回或业务语义 |
| 手术植入 | 正式植入结果只读回写O01 | 实际植入不是S组动作；补录或更正仍进入手术植入正式流程 |
| 库存 | O01轻量组件提交入库申请并读取批准结果 | 不展示库存余额，不设计库存审批、入账和计算 |
| 消毒 | O01转用组件为器械包读取独立放行结果 | 不在S组设计清洗、消毒、灭菌流程 |
| Web后台 | S组提交申请、交寄事实和异常事实，读取审批、清点及最终结果 | 不预设后台页面、岗位或内部状态机 |
| 未来业务报销模块 | S01记录交接方式时登记跳转桩子 | 当前只留桩子；不建立报销页面、字段、审批或结果规则，具体触发与返回待该模块正式讨论 |

## 4. 原五页最终处置矩阵

| 原页面 | 最终处置 | 确认理由 |
|---|---|---|
| S01 本单物品结余 | 取消独立总览身份；其总览职责融入O01，其动作身份与原S04融合 | O01已经表达本单全部交付物和责任结果，再建立一张总览只会重复订单详情；S01剩余的稳定独立动作是借单还回 |
| S02 转入个人仓申请 | 与原S03能力融合后融入O01轻量组件 | 两者共享实物选择、申请、等待批准、责任锁定和结果回写，仅目标条件不同；删除独立页后无职责缺口 |
| S03 本人订单转用申请 | 与原S02能力融合后融入O01轻量组件 | 个人仓／本人其他订单作为同一组件的两种目标模式；后一模式条件性选择目标订单 |
| S04 还回处理 | 与原S01融合并重编号为新S01“借单还回” | 承担选择待还物品、合并本人其他订单实物、执行公司安排和处理还回问题的完整生命周期 |
| S05 在手实物异常 | 职责融入O01在手异常轻量组件 | 始终绑定单张来源O01和具体实物；申报、补充、等待与结果都可由O01、G03同一任务和O04记录闭合 |

| O01组件 | 入库／转用轻量办理 | 已确认不建立独立页面；在O01选择具体实物和处理目标，提交后回到原物品位置查看进度与结果 |

## 6. O01与动作载体的关系

```text
O01未闭环实物责任区
├─ 只读展示：实际接收、已植入、已入库、已转用、已还回、已处置异常、仍在手数量
├─ 仍需本人处理
│  ├─ 借单还回 → S01
│  ├─ 申请入库／申请转用 → O01轻量组件
│  └─ 申报在手实物异常 → O01轻量组件
└─ 只等待审批、运输、清点或处置：O01显示普通进度，不占待我处理

还回／入库／转用／异常正式结果 → 回写O01及O04
全部责任闭环 → 系统判断完成资格 → 公司最终确认
```

没有异常且植入、转用结果均已确定后，剩余待处理实物进入“借单还回”。但“未植入”不自动等于“已还回”：在公司指定方式、本人完成交寄及公司清点确认前，责任仍保持未闭环。

## 7. T03与O01在手异常组件的责任边界

两页是否合并不按异常名称判断，而以“本人是否已经确认接收”为唯一责任分界：

| 页面 | 发生节点 | 责任作用 | 固定返回 |
|---|---|---|---|
| T03 收货异常申报 | 确认接收前，核对实际交付批次 | 判定责任是否形成；未收到不形成本人责任，到手异常形成临时责任 | 原T02批次 |
| O01在手异常组件 | 确认接收后，实物已由本人负责 | 冻结已经形成的本人责任，等待正式处置结果 | 关闭或返回原O01实物位置 |

两者可以复用实物选择、数量、说明、照片证据和提交反馈能力，但异常类型、对象上下文、责任回写和返回路径分别维护。还回后公司清点发现的差异继续留在S01“借单还回”。

## 8. 首轮宏观审查失效原因与纠偏

首轮方案错误建议保留独立S01总览和独立S04。问题不是资料池缺失，而是执行方法没有完成宏观审查应有的逆向验证：

1. 被现行S01—S05编号锚定，把候选页面当成默认骨架；
2. 只对照了页面职责，没有逐页验证“删除该页后，职责是否已被O01或共用组件承接”；
3. 已经读到O01展示实际接收、植入、转用、还回、异常和在手数量，却没有据此判定独立S01总览重复；
4. 把S04生命周期复杂作为保留S04的理由，却没有继续检查O01承接总览后S01只剩还回动作，因此漏掉S01／S04融合；
5. 对T03／S05只做“是否合页”的二选一判断，没有完成“共享组件但保持不同业务页面”的承载层比较。

纠偏后的检查方式是：先从现有O01／T页面已经承担的能力中扣除重复职责，再要求每张S页证明其独立上下文、本人动作、返回和结果回写；只剩摘要或状态的候选页不成立为独立页面。

## 9. 确认结论与下一步

用户已经确认：取消独立S组总览，把总览留在O01；原S01与S04融合为S01“借单还回”；原S02／S03的入库／转用能力由O01轻量组件承载；原S05的在手异常能力同样由O01轻量组件承载。T03与确认接收后的在手异常只共享表单能力，不混同责任语义。

后续复盘确认，不能由“动作能力存在”直接推导独立页面已经成立。O01本单物品保留原交付结构、叠加结果并集中操作；借单还回通过删除反证并确认独立页面；入库／转用和在手异常均通过独立页面删除反证。S组宏观审查至此完成，当时页面集合收口为23页。S组结束筛查与远程同步随后完成；后续C组收敛到18页，O组删除O03后当前为17页。低保真、视觉、代码、Web后台、库存和手术植入内部设计仍未启动。

S01后续具体结构必须在“记录交接方式”的相应位置标注未来业务报销模块跳转桩子。该模块尚未登记和启动，本阶段只保存桩子，不推演其内部页面与业务规则。
