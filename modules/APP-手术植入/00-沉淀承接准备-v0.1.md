# 手术植入 APP 沉淀承接准备 v0.1

> 状态：承接准备资料；不新增业务规则，不替代模块总池、规则池、接口池或验收资料。  
> 建立日期：2026-08-26  
> 目的：依据当前正式资料判断手术植入已形成的沉淀范围、尚未沉淀的范围及后续正常续接条件。

## 1. 当前沉淀成熟度判断

手术植入不是空白模块，也不是已经完成整体闭环的模块。当前正式资料已经形成部分规则、接口、业务主线和探索承载，适合按“部分正式沉淀”正常续接；不再从旧聊天或接管包重新迁移。

当前已形成的正式沉淀包括：

- R-01—R-10 及业务语义-01／02；
- 手术通知进入、正式结果正向回写、取消／失效反向调整及冲正顺序接口；
- 实际销售事件、销售明细、来源分配和正式结果主线；
- 异常、未正式形成、取消／失效和销错冲正的业务方向；
- 页面组宏观审查、全局纵览与 I 组推进结构；
- 完整闭环低保真探索原型及其承载图、探索记录和覆盖边界；
- 当前桩子、未启动模块和不进入范围。

当前尚未形成模块整体闭环沉淀的部分包括：

- R-11—R-19 的规则池正式拆分；
- 数据销售的实际明细、正式结果与回写边界；
- 具体权限、时限、审核、字段、算法、幂等和重试；
- 模块整体业务闭环、设计和交付验收。

低保真资料的身份是探索沉淀，不是正式页面或业务规则。它可以证明当前主线已经被哪些入口、对象、状态、动作、结果和异常路径承载，也必须同时登记未覆盖项、占位项、原型与真实接口的差距，以及被后续原型替代的旧稿。原型中的样例字段、按钮和状态不能单独提升为正式事实。

## 2. 正常承接入口

后续新对话从以下资料承接：

1. 项目范围登记、驾驶舱和任务承接矩阵；
2. 本模块总池；
3. 当前规则基线及本轮相关规则正文；
4. 接口登记和手术通知直接接口；
5. 业务主线、全流程逻辑基线及当前探索记录；
6. 本准备资料，用于理解沉淀等级和未闭合范围。

接管包和历史迁移记录仅用于来源追溯，不作为当前业务判断入口。旧聊天不补充当前事实。

## 3. 承接前检查

- 总池、路线图、驾驶舱和任务矩阵的当前恢复点一致；
- 已确认规则、业务闭环方向和接口契约能够互相定位；
- 当前有效低保真及其承载图、探索记录和替代关系已登记，且与业务主线和接口边界一致；
- 未闭合内容均登记为桩子或未闭合规则组；
- 探索原型中的占位未被升级为业务事实；
- 当前任务能够明确属于规则正式化、探索补测、数据销售定位、页面承载或验收中的一项；
- 本地工作区、当前分支和远端引用已核对；正式承接资料以已确认且可追溯的版本为准，无关未提交改动不得混入；
- 若资料不足以支撑下一项判断，先补正式沉淀或说明缺口，不直接回读聊天。

## 4. 下一项准备动作

下一新对话先核验承接内容、低保真身份、当前恢复点和开发路线。核验通过后，进入 P2 规则正式化：整理 R-11—R-19 中已有明确方向的规则与继续保留的桩子；随后再进入实物销售探索补测和数据销售边界定位。

## 5. 本地与远端对齐要求

在历史迁移、阶段收口或新对话承接前，先核对当前分支、工作区状态、远端跟踪分支和承接资料的提交版本。远端存在未处理分叉、相关正式资料未提交或本地与远端版本无法确认时，暂停承接结论；无关业务改动保留原位，不纳入本次沉淀。对齐完成后记录所依据的提交或标签。

## 6. 基线核对记录

- 正式承接入口、规则基线、接口登记、双向结果接口、业务主线、全流程逻辑基线及低保真探索资料均存在；
- 低保真承载图和完整闭环探索记录已纳入沉淀范围，并明确为探索身份，不替代正式规则、页面清单或验收；
- 首次核对所见的提交状态只作为当时快照，不作为后续承接依据；每次承接以当次 Git 核对和《新对话前全量沉淀基线审计》为准；
- 已完成恢复点统一：P1 双向接口闭合已完成；新对话首轮先完成承接核验，通过后才进入 P2 规则正式化；
- 当前沉淀不是模块整体收口；可以承接已确认的规则、接口和探索资料，不得把未闭合桩子升级为事实。
