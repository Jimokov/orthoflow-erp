# 手术植入全面盘查记录 v0.1

> 状态：当前有效的盘查记录；不新增产品、库存、后台、页面或技术规则。  
> 盘查日期：2026-09-04。  
> 范围：手术植入当前规则、接口、业务闭环、探索载体及与业务员侧常备物资、手术通知的直接关系；历史资料只核对身份和替代关系。

## 1. 当前模块究竟要完成什么

当前范围不是“处理所有手术相关业务”，而是现实手术完成后，业务员把实际使用的实物据实登记为正式销售结果，并把该实物的真实来源结果返回给需要接收该结果的外部业务。

```text
现实手术完成
→ 医院使用登记单／胶贴取得实际使用事实
→ 扫码、识别、补拍或手动补录形成同一种明细
→ 系统回查实物的最近有效交接
→ 形成正式结果；或保留未正式记录等待补齐／退出
→ 仅必要的来源结果返回外部业务
→ 来源校正、取消／失效／冲正保持可追溯
```

这条当前范围仅适用于实物销售。数据销售已在[销售形态确定规则 v0.2](../01-规则池/04-手术植入APP销售形态确定规则-v0.2.md)登记为非阻塞桩子，不嵌入本闭环。

## 2. 两条外部业务关系

| 外部业务 | 它向手术植入提供什么 | 手术植入对它返回什么 | 当前边界 |
|---|---|---|---|
| 业务员侧常备物资 | 现实手术前已在业务员侧的实物及其可回查的最近有效交接。它是一个对外来源，不因医院托管或业务员自持再拆成来源类别。 | 当前不返回库存扣减、恢复或入库动作；只把实际使用明细保留为可追溯事实。 | 常备物资接收登记、漏登补救、可用量、扣减、补回与内部责任属于库存管理。K-C07、P-I01 是非阻塞桩子。 |
| 手术通知 | O01／G03 可提供进入上下文、已确认接收且仍绑定本需求组的候选实物及返回位置。 | 正常通知来源返回实际植入；待核实但保留通知上下文时返回非结清关联；取消、失效或冲正撤销原记录产生的全部通知侧结果。 | 手术通知保留未植入候选的责任并重算结余、完成资格和必要任务；它不替植入决定患者、实际明细或来源。 |

两条外部关系不是让业务员在页面上“选择来源”的两个按钮。胶贴证明实际使用，系统按真实上游链和最近有效交接得出来源；业务员只补齐或核对凭证所证明的事实。

## 3. 闭环判定

| 闭环段 | 判定 | 依据 |
|---|---|---|
| 实际手术事件与记录身份 | 已闭合 | 一名业务员＋一位患者＋一次实际手术事件；五项基础信息；动作事实不自动形成销售。 |
| 实际实物事实取得 | 已闭合 | 医院登记单／胶贴为锚；扫码、识别、补拍、手动补录均形成同一明细，且不面对公司总目录。 |
| 来源锚定 | 已闭合 | 原始来路与最近有效交接并存；以最近有效交接归属；无法核验不伪造来源。 |
| 两类外部结果 | 已闭合 | 常备物资不触碰通知；正常通知来源与待核实关联分别回写；同一记录可混合而不混算。 |
| 正式结果前恢复 | 已闭合 | 不完整或校验异常不形成正式结果；补齐重提或退出均不回写。 |
| 正式结果后变化 | 已闭合 | 来源核实是责任校正；取消、失效、销错冲正按原记录关系撤销全部通知侧结果，正确结果重新形成。 |
| 当前实物销售业务闭环 | **业务逻辑已闭合** | 上述链路已有规则、接口与复走记录；不以库存内部动作、Web、算法或数据销售为前置。 |
| 正式低保真准入 | **已启动 I01 探索，设计验收尚未开始** | v0.2 已确认，探索承载已复核并形成页面流程交接；已制作 A／B／C 三种 I01 结构变体，等待审阅确认。 |

## 4. 为什么此前会绕圈

1. 原本简单的“术后凭证 → 实物来源 → 正式结果”被旧探索稿中的“来源选择”表述带偏，导致系统回查与库存内部细节被反复当作同一问题。
2. 讨论中新出现的接收漏登、拆盒、包装粒度等问题没有第一时间作为外部桩子隔离，曾挤占来源主线；它们现在分别定位到 K-C07 与 P-I01。
3. 旧的全流程验收、业务主线和探索载体早于待核实关联及 N-X03，仍是“当前有效”外观，容易让已经收口的生命周期再次被误判为未完成。
4. “模块全流程”与“当前实物销售闭环”未先分层，数据销售和库存内部事项被错误当作当前页面前置。
