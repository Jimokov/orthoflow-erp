## 1. 本轮目的

在《手术植入模块页面流程 v0.1》和《实物销售手术植入全流程逻辑验收与总路线图 v0.2》已确认的范围内，第一次制作可运行 I01 低保真，验证“一张页面、条件区块承载完整手术植入闭环”是否能被现场业务员看懂和操作。

本轮不重新讨论业务规则，不新增页面，不裁决 OCR 算法、权限、审核、时限、接口技术或库存内部作业。

## 2. 三种结构变体

同一 HTML 通过 `?variant=A|B|C` 切换，底部浮动切换器和左右方向键均可切换；状态仅存在于 URL／本次浏览，不落库、不持久化。

| 变体 | 组织方式 | 重点观察 |
|---|---|---|
| A 连续工作区 | 按现场顺序排列：入口 → 事件 → 凭证／明细 → 来源结果 → 提交／结果 | 一页完成是否顺手，底部提交是否清晰 |
| B 核对清单 | 先显示完成度与缺口，再逐项核对明细和凭证 | 业务员是否能快速知道“还缺什么” |
| C 凭证优先 | 第一屏锁定术后登记单，再展示识别结果和系统来源回查 | 胶贴事实是否被置于核心位置，来源是否保持系统回显 |

## 3. 可观察状态与入口

示例状态由顶部“原型驱动器”切换，仅为审阅工具，不代表用户可以选择校验结果：

- `draft`：新建／未采集；
- `scan`：已取得凭证并形成探索明细；
- `mixed`：明细混合业务员侧常备物资、手术通知来源和待核实表现；
- `pending`：已使用、来源待核实，不结清通知候选；
- `formal`：正式结果及通知正向回写摘要；
- `error`：未正式形成，展示缺口和同一记录内补齐重提。

入口可切换为 `entry=g01`（G01 独立进入）或 `entry=notice`（O01／G03 通知上下文进入），用于观察同一 I01 页面如何保留返回上下文。

## 4. 本稿覆盖的已确认承载

- 同一 I01 页面承载两种入口；
- 术后使用登记单／胶贴作为实际事实锚；拍照、扫码、补拍、手动补录回到同一种实际销售明细；
- 每项明细单独显示系统回查的来源结果，不提供业务员来源选择器；
- 业务员侧常备物资、手术通知来源、来源待核实及混合明细的表现；
- 凭证关联、不可静默覆盖的提示、提交与自动校验前后状态；
- 正式结果通知正向回写、来源待核实非结清、校验异常和失败恢复提示；
- 返回发起入口和记录上下文保留。

## 5. 明确不在本稿内

- 不新增 I02—I05 正式页面；它们仍是旧探索节点／条件区块参考；
- 不提供人工来源选择、常备优先扣减、通知候选手动结清或公司全量产品目录；
- 不画库存数量、入库、调拨、Web 后台、数据销售、销售汇总、提成、患者／病例后台；
- 不把样例字段、按钮、状态驱动器或弹窗提示升级为规则、权限、接口或验收结论；
- 取消／失效／修改／冲正只保留结果关系和提示位置，具体操作条件仍按正式资料中的桩子处理。

## 6. 低保真审阅后处理

本稿需要用户和带码设计方先比较三种结构在现场场景下的可理解性，重点确认：

1. 哪种结构最容易让业务员完成“先锁事实、再看来源、最后提交”；
2. 待核实、未正式和正式结果是否在一张记录内足够清楚；
3. 入口返回、凭证关联和多次扫描／手动兜底是否需要调整区块位置。

审阅结论确认后，才形成《手术植入模块设计验收记录》；本记录本身不代表设计验收通过。
