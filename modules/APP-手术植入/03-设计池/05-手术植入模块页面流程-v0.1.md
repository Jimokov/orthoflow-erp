> 发布日期：2026-09-04。  
> 业务基线：[实物销售手术植入全流程逻辑验收与总路线图 v0.2](../04-业务闭环/10-实物销售手术植入全流程逻辑验收与总路线图-v0.2.md)。

> 适用端：业务员移动端；适用业务：实物销售手术植入。

## 1. 这份文件负责什么

这份文件把已经确认的实物销售业务链转换为设计可以直接承接的页面流程：从哪里进入、在同一条记录上完成什么动作、系统在什么条件下显示什么结果、处理后回到哪里。它不重新裁决业务规则，也不要求设计方把每个条件拆成独立页面。

页面流程与业务验收的关系如下：

| 文件 | 负责回答的问题 |
|---|---|
| 《实物销售手术植入全流程逻辑验收与总路线图 v0.2》 | 业务是否闭环、正式结果是什么、通知侧如何正向／反向变化、哪些范围不进入。 |
| 本文件 | 已闭环业务由页面如何承接入口、本人动作、条件、返回和结果回写。 |
| 原后续 I01 低保真 | 该执行入口已撤销；本文件只保留历史交接内容和可复用业务动作素材。 |

## 2. 页面总判断

### 2.1 正式页面数量

本文件当时提出只保留一个正式页面候选 I01「手术植入记录」；该候选权重已经撤销，不再代表当前页面集合。

事件、基础信息、实际销售明细、来源结果、凭证、提交、正式／未正式状态和后续变化，都是同一条植入销售记录的不同阶段或条件区块。旧探索中的 I02—I05 仅是验证闭环的节点，不是五张正式页面。

### 2.2 设计承载原则

- 业务员看到的是实际手术登记工作区，不是来源选择器；
- 胶贴所证明的实际使用事实优先于任何来源展示；
- 来源由系统依据真实上游实物链和最近有效交接得出，业务员只能补齐或核对事实；
- 明细可以混合不同来源，但每项明细独立显示结果，不把整张记录压成一个来源；
- 未正式、异常、待核实和正式结果是同一记录的条件状态，不自动变成新的页面；
- 页面要给出下一步和返回位置，但不把未确认的权限、时限、审核或算法画成既定能力。

## 3. 入口与返回总图

```text
G01 首页「手术植入」
        │ 无通知上下文
        ▼
┌──────────────────────────┐
│ I01 手术植入记录          │
│ 事件／基础信息             │
│ 实际销售明细               │
│ 系统来源结果               │
│ 凭证／提交／校验            │
│ 正式、未正式、待核实条件区块 │
└──────────────────────────┘
        ▲
        │ 处理结束后回到发起入口
O01／G03「手术情况确认」─────┘
  携带需求组、任务、候选实物和返回上下文

正式结果：按明细来源返回通知结果；通知侧重算责任与结余
未正式／异常：留在 I01，补齐重提或退出；不产生通知正式回写
后续变化：在正式记录上下文中进行来源校正、取消／失效或销错冲正
```

进入来源不同只改变上下文条，不改变页面身份和记录身份。通知入口的候选实物是系统回查依据，不是页面上的人工来源按钮。

## 4. I01 页面承载结构

| 区块 | 页面承载内容 | 业务员本人动作 | 系统结果 | 明确不画成能力 |
|---|---|---|---|---|
| 入口上下文 | G01 独立进入，或 O01／G03 任务进入；通知入口的需求组、任务、候选实物和返回位置 | 查看并继续当前记录 | 保留进入来源和返回目标 | 不建立两套植入记录，不让入口预置实际使用结果 |
| 手术事件与基础信息 | 医院、科室、术者、患者姓名、住院号等已确认边界；实际手术动作事实 | 建立或补齐本次事件 | 形成一次现实手术事件与植入销售记录 | 不由动作事实自动生成销售，不创建患者／病例后台 |
| 实际销售明细 | 胶贴事实中的产品、批号／可追溯身份（如有）、数量 | 拍照、扫码、补拍或人工补录；核对识别结果 | 形成同一种实际销售明细 | 不打开公司完整产品目录，不把识别方式变成不同业务链 |
| 来源结果 | 每条明细的系统回查结果：业务员侧常备物资、正常通知来源或来源待核实 | 查看、补齐事实或凭证；不能手选来源 | 按最近有效交接确定来源；可在一条记录中混合 | 不显示“选择常备／通知／混合来源”作为业务动作，不显示库存可用量或扣减 |
| 凭证与提交 | 术后使用登记单或同等凭证的关联 | 上传／关联凭证，提交记录 | 凭证留存且不可被新文件静默覆盖；触发自动校验 | 不规定凭证字段、审核角色、算法或接口技术 |
| 结果与下一步 | 未正式、校验异常、正式、待核实关联、后续校正或退出提示 | 按已确认条件补齐、重提、查看或发起后续动作 | 正式结果按来源产生通知结果；未正式不回写 | 不新增独立结果页、库存页、审核后台或数据销售页 |

## 5. 页面流程段

### 5.1 进入与建立

| 项目 | G01 独立进入 | O01／G03 任务进入 |
|---|---|---|
| 进入条件 | 业务员从首页发起实际手术植入登记 | 业务员处理手术情况确认任务并进入“记录手术植入” |
| 带入内容 | 无通知需求组或候选实物上下文 | 需求组、任务、候选实物、发起位置和返回位置 |
| 共同动作 | 建立或继续同一种实际手术事件与植入销售记录 | 建立或继续同一种实际手术事件与植入销售记录 |
| 进入结果 | 仅进入，不形成植入结果 | 仅进入，不形成植入结果；不得把任务当作已植入事实 |

### 5.2 实际事实采集

页面按“术后凭证是事实锚”的顺序承载：

1. 业务员提交医院使用登记单或同等凭证的照片／扫描结果；
2. 系统展示已识别或已取得的产品、批号／可追溯身份（如有）和数量；
3. 识别不完整时允许继续补拍、再次扫描或人工补录实际凭证信息；
4. 所有采集方式均回到同一条实际销售明细，业务员对事实进行核对；
5. 识别算法、成功率和未预见识别情况不在本文件中预设固定分支。

“人工补录”表示补齐凭证证明的实际事实，不表示从公司产品总目录选一个产品，也不表示人工指定来源。

### 5.3 来源结果展示

系统在明细形成后显示回查结果，不显示来源选择控件：

| 系统结果 | 页面表现 | 下游结果 |
|---|---|---|
| 业务员侧常备物资 | 明细行显示已核验来源及可追溯事实 | 保留实际销售结果，不产生通知回写 |
| 正常手术通知来源 | 明细行显示对应需求组／候选实物上下文 | 正式结果形成后回写通知并重算责任与结余 |
| 来源待核实且有通知上下文 | 明细行显示“已使用，来源待核实”及非结清提示 | 不结清候选实物，通知订单不能完成；后续可转换或撤销关联 |
| 来源待核实且无通知上下文 | 明细行显示来源核验异常 | 不触碰任何通知订单 |
| 同一记录混合来源 | 各明细行分别显示各自结果 | 只对正常通知来源及适用的待核实关联产生对应通知结果 |

明细来源结果由系统依据原始来路与最近有效交接推导；最近有效交接决定本次来源归属，业务员不得以“常备先承接、通知承接剩余”改归可回查实物。

### 5.4 凭证、提交与校验

页面提供同一记录下的凭证关联与提交动作：

- 凭证与本次植入记录关联并留存；已上传凭证不被新文件静默覆盖；
- 业务员提交后才触发自动校验；
- 自动校验通过，形成正式植入结果；
- 记录不完整或校验异常，保持“未正式形成”，不产生通知正式回写；
- 未正式记录可回到 I01 补齐后重提，或在已确认条件下退出；具体时限、权限、审核反馈和重试方式仍不在页面流程中裁决。

### 5.5 正式结果与通知返回

正式结果区块至少能让业务员看清：

- 正式植入记录已经形成；
- 本次实际销售明细及其系统来源结果；
- 哪些正常通知来源明细将回写手术通知；
- 哪些业务员侧常备物资明细不回写；
- 哪些明细仍是来源待核实、尚未结清通知候选；
- 处理结束后回到 G01 或发起本次动作的 O01／G03 上下文。

通知侧的责任、结余、完成资格和必要任务由手术通知按已确认接口自行重算，植入页面不复制通知订单总览。

### 5.6 正式结果后的变化

这些动作在 I01 正式记录上下文中作为条件操作或后续入口表达，不创建新的植入页面：

| 后续事实 | 页面表达 | 业务结果 |
|---|---|---|
| 来源后来核实 | 标记同一明细的来源责任已校正 | 转换为正常通知来源或撤销待核实关联；实际使用记录持续有效 |
| 正式结果取消／失效 | 显示原记录保留及反向处理状态 | 撤销原记录产生的全部通知侧结果，通知重新计算 |
| 销错冲正 | 显示原结果保留、先反向、再形成正确结果 | 正确结果按真实来源重新输出；原结果不被静默覆盖 |

取消／失效／冲正的权限、审批、时限、失败恢复和幂等不由页面流程虚构；正式低保真只承载已确认的状态关系和必要提示。

## 6. 页面状态与条件区块矩阵

| 页面状态 | 必须看见什么 | 允许的本人动作 | 不应出现 |
|---|---|---|---|
| 空白／新建 | 入口上下文、事件与基础信息入口 | 建立事件、返回入口 | 正式结果、通知回写、库存信息 |
| 明细采集中 | 胶贴／凭证采集反馈、已形成明细 | 拍照、扫码、补拍、人工补录、核对 | 公司总目录选品、来源按钮 |
| 来源结果已出 | 每项明细的系统来源和核验状态 | 查看、补齐事实、继续关联凭证 | 类别优先分配、库存扣减 |
| 待提交 | 明细、凭证关联、提交动作和缺口提示 | 关联凭证、提交、返回继续编辑 | 直接显示正式结果 |
| 未正式／校验异常 | 未正式原因或缺口、实际使用是否已保留、通知是否未回写 | 补齐重提、按条件退出、返回 | 把异常画成已完成或通知已结清 |
| 正式结果 | 正式记录引用、逐项来源结果、通知回写结果 | 查看、返回原入口、进入后续条件操作 | 把常备物资明细伪装成通知回写 |
| 来源待核实 | “已使用，来源待核实”、非结清提示 | 补齐核验事实或等待后续结果 | 人工指定通知来源、自动结清候选 |
| 取消／失效／冲正 | 原记录、原结果与反向／新结果关系 | 在合法条件下发起或查看处理 | 删除原记录、整单覆盖、静默改写 |

## 7. 旧探索载体复核结论

本轮已复核 `03-完整闭环探索承载图-v0.1.md`、`04-完整闭环探索记录-v0.1.md`、I01 静态探索记录及两份 HTML 原型：

| 旧探索表现 | 处理结论 |
|---|---|
| 把 I01—I05 连成五个节点 | 保留为探索导航和状态验证，不作为正式页面集合；本文件统一为一个 I01 页面及条件区块。 |
| I03 提供“选择业务员侧常备物资／通知／混合来源” | 认定为旧探索表现；正式页面只能展示系统回查结果，不能让业务员选择来源。 |
| 正式结果只表现正常通知来源正向回写 | 补入来源待核实非结清关联、取消／失效撤销全部通知侧结果及冲正顺序。 |
| 原型用按钮模拟“通过／异常／取消／冲正” | 保留为探索驱动器；按钮不代表业务员权限、系统可选校验结果或正式实现。 |
| 全局总览、I 组总览 | 继续作为原型审阅导航层，不计入业务员正式页面。 |

因此，旧原型不直接交给带码设计方作为正式依据；设计方应以本文件和 v0.2 为准，把旧原型只当作灰阶信息密度与导航风格参考。

## 8. 给低保真设计方的硬边界

必须表达：

- G01 与 O01／G03 两种入口进入同一页面和同一种记录；
- 胶贴事实采集、扫码／拍照／补拍／手动补录的统一明细；
- 系统来源结果与混合来源逐项显示；
- 凭证关联、提交、自动校验、正式／未正式结果；
- 通知正向回写、待核实非结清、取消／失效反向和冲正顺序；
- 返回原入口和记录上下文保留。

不得表达为已确认能力：

- 人工来源选择或“常备优先扣减”；
- 面向公司产品总目录的自由选品；
- 库存可用量、扣减、入库、调拨、库存恢复或后台审核；
- 数据销售、销售汇总、提成或 Web 后台；
- OCR 算法、识别成功率、权限、审批、时限、幂等和重试细节；
- 患者／病例后台管理或由手术动作自动产生销售。
