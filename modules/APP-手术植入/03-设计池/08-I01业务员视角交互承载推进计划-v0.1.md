## 1. 本日发生了什么

### 1.1 已有业务基础

手术植入的实物销售业务逻辑已经在当前正式资料中形成闭环：

`G01／手术通知任务进入 → 建立实际手术事件 → 术后使用登记单／胶贴采集 → 拍照、扫码、补拍或受限手动补录 → 每条明细自动回查来源 → 关联凭证 → 提交自动校验 → 正式／未正式／来源待核实结果 → 通知正向或反向处理`。

这条业务链由《实物销售手术植入全流程逻辑验收与总路线图 v0.2》、规则池、接口池和业务闭环资料共同承载，不能因为低保真失败就重新猜测或推翻。

### 1.2 推进中的错误

本日制作低保真时发生了几个连续错误：

1. 把“一个 I01 业务上下文”错误地压缩成“一张静态长页面”。
2. 主要复用了《手术通知.html》的外壳，却没有真正继承它的点击、状态、返回栈、确认提交和异常恢复制作思路。
3. 把入口、正式结果、来源待核实和校验异常做成地址栏可切换的样例状态，而不是由业务员动作和系统结果产生。
4. “拍照／扫描”“手动补录”“关联凭证”“提交校验”“返回”均没有形成真实状态转换。
5. 把审阅者使用的原型驱动器放进手机业务内容，混淆了审阅操作和业务员操作。
6. 因此形成了一个能观察区块、不能走完流程的结构稿，并错误地接近了“正式低保真”的表达方式。

### 1.3 深度审查后的当前判断

- **业务规则闭环**：当前正式基线仍成立。
- **页面职责交接**：已有页面流程，但交互承载层不足。
- **业务员点击闭环**：当前 I01 HTML 未通过，不能证明业务员可以从入口走到正式结果。
- **旧完整闭环原型**：其中的状态机、动作分发、重新渲染、返回栈和恢复路径有制作价值；其来源选择和单一来源模型与当前规则冲突，不能直接继承。

本日真正暴露的不是“还缺几个字段”，而是业务规则与可操作页面之间缺少一层逐动作交互契约。

## 2. 明日第一步

明日只做一件事：

> **基于当前 v0.2 业务基线，先形成《I01 页面承载调整可行性论证》及其逐动作交互矩阵；不制作 HTML，不做视觉，不进入代码。**

这一步不是重新讨论手术植入业务，也不是再次讨论来源规则，而是回答页面承载问题：

1. 一个 I01 业务上下文需要哪些可点击步骤／屏幕；
2. 哪些步骤可以作为同一屏的条件区块，哪些必须独立承载；
3. 从 G01 独立进入和从手术通知任务进入时，入口上下文如何保留；
4. 每次点击改变什么记录状态，业务员下一步能点什么；
5. 提交、未正式、待核实、正式、返回、取消／失效和冲正如何在同一记录链中表达；
6. 哪些内容仍是桩子，不能由原型样例写死。

## 3. 明日交互矩阵的最小结构

| 业务阶段 | 业务员要解决的问题 | 业务员动作 | 点击后可见状态 | 下一步／返回 |
|---|---|---|---|---|
| 入口 | 我从哪里来、这是不是已发生植入 | 点击 G01 或通知任务入口 | 显示入口上下文；仅进入，不形成结果 | 建立事件；返回原入口 |
| 事件 | 本次实际手术是否建立 | 填写／核对必要事实并继续 | 事件已建立；销售结果仍未形成 | 进入凭证采集 |
| 凭证采集 | 胶贴是否已取得、识别了什么 | 拍照／扫描／补拍 | 显示本次识别结果及未识别部分 | 核对明细或继续采集 |
| 明细核对 | 哪些产品、追溯身份和数量确实被使用 | 核对、修改事实、受限手动补录 | 明细进入同一记录；不出现公司全目录 | 继续来源回查 |
| 来源结果 | 每条明细从哪里来 | 查看系统回查结果 | 逐项显示常备、通知来源或待核实 | 关联凭证 |
| 提交校验 | 当前是否足以形成正式结果 | 关联凭证并提交 | 进入校验中；不能手选通过／异常 | 正式、未正式或待核实 |
| 结果 | 通知有没有被回写、记录是否完成 | 查看并返回 | 正式结果、未正式或待核实关系明确 | 返回原入口或同记录恢复 |
| 后续 | 原结果发生取消、失效或错误怎么办 | 在合法条件下查看／发起后续操作 | 原记录保留，反向与新结果顺序可见 | 返回记录上下文 |

这张矩阵只是明日的审查骨架。正式屏幕数量、页面编号和视觉布局必须在矩阵确认后再决定。

## 4. 明确不做的事

- 不把 I01 预先固定为一张页面，也不预先固定为若干页面；
- 不把旧 I02—I05 编号直接变成正式页面；
- 不让业务员手动选择来源；
- 不用地址栏或原型驱动器替代业务员动作；
- 不把库存扣减、后台审核、OCR 算法、权限、时限、幂等和数据销售写进低保真；
- 不因今天的页面问题重新打开已经确认的业务规则；
- 不在明日第一步直接进入视觉、代码或设计验收。

## 5. 明日第一步的完成标准

只有同时满足以下条件，才允许进入新的低保真制作：

1. G01 和通知任务两条入口均能按业务员视角逐步走通；
2. 采集、补拍、手动补录、逐项来源结果、凭证、提交、校验和结果均有动作与状态对应；
3. 正式、未正式、待核实、返回和恢复不存在断流；
4. 通知正向回写、常备物资不回写、待核实不结清、取消／失效反向、冲正先反向后正向均能定位到对应结果；
5. 旧探索中保留的内容与当前规则的冲突被明确隔离；
6. 用户确认页面承载方案后，才修订页面流程并重新制作可点击低保真。
