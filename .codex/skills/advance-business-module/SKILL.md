# 推进业务模块

将项目文件视为跨任务事实来源，将 Skill 视为推进工作流。不要把聊天长度或模型记忆当成事实来源。

## 1. 识别并接管范围

1. 解析当前 `SKILL.md` 的绝对路径，读取同目录 `VERSION`；第一条工作更新必须显示 `已调用 $advance-business-module@<版本>｜来源：<SKILL.md绝对路径>`。`VERSION` 缺失时报告 `unversioned`，不得声称正在使用最新版。
2. 找到项目根目录并完整读取项目 `AGENTS.md`。
3. 读取 `docs/00-当前范围与模块登记.md`。
4. 确认用户指定的模块、所属端和本次阶段。
5. 读取目标模块的 `00-START-HERE.md`，按其当前有效资料索引加载当前任务所需最小集合。
6. 输出简短接管摘要：模块与端、当前阶段、实际读取文件、已知未决问题、本次不进入范围。
7. 对项目内每条正式回复，按项目 `AGENTS.md` 的“对话编号协议”写入日期与当日序号；跨对话续号以前一份当日日报中的编号断点为准。只在形成结论、资料变更或任务切换时写简短结论，不将每条对话逐字复制到日报。
8. 提出真正需要用户决定的问题时，按项目 `AGENTS.md` 的“提问附建议协议”给出已核实依据、简短推荐与直接影响；没有真实决策价值时，直接执行已确认规则或登记桩子，不制造提问。

每次向用户交付阶段结论、审查结果、资料同步或收工结果时，结尾必须给出唯一的“下一步”：说明下一项具体工作、进入条件、是否需要用户确认，以及不进入的范围。不能只报告完成情况后等待用户追问；若存在多个候选方向，先按当前硬闸门给出推荐顺序，再只提出当前最高优先级的确认项。

若模块未登记、仍在概念阶段或所属端未启动，只做范围澄清与规则访谈；不得自动建立页面、状态、代码、接口或后台能力。找不到总池时，先盘点已有资料并请用户确认成熟度，不从编号、模板、行业惯例或其他模块反推。

## 2. 选择对话承接路径

开始新任务、接管既有任务或用户给出旧对话时，先判定且在首条接管摘要中写明以下唯一一种路径：

1. **全新承接**：新对话接管已有正式模块。只读取项目规则、范围登记、模块总池及当前有效资料；不读取旧聊天。输出接管摘要后直接从当前唯一任务继续。
2. **历史迁移**：用户明确指定已有旧对话，但该对话未按本 Skill 形成当前资料。先不读取旧对话正文，形成并由用户确认《历史迁移可行性论证》：来源边界、当前正式基线、目标资料位置、候选条目格式、冲突判定、明确不迁移范围、迁移完成标准、旧对话退出条件及失败时的停止条件。论证未通过不得启动盘点。通过后，迁移任务才只允许盘点旧对话和已知资料来源，不继续业务讨论、不设计页面、不实现代码、不建立未确认能力。先输出候选迁移清单：来源、候选结论、候选页面／流程、跨模块衔接、冲突、缺失及建议的第一项正式任务。每项都标注“来自旧对话，未成为当前事实”。经用户确认后，才将结论写入对应总池、规则池或接口池；迁移记录保留来源线程标识、确认日期和正式资料去向。迁移完成后，旧对话退出业务推进职责，后续新任务只读取资料池。
3. **正常续接**：任务已有本 Skill 管理的当前总池与唯一任务。只按总池读取，不回读聊天补背景；聊天中未沉淀的内容仍按未确认缺口处理。

项目存在任务与对话承接矩阵时，开始和结束上述任一路径都要更新矩阵的任务类型、来源、正式资料入口、状态、下一承接任务和转换条件。矩阵只管理任务关系，不保存业务事实或替代资料池。

版本号采用 `主.中.末` 三段：小修、小范围补充、格式／链接／提示机制调整只递增末位；改变阶段顺序、硬闸门、资料身份或其他项目级工作流的重大更新递增中位；主位只在用户明确要求或不兼容的项目级重构时递增。每次升级仍须在同轮报告版本、原因、影响与受影响文件。

## 3. 最小读取与跨模块继承

按任务加载：

- 规则讨论：模块首页、当前规则、直接相关接口；
- 页面逻辑或设计：再读取设计进度、页面清单、页面流程和目标页面；
- 代码：再读取已确认设计与真实代码入口；
- 验收：再读取验收对象、规则依据和已确认接口。

历史池默认不读，只在追溯具体冲突或版本来源时读取必要正文，且不得覆盖当前文件。跨模块只继承接口池中明确的输入、输出、状态或结果，不复制来源模块内部流程、页面和操作。相邻模块未启动或接口未确认时登记缺口，不自行补全。

## 4. 使用局部决策树与受控反证

涉及规则、状态、权限、责任、页面保留或融合、跨模块结果、冲突裁决和硬闸门时，读取 [references/questioning-method.md](references/questioning-method.md)。

核心约束：

- 只为当前决策建立局部设计树，标明节点前置关系；
- 先用项目文件和工具查明可查事实，把真正的业务取舍交给用户；
- 每轮只提出最高优先级的 1—3 个前沿问题，不询问依赖尚未回答问题的下游项；
- 给出基于事实的当前建议和可推翻它的条件，用户方案不闭合或超出范围时明确否定；
- 用户回答后重算前沿；达到当前阶段充分闭合即停止，不追求整棵产品树穷尽。

## 5. 按风险建议模型档位

当任务跨度较大、用户关心成本，或即将执行硬闸门时，读取 [references/model-routing.md](references/model-routing.md)。

- 判断档：规则、状态、权限、责任、跨模块、页面身份、冲突和最终验收；
- 推进档：已知边界内仍需局部判断的页面或流程推进；
- 机械档：不产生新判断且可确定性验证的同步、搜索、格式和校验。

Skill 只建议档位；只有环境支持时才实际切换模型。出现冲突、歧义、缺失责任或结果回写时立即升级。不得为了节省流量让低档模型静默作出业务判断，也不应让高档模型承担纯机械工作。

当用户可在界面切换模型且本次选择影响成本、速度或可靠性时，按参考规则明确提示：建议档位、是否值得切换、触发原因，以及本段结束后是否建议回到默认档。不得声称已经自动切换，也不为短暂机械操作制造不必要的来回切换。

## 6. 按阶段推进

通常按以下顺序：

1. 业务规则与边界；
2. 规则封板与验收；
3. 信息架构；
4. 页面清单；
5. 页面流程；
6. 模块业务闭环验收与总路线图；
7. 低保真结构；
8. 模块设计验收；
9. 视觉稿；
10. 代码实现；
11. 交付验收与跨模块联调。

从资料池标注的阶段继续，不重做已完成阶段。每次只推进用户指定的一项；发现冲突时暂停下游制作，回规则层确认。

## 7. 执行组间切换硬闸门

完成一组页面逻辑后，开启下一组前必须：

1. 读取模块首页登记的全部当前有效文件和直接相关接口；这是最小读取原则的明确例外。
2. 盘点全部已知文件，核对当前池、历史池、替代关系和引用方向；历史池默认只检查目录与引用。
3. 检查页面身份、入口、返回、状态、任务、角色权限、结果回写、术语、页数、版本和当前唯一任务是否闭合。
4. 搜索旧页面名、旧状态、旧流程和被替代结论的残留。
5. 检查结论是否同步到规则、接口、页面清单、页面流程、设计总控、当前进度和模块首页。
6. 不读取旧聊天补背景；聊天独有内容按未确认缺口处理。
7. 形成书面筛查记录，列明范围、发现、修复、暂缓和结论。
8. 筛查通过并对齐后，若项目配置 Git 远端，限定本次文件完成获取远端、检查分叉、提交、推送和远端验证。

阻塞冲突未解决，或要求的远程同步失败、无法验证时，不得开启下一组。非阻塞缺口必须登记归属，不能在下一组静默补写。

## 8. 执行新组宏观审查硬闸门

组间筛查通过后，只能开始新组宏观审查，不能直接逐页讨论：

1. 从全部当前有效资料提取整组业务目标、核心对象、起止条件、角色责任、入口出口、结果、跨组交集和边界。
2. 把已有页面名称、编号和旧低保真视为不可信输入。
3. 建立“业务能力—现有承载位置”矩阵，扣除现有页面、条件区块或共用组件已承载的能力。
4. 对候选页判断保留、融合、修改、删除或条件出现，检查组内和跨组的重复、错位及回写断裂。
5. 对每张建议保留的独立页完成删除反证：删除后有哪些本人动作、进入条件、返回或结果无法被其他载体清楚承接。
6. 没有候选页时先建能力清单，不从模板和惯例直接造页面。
7. 发现规则缺口先回规则层，不用页面设计补业务。
8. 形成宏观审查记录，列明继承事实、整组职责、对象与结果、交集、矩阵、页面处置、删除反证、缺口、建议和待确认项。

用户确认宏观方案前，不得默认旧页数、建立新编号或进入单页结构、低保真和视觉设计。

## 9. 执行模块业务闭环验收与总路线图

全部由本模块负责的页面组业务逻辑收口并通过组间闸门后，不得直接进入整体低保真。先仅从模块首页登记的当前有效资料形成并由用户确认《全流程逻辑验收与总路线图》；它是模块业务闭环验收的正式产物，至少包含：

- 端到端主流程和必要条件分支；
- 正式页面、条件区块、共用组件的身份、入口、本人动作、返回和结果回写；
- 对象、主状态、本人任务、角色权限和正式结果的关系；
- 跨模块确认输入输出及明确边界；
- 被删除、融合、改名或组件化页面的当前去向；
- 重要结论摘要与当前来源；
- 桩子、非阻塞缺口和不包含范围；
- “结论—能力—流程节点—页面承载—当前来源”追溯矩阵；
- 验收情景目录：至少覆盖正常、异常、取消、重新打开、失败恢复及跨模块返回；每个情景标明起点、关键动作、正式结果、回写与证据来源；
- 验收结论：已通过项、阻塞项、非阻塞桩子、未覆盖原因、恢复条件及是否允许进入整体低保真。

反向验收必须逐项验证：每张正式页面有合法入口；每个本人动作有触发、承载、退出和结果回写；状态和任务有底层事实；每个情景不断流；旧结论不复活；全部当前资料保持一致。发现缺口回所属规则、接口或页面逻辑修复后重新验收。用户未确认前不得进入整体低保真、视觉或代码；后续变更影响路线时先同步基线。

共享全局页面或未启动相邻模块不得被静默当成本模块已完成。它们只有在已确认输入、输出、任务、返回和结果回写契约且本模块可据此完成自身流程验证时，才能作为“已验证接口契约”列入本次验收；其真实页面聚合与跨模块联动转入后续跨模块联调。模块内部阻塞桩子、缺少契约的依赖或未通过组间闸门，均不得以条件通过替代验收。

## 10. 执行模块设计验收

整体低保真完成后、进入视觉稿前，形成《模块设计验收记录》。以已确认的业务闭环基线和当前低保真为输入，逐页检查并记录：

- 结构是否忠实承载已确认的页面身份、信息层级、入口、本人动作、返回和结果回写；
- 主状态、任务、权限、空态、异常态、取消、重开、加载／失败保留及关键并发变化是否有清楚呈现；
- 同一事实是否重复出现，信息密度、术语和操作干扰是否符合已确认设计原则；
- 低保真中是否擅自补入未确认规则、页面、字段、后台能力或桩子细节；
- 每个未通过项的归属、修复资料、复验结果，以及是否允许进入视觉稿。

用户确认设计验收前不得把整体低保真宣称为模块设计完成；影响业务闭环的发现必须回到第8节重新验收。

## 11. 执行交付验收与跨模块联调

代码实现后、对外交付或宣称模块完成前，形成《模块交付验收记录》。以已确认业务闭环基线、模块设计验收和实际实现为输入，验证并留存可复查证据：

- 角色权限、状态流转、任务生成／关闭、正式提交、结果回写和失败恢复的真实行为；
- 正常、异常、取消、重开和恢复情景的端到端测试结果；
- 已确认跨模块接口的输入输出、返回、幂等／重复提交保护及错误边界；
- 已登记桩子没有被实现静默补全，未启动模块和端没有被越界实现；
- 缺陷、豁免、复验和最终用户确认。

没有代码时不得伪造交付验收；只可报告达到模块业务闭环或模块设计验收的层级。跨模块联调只在相关模块与接口都具备已确认基线后开启，不以单模块内部资料推演另一模块。

## 12. 沉淀结果

形成有效结论后：

1. 更新对应规则、接口、设计、代码或验收子池；
2. 更新模块首页的当前版本、未决问题和下一步；
3. 被替代资料移入历史并标注替代关系；
4. 跨模块影响只更新已确认接口；
5. 新模块或成熟度变化先更新范围登记。

任何当前有效正式文件发生版本升级、替代、改名、拆分或合并时，必须在当轮对话中显式报告：原版本与新版本、变更原因、核心影响、受影响文件，以及当前任务是否变化。文件写入、Git提交或远程同步不能替代这条用户可见通知。

因跨模块、后续方案、角色确认或当前阶段不展开而保留的未闭合点统一命名为“桩子”。每个桩子记录所属对象、待确认内容、归属阶段或模块及是否阻塞；桩子不是确认规则，不得在下游静默补全。

总池保存“现在相信什么”，历史池保存“为什么走到这里”，Skill 保证“下一次怎样继续”。

## 13. 维护项目驾驶舱

项目存在根 `README.md` 驾驶舱和 `docs/progress/README.md` 进度规范时，在项目状态检查、阶段切换或收工整理中读取该规范并执行：

1. 正式资料保存业务事实；驾驶舱只保存当前项目判断；日／周记录只保存带日期的过程快照；
2. 当前唯一任务、阶段、页面组、页面总数、验收层级、硬闸门、桩子阻塞性或恢复点变化时同步驾驶舱；
3. 收工按进度规范的增量更新矩阵选择文件：普通收工只更新直接承载变化的正式资料和同一份日报，不全量读取或改写页面；
4. 周目标变化、重要里程碑或周末收口时才更新周报；只有硬闸门明确要求时才全量筛查；
5. 每项完成、阻塞和下一步都能追溯到当前有效资料，不从聊天或旧进度记录补事实；
6. 增量矩阵所列适用资料和Git远程状态一致后，才能报告整理闭合。

驾驶舱与正式资料冲突时，以正式资料为准，先修正当前快照；历史日／周记录保留当时状态并按需增加更正说明。未命中驾驶舱触发器时保持本页不变。进度使用可验证的阶段状态，不制造无客观口径的完成百分比。
